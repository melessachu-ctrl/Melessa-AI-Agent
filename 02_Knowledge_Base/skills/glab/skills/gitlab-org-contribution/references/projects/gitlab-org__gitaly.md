# gitlab-org/gitaly

Gitaly, the Git RPC service. It does not squash at merge, so every commit lands on `master` as written: each must stand alone with a scoped subject and, when user-facing, a `Changelog:` trailer, and Danger turns commit message problems into errors.

| Fact | Value |
| --- | --- |
| Default branch | `master` |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/gitaly` (personal-fork pipelines failed for lack of runners) |
| Merge settings | Squash default off, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | Atomic commits with scoped subjects (`pkg: Summary`), checked as errors by Danger |
| MR template | None by default (only `RFC.md` and `Security Release.md`); write the description yourself |
| Changelog | `Changelog:` trailer per user-facing commit; the commit title becomes the entry |
| Contributor docs | `CONTRIBUTING.md`, `REVIEWING.md`, `AGENTS.md`, `doc/development.md`, `doc/beginners_guide.md` |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Before you start

- No issue is needed before an MR: `CONTRIBUTING.md`, `REVIEWING.md` and `AGENTS.md` ask for none, there is no default MR template, and 9 of the last 24 merged community MRs carried no `linked-issue`. A `Closes` link mainly lets Danger copy labels and the milestone; a behaviour change still benefits from agreeing the approach in an issue. (observed, 24 MRs; checked 2026-10-21; `gitlab-org/gitaly:CONTRIBUTING.md@7baaf84d`, [!9409](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9409), [!9404](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9404), [!9329](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9329))
- Gitaly has an `ee/` directory: since the MR that added an EE-licensed object storage backend (October 2026), `LICENSE` puts everything under `ee/` under the GitLab Enterprise Edition license in `ee/LICENSE` and the rest under MIT, while `CONTRIBUTING.md` names only the Developer Certificate of Origin and License. Read `ee/LICENSE` before changing anything under `ee/` (see Open questions). (documented; `gitlab-org/gitaly:LICENSE@c2b60c38`, `gitlab-org/gitaly:ee/LICENSE@c2b60c38`, `gitlab-org/gitaly:CONTRIBUTING.md@7baaf84d`, [!9033](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9033))
- `STYLE.md` is the style guide reviewers check against. Tests generate Git data at runtime with `gittest.WriteBlob`, `WriteTree`, `WriteCommit` and `WriteTag` rather than seed repositories, so they work with SHA-1 and SHA-256; test helpers take `testing.TB` and call `tb.Helper()`; `TestMain` lives in `testhelper_test.go` and calls `testhelper.Run()`; errors wrap with `%w`, stay lower case, interpolate with `%q` and are built with `structerr`; developer-facing code uses ASCII only. (documented; `gitlab-org/gitaly:STYLE.md@bd3bba45`)
- `AGENTS.md` (`CLAUDE.md` only points to it) has always-on rules: the smallest change that solves the problem, the standard library and already-vendored dependencies before new ones, deletion before addition, the patterns of the file you edit, and `CONTRIBUTING.md`'s commit hygiene for amends and rebases too. The repository ships Agent Skills under `skills/`: `gitaly-rpc-development` for adding or changing an RPC, and `gitaly-rpc-querying`. (documented; `gitlab-org/gitaly:AGENTS.md@6d1c64e3`, `gitlab-org/gitaly:CLAUDE.md@f3931564`, `gitlab-org/gitaly:skills/gitaly-rpc-development/SKILL.md@2dffb8f5`)

## Commits

- Make each commit atomic, with a scoped subject (`pkg: Summary`) of at most 72 characters starting with a capital letter, a body that explains why, full URLs instead of `#123` or `!123`, and the commit that introduced a bug when you fix one. Danger reports these as errors because squash is off. Name that commit in the form `git show -s --pretty=reference` prints (`<short sha> (<subject>, <date>)`), and link an issue with a trailer such as `Fixes: <full issue URL>`. `Signed-off-by:` appears in the guide's example, but nothing checks it: community commits without it merged. (enforced; documented; observed, 2 MRs; `gitlab-org/gitaly:CONTRIBUTING.md@7baaf84d`, `gitlab-org/gitaly:Dangerfile@98432633`, [!8715](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8715), [!8878](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8878), [!8925](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8925), [!9429](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9429), [!9349](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9349))
- Squash review fixes into the commit they fix with `git commit --fixup` and `git rebase -i --autosquash` before review, because a fixup commit would land on `master`. Put refactors in their own commit before the behavior change. No merge commits. (enforced; `gitlab-org/gitaly:CONTRIBUTING.md@7baaf84d`, [!9251](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9251), [!9118](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9118))
- Add a `Changelog:` trailer to user-facing commits, chosen from Gitaly's point of view: do not use `fixed` for something that is not a bug in Gitaly. (documented; `gitlab-org/gitaly:CONTRIBUTING.md@7baaf84d`, [!9118](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9118))

## Local checks before pushing

- Run `make build format lint test` (narrow with `TEST_PACKAGES=./internal/... TEST_OPTIONS='-count=1 -run=X' make test`), `make verify` before pushing, and `make proto` after changing protos (commit the generated code). Check every commit with `git rebase -i --exec='make build format lint test'`. Use `make lint-docs` for docs. A format failure after approval reset an approval. (documented; `gitlab-org/gitaly:doc/development.md@2521a644`, [!9046](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9046))
- `make build`, `make test` (through `prepare-tests`) and `make lint` first build Gitaly's own Git: by default the bundled Git in three versions (master, prev and mvcc), and `make lint` builds all three whatever `GIT_VERSION` says, so the first run is slow. The build runs meson and ninja (pinned in `.tool-versions`) and needs a C toolchain, pkg-config and the development packages of the libraries the Makefile enables: libcurl (`-Dcurl=enabled`), PCRE2 (`-Dpcre2=enabled`), OpenSSL on Linux (`-Dsha1_unsafe_backend=openssl`), and zlib, without which Git does not build. The Makefile passes `-Dwrap_mode=nofallback`, so meson downloads none of them and its setup stops at the first one missing. `doc/beginners_guide.md` assumes a working GDK; outside one, install these before the first `make`. (enforced; documented; `gitlab-org/gitaly:Makefile@0d573533`, `gitlab-org/gitaly:.tool-versions@c58e85a5`, `gitlab-org/gitaly:doc/development.md@2521a644`, `gitlab-org/gitaly:doc/beginners_guide.md@d4944515`, https://github.com/git/git/blob/702d8c1f3b5377a64670b0f22add157b0bfc33dd/INSTALL)
- When you change a proto, document the errors the RPC returns in the proto comments; the generated docs come from them. (observed, 1 MR; [!9118](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9118))
- CI runs every MR's tests in several variants: the Go versions in `go_supported` (1.26 and 1.27, checked 2026-10-22), Git master and the previous Git, Praefect and `-race` (the `test` matrix), SHA-256 repositories (`test:sha256`), reftable (`test:reftable`) and the MVCC reference backend (`test:mvcc`). Reproduce them with `make test-with-sha256`, `make test-with-reftable`, `make test-with-mvcc`, `make test-with-git-prev` and `make test-with-praefect`, narrowed with `TEST_PACKAGES`. MVCC tests skip themselves when `GITALY_TESTING_GIT_BINARY` overrides Git, so run them with the Makefile's bundled Git. (enforced; `gitlab-org/gitaly:.gitlab-ci.yml@2521a644`, `gitlab-org/gitaly:Makefile@0d573533`, `gitlab-org/gitaly:internal/git/gittest/reference_backend.go@0d61a666`)
- Run the tests with the Git the Makefile builds: `make test-go`, narrowed with `TEST_PACKAGES`. For a faster loop on one package, build a single Git with `make build-git` and run `go test` with `GITALY_TESTING_GIT_BINARY` set to `_build/deps/git-distribution/build/bin-wrappers/git`, the path the Makefile itself exports when bundled Git is off. That variable replaces the bundled Git environments, so the MVCC tests then skip, as the previous rule says; run them through make before pushing. (enforced; `gitlab-org/gitaly:Makefile@0d573533`, `gitlab-org/gitaly:internal/git/gitcmd/execution_environment.go@6bf8e47a`, [!9429](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9429))
- To run the tests the way the `test` jobs do, use their image (`gitlab-build-images/debian-<debian>-golang-<go>-rust-<rust>:git-<version>`) and set `GIT_VERSION=default`, as the jobs do: the Makefile builds the bundled Git only when `GIT_VERSION` is empty or `default`, and any other value, such as one already set in the environment, makes it build that Git release instead. The jobs also run `make` as an unprivileged user (`setpriv --reuid=9999 ... env HOME=/tmp/home`) with `GITALY_TESTING_INTERCEPT_HOME=YesPlease` and `GOFLAGS=-buildvcs=false -modcacherw`, which, as the job says, "assures that we pay proper attention to permission bits and that we don't modify the source directory": run them as a normal user, not as root. (enforced; documented; `gitlab-org/gitaly:.gitlab-ci.yml@2521a644`, `gitlab-org/gitaly:Makefile@0d573533`, [!9429](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9429))
- The Makefile exports `GOTOOLCHAIN=local`, so make never downloads the toolchain `go.mod` names; with an older Go first on `PATH`, building the tools and tests fails. Put a Go that matches `go.mod` first on `PATH` (CI tests the versions in `go_supported`). (enforced; `gitlab-org/gitaly:Makefile@0d573533`, `gitlab-org/gitaly:go.mod@e499db81`)
- `make lint` builds the bundled Git and the packed binaries before it lints. To lint only your packages, build the linter and the Gitaly linters plugin, whose make targets are absolute paths (`make "$(pwd -P)/_build/tools/golangci-lint" "$(pwd -P)/_build/tools/gitaly-linters.so"`; a relative target answers "No rule to make target"), then run `_build/tools/golangci-lint run --build-tags continuous_profiler_stackdriver --config .golangci.yml ./internal/<package>/...` and `_build/tools/golangci-lint fmt --config .golangci.yml --diff` on the same paths. Use that build, not a golangci-lint release binary: the Makefile builds golangci-lint (v2.14.0) and the plugin from the same `tools/golangci-lint/go.mod`, because the plugin loads into that build, and the beginner's guide points editors at the same `_build/tools/golangci-lint`. (enforced; documented; `gitlab-org/gitaly:Makefile@0d573533`, `gitlab-org/gitaly:tools/golangci-lint/go.mod@1e87523f`, `gitlab-org/gitaly:doc/beginners_guide.md@d4944515`)
- From the community fork the MR pipeline runs the test matrix, danger-review and `logging-field-validator` in the fork and can pass without a maintainer. Jobs under `.rules_run_on_merge` are manual and may fail outside `gitlab-org/gitaly` and run on their own in the merge train; the `rails-specs` downstream pipeline is started by hand (`start-rails-specs`). (enforced; observed, 1 MR; `gitlab-org/gitaly:.gitlab-ci.yml@2521a644`, [!9429](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9429))

## Review and labels

- Use the two reviewers Danger's roulette suggests (they are often in different time zones), and if you pick someone else, say why: a ready that named someone outside the roulette without a reason drew "is there a reason you are tagging me specifically? Normally you should follow the roulette suggestions". (documented; observed, 1 MR; `gitlab-org/gitaly:REVIEWING.md@145f8c00`, [!9445](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9445#note_4085252467))
- Code Owner approval comes from the Gitaly group in `.gitlab/CODEOWNERS` (`[Code] *`), and an optional `^[Documentation]` section gives `/doc/` and every `*.md` file to a technical writer; Danger also counts `doc/` and the root guides as docs, so a docs change brings a writer into review. (documented; enforced; `gitlab-org/gitaly:REVIEWING.md@145f8c00`, `gitlab-org/gitaly:.gitlab/CODEOWNERS@e2db41be`, `gitlab-org/gitaly:Dangerfile@98432633`, [!9329](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9329))
- `REVIEWING.md` asks for at least one reviewer's approval and allows a single reviewer for a small change, but 10 of the last 15 merged community MRs collected two human approvals: the first reviewer often asks a second team member and says to wait across time zones. Review is fast: in the last 24 merged community MRs the first human note or approval came a median of 0.7 days after opening and the merge 1.4 days after, so silence beyond a few working days is worth a polite nudge. (documented; observed, 24 MRs; checked 2026-10-21; `gitlab-org/gitaly:REVIEWING.md@145f8c00`, [!9118](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9118), [!9429](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9429), [!9326](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9326))
- GitLab Duo reviews against three custom instructions: in non-test Go files, new or changed log fields that are not service-specific come from the LabKit fields package and are neither dynamically named nor unbounded, and for `go.mod` changes it scores the dependency update's risk from 1 to 3. `logging-field-validator` (`make validate-log-fields`) enforces the LabKit field names in CI; only Duo checks for unbounded size and high cardinality. (documented; enforced; `gitlab-org/gitaly:.gitlab/duo/mr-review-instructions.yaml@eb71b31d`, `gitlab-org/gitaly:.gitlab-ci.yml@2521a644`, `gitlab-org/gitaly:Makefile@0d573533`)
- A push that adds commits removes every approval, GitLab Duo's included ("reset approvals from @GitLabDuo and @<reviewer> by pushing to the branch"), so a follow-up a reviewer asks for after approving costs that approval. A maintainer here asks Duo again after each push: on that MR they asked for Duo's new review after each push that answered review, before the author did, so Duo's new review was due each time; check the notes for their "requested review from @GitLabDuo" before you ask through the platform, and re-request the human reviewers once Duo's new review is in, since an approval given before it is lost again if Duo asks for another change (references/review.md, sections 8 and 9). (enforced; observed, 1 MR; [!9445](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9445#note_4091350615))
- Before asking for review, do the self-review in `REVIEWING.md`: the MR is not a draft, every Danger comment is addressed and CI is green. (documented; `gitlab-org/gitaly:REVIEWING.md@145f8c00`)
- Danger's labels rule copies `type::bug`, `type::feature`, `type::maintenance`, `feature::addition`, `security`, `performance`, `Deliverable` and the `group::gitaly` labels from the issues the MR closes, and adds `group::gitaly` on its own only for members of the Gitaly group. From a fork it cannot set them and posts "Labels missing: please ask a reviewer or maintainer to add ..."; add them yourself with `@gitlab-bot label ~"type::bug" ~"group::gitaly"`. An MR that closes no labelled issue gets no such row, so set the type and group anyway. (enforced; `gitlab-org/gitaly:danger/rules/labels/Dangerfile@69e1c2e3`, [!9429](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9429), [!9349](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9349))
- When you discuss code in a reply, link the exact lines (a permalink) rather than describing file and line in prose. (observed, 1 MR; [!9379](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9379))
- Before removing a feature flag, ask the issue assignee: removal waits for rollout conditions the code does not show, and one such MR was closed. (observed, 1 MR; [!8981](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8981))
- If an AI agent opens the MR, `AGENTS.md` asks for a draft whose title ends with the CI-skip marker it names; remove the marker and push when you want a pipeline, because editing the title starts none. (documented; `gitlab-org/gitaly:AGENTS.md@6d1c64e3`)
- Use a plain description for ordinary changes; an MR built from the RFC template went quiet and was closed. (observed, 1 MR; [!8698](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8698))

## Troubleshooting

**Danger: "Danger has errored" with a 403 Forbidden from `update_merge_request`**
- Cause: the milestones rule tries to copy the milestone from the closed issue to the MR, and Danger's token cannot edit an MR from a fork.
- Fix: ignore it; a maintainer sets the milestone.
- Who can fix it: a maintainer or member.
- Sources: `gitlab-org/gitaly:danger/rules/milestones/Dangerfile@380f1dda`, [!9165](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9165), [!8980](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8980)

**A personal-fork pipeline fails with `no_matching_runner` or many failed jobs**
- Cause: the pipeline needs runners and settings personal forks do not have.
- Fix: push to the community fork, open a new MR, close the old one with a link.
- Who can fix it: you.
- Sources: [!8925](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8925), [!9055](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9055), [!9115](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9115)

**Danger reports commit message errors (lowercase start, short references, lines over 72)**
- Cause: the commit message rule runs with squash off, so problems are errors.
- Fix: rewrite the commits with `git rebase -i` and force-push.
- Who can fix it: you.
- Sources: [!8716](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8716), [!8925](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8925)

**`make` fails building the tools or tests with a Go version error, such as `go: <file> requires go >= <version> (running go <older version>; GOTOOLCHAIN=local)`, for example for `tools/golangci-lint/go.mod`**
- Cause: the Makefile sets `GOTOOLCHAIN=local`, and an older Go is first on `PATH`.
- Fix: put a Go that matches `go.mod` first on `PATH` (CI tests the `go_supported` versions, 1.26 and 1.27).
- Who can fix it: you.
- Sources: `gitlab-org/gitaly:Makefile@0d573533`, `gitlab-org/gitaly:go.mod@e499db81`, `gitlab-org/gitaly:.gitlab-ci.yml@2521a644`, https://go.googlesource.com/go/+/refs/tags/go1.27.3/src/cmd/go/internal/gover/toolchain.go

## Why MRs here were closed

- Stale: no review requested, failing pipelines, or comments left unanswered ([!8368](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8368), [!8698](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8698), [!8724](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8724), [!8803](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8803)); one where only Duo reviewed and Danger failed with a 403 ([!9165](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9165)).
- Superseded: moved to the community fork ([!9115](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9115), [!9164](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9164)), made obsolete by an MR removing the code ([!9346](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9346)), or replaced by an approach agreed in review ([!9379](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/9379)).
- A team member already working on the issue ([!8980](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8980)); a premature feature flag removal ([!8981](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8981)).
- Empty or accidental MRs ([!8937](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8937), [!8939](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8939)), and one that added database connection strings to the README ([!8955](https://gitlab.com/gitlab-org/gitaly/-/merge_requests/8955)).
