# gitlab-org/gitlab

The GitLab monorepo: the Rails backend, the REST API (Grape), GraphQL, the Vue frontend, Workhorse (Go), database migrations, EE code under `ee/`, and the product documentation under `doc/`.

| Fact | Value |
| --- | --- |
| Default branch | `master` |
| Languages | Ruby, JavaScript, Vue, Go (Workhorse) |
| Fork to use | Community fork `gitlab-community/gitlab-org/gitlab` (project 41372369) |
| Merge settings | Squash default on, squash message template `%{first_commit}`, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | gitlab-dangerfiles commit linter, no Conventional Commits |
| Changelog | `Changelog:` git trailer (plus `EE: true` for EE-only changes) |
| Contributor docs | `doc/development/` (published at https://docs.gitlab.com/development/) |

Each rule ends with its kind and its sources. "Enforced" means a bot, linter, Danger rule or CI job checks it; "documented" means a guide or template says it; "observed" means reviewers asked for it, with the number of merge requests (MRs) where that was seen.

## Fork and setup

- Request access at https://contributors.gitlab.com/start and branch in `gitlab-community/gitlab-org/gitlab`, not in a personal fork. The community fork carries the CI minutes and settings that community pipelines need, and a personal-fork MR was asked to move. (documented; `gitlab-org/gitlab:CONTRIBUTING.md@334527f8`, `gitlab-org/gitlab:doc/development/contributing/first_contribution/_index.md@88381481`, [!258022](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/258022))
- Open the MR from the community fork into `gitlab-org/gitlab` `master`. An MR opened inside the fork project targets the fork's own default branch and gets closed. (documented; `gitlab-org/gitlab:doc/development/contributing/first_contribution/mr-review.md@cdf1fd18`, [!258022](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/258022))
- For backend or frontend code, work in a local clone of the community fork rather than in the Web IDE: specs, RuboCop, prettier, gettext extraction and the generated-artifact rake tasks need a local environment, and a Web IDE contributor went through several rounds of lint failures. The first-contribution guide recommends the GDK or GDK-in-a-box for local work, but specs and the generators need neither: the test setup configures and starts its own services when the first spec runs, and CI runs the same specs from a plain checkout ([Test environment](#test-environment)). Use a GDK when the change needs the running application or its development database: Before and After screenshots of a UI change, `:js` feature specs (a JavaScript-capable headless browser), validation steps a reviewer follows in a browser, query plans from a database seeded with realistic data, or a new migration, whose `db/structure.sql` and checksum file are written by running it on the development database a GDK provides ([Test environment](#test-environment); preparing that database without the GDK is under [Open questions](#open-questions)). (documented; enforced; `gitlab-org/gitlab:doc/development/contributing/first_contribution/_index.md@88381481`, `gitlab-org/gitlab:doc/development/testing_guide/best_practices.md@5f205b37`, `gitlab-org/gitlab:scripts/prepare_build.sh@0031b508`, `gitlab-org/gitlab:spec/support/helpers/test_env.rb@3afa7a66`, `gitlab-org/gitlab:.gitlab/merge_request_templates/Default.md@4529e892`, [!256644](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/256644))
- GDK-in-a-box is a container image now (`registry.gitlab.com/gitlab-org/gitlab-development-kit/gitlab-gdk-in-a-box:latest`; its VM images are deprecated). It needs 30 GB of disk and a download of more than 8 GB, and the guide suggests giving the container runtime at least 12 GB of RAM and 4 cores; for a standalone GDK the guide says to set aside about two hours. The GDK's own install page and `AGENTS.md` tell first-time setups to consider Caproni instead, which runs GitLab in a local Kubernetes cluster and is to replace the GDK for all GitLab contributors, while the first-contribution guide here still recommends GDK-in-a-box and does not mention Caproni. (documented, with a difference between the two projects' guides; `gitlab-org/gitlab:doc/development/contributing/first_contribution/configure-dev-env-gdk-in-a-box.md@e409ba96`, `gitlab-org/gitlab:doc/development/contributing/first_contribution/configure-dev-env-gdk.md@f81e9fea`, `gitlab-org/gitlab-development-kit:doc/_index.md@cf704d5c`, `gitlab-org/gitlab-development-kit:AGENTS.md@3942e100`, `gitlab-org/caproni:docs/gitlab/_index.md@ce77d760`)
- Keep "Allow commits from members who can merge to the target branch" on. A reviewer who pushes a fix to your branch saves a round trip, but becomes a commit author and can no longer approve, so another approver is then needed. (documented; `gitlab-org/gitlab:doc/development/code_review.md@46d16a14`, [!256644](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/256644))
- If your branch conflicts with `master` and only you push to it, rebase; if others push to it, merge `master` instead. An MR with conflicts is dropped from the merge train. (documented; `gitlab-org/gitlab:doc/development/contributing/merge_request_workflow.md@c7c8aec1`, [!261673](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261673))

## Reporting bugs

- An issue is optional for a clear bug fix. The contributing guide says to open one when none exists, while the merge request workflow guide counts unprioritized bug fixes among the small problems fixed "with or without an issue", and community bug fixes merged with no linked issue. Most community MRs link one anyway: 226 of the 247 merged from 10 to 21 October 2026 carried `linked-issue`. Open the issue first when the fix chooses between behaviours or changes results for many callers. (documented, with a difference between the two guides; observed, 247 MRs; checked 2026-10-21; `gitlab-org/gitlab:doc/development/contributing/_index.md@c0ef4bfa`, `gitlab-org/gitlab:doc/development/contributing/merge_request_workflow.md@c7c8aec1`, [!261567](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261567), [!262500](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/262500))
- Report a bug with `.gitlab/issue_templates/Bug.md` (Summary, Steps to reproduce, Example Project, current and expected behavior, logs, output of checks, possible fixes). Its closing `/label ~"type::bug"` does nothing without a role, so, as the template's own comments say, follow up with an issue comment `@gitlab-bot label ~"type::bug"`, adding `~"reproduced on GitLab.com"` when you reproduced it there. (documented; `gitlab-org/gitlab:.gitlab/issue_templates/Bug.md@f9a343bd`)
- The template asks "If possible" for an example project on GitLab.com. When the feature needs a paid tier that a namespace without it cannot use, or the reproduction would need a write you should not make, say so under Example Project and give what reproduces it instead: the self-managed version you saw it on, or the spec that fails. (documented; `gitlab-org/gitlab:.gitlab/issue_templates/Bug.md@f9a343bd`, [#635966](https://gitlab.com/gitlab-org/gitlab/-/issues/635966))
- Name in Steps to reproduce the surface you actually ran, and quote its answer: two surfaces of one feature can run different code. `GET` and `POST /projects/:id/ci/lint` and the old `Projects::Ci::LintsController` call `Gitlab::Ci::Lint#legacy_validate`, whose static check lets an exception through as a `500`, while the CI Lint page sends the GraphQL `ciLint` mutation, which calls `#validate` and lints through pipeline creation, where any exception becomes `Undefined error (<correlation id>)`. (enforced; `gitlab-org/gitlab:lib/api/lint.rb@ac7db439`, `gitlab-org/gitlab:app/controllers/projects/ci/lints_controller.rb@ac7db439`, `gitlab-org/gitlab:app/graphql/mutations/ci/lint.rb@ac7db439`, `gitlab-org/gitlab:app/assets/javascripts/ci/ci_lint/components/ci_lint.vue@0f1e2c01`, `gitlab-org/gitlab:lib/gitlab/ci/lint.rb@eea56861`, `gitlab-org/gitlab:lib/gitlab/ci/pipeline/chain/config/process.rb@ac7db439`, [#635966](https://gitlab.com/gitlab-org/gitlab/-/issues/635966))
- A Markdown rendering bug can be reproduced on GitLab.com without writing anything. A Markdown file in a project's repository file view is rendered by Banzai's full pipeline with post-processing, the renderer of issues and notes, so a public project's file that holds the construct shows it; `POST /api/v4/markdown` with `gfm=true` and a `project` renders a snippet through the same pipeline and stores nothing (only file context, such as relative links, differs). docs.gitlab.com is built with Hugo, not Banzai, and the repository file APIs return the raw file. Write "This bug happens on GitLab.com", and add `reproduced on GitLab.com`, only once it was seen there: by the agent through the Markdown API, or by the person given the file URL and the element to check. (enforced; `gitlab-org/gitlab:app/views/projects/blob/viewers/_markup.html.haml@0b79d3c2`, `gitlab-org/gitlab:app/services/markup/rendering_service.rb@d55c401d`, `gitlab-org/gitlab:lib/api/markdown.rb@f8875b09`)
- A reproduction step through the rich text editor needs an edit. The editor writes Markdown back only when its document changes: loading content dispatches its transaction with `preventUpdate`, which stops tiptap's `update` event, and `content_editor.vue` emits `change`, the only path that updates the Markdown in `markdown_editor.vue`, on that event alone. Switching to the rich text editor and back without typing leaves the Markdown as it was, so write the step as "type a character and delete it" before switching back. (enforced; `gitlab-org/gitlab:app/assets/javascripts/content_editor/services/content_editor.js@f376b2a8`, `gitlab-org/gitlab:app/assets/javascripts/content_editor/components/editor_state_observer.vue@b034a388`, `gitlab-org/gitlab:app/assets/javascripts/content_editor/components/content_editor.vue@f376b2a8`, `gitlab-org/gitlab:app/assets/javascripts/vue_shared/components/markdown/markdown_editor.vue@b4c5a783`, `gitlab-org/gitlab:yarn.lock@178164c6`, https://unpkg.com/@tiptap/core@2.27.3/src/Editor.ts)

## Commits and title

- Write every commit subject with at least 3 words and at most 72 characters, starting with a capital letter (one lowercase `prefix:` or `[prefix]` before it is allowed), no trailing period, no emoji. Separate subject and body with a blank line, wrap body lines at 72 characters (URLs excepted), and give a body to any commit that changes more than 30 lines across more than 3 files. The danger-review job fails on these. (enforced; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/gitlab/dangerfiles/commit_linter.rb@c64980c9`, `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/gitlab/dangerfiles/base_linter.rb@38d20dd4`, [!254699](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/254699), [!258526](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/258526))
- Put no short references (`#123`, `!123`, `&123`, `group/project#123`, `%19.6`) in commit messages; they fail Danger. A full URL passes, but makes GitLab post a "mentioned in commit" note on the referenced item on every push, so keep links in the MR description. (enforced; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/gitlab/dangerfiles/commit_linter.rb@c64980c9`, [!260353](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260353), [!261715](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261715))
- Lint messages before you push with `mise exec ruby@3.3.11 -- bundle exec ruby scripts/lint/commit_linter.rb <file>` (or `-m "<message>"`), with the prefix [Test environment](#test-environment) gives every Ruby command. It runs the same linter Danger uses and needs only the gitlab-dangerfiles gem, so without the bundle `mise exec ruby@3.3.11 -- gem install gitlab-dangerfiles -v <the version in Gemfile.lock>` and `mise exec ruby@3.3.11 -- ruby scripts/lint/commit_linter.rb -m "<message>"` are enough. With no argument it lints the first commit ahead of `origin/master` (`COMMIT_LINT_BASE` changes the base), the commit the squash message is built from. With the remotes of references/workflow.md, section 6, where `origin` is the community fork, run `git fetch upstream` and `COMMIT_LINT_BASE=upstream/master mise exec ruby@3.3.11 -- bundle exec ruby scripts/lint/commit_linter.rb`, or it may lint a canonical commit instead of yours. It prints nothing and exits 0 when every message passes, and also when it finds no commit to lint; problems are listed and it exits 1. A message fixed after approval costs a force-push; what a push after approval drops is under [CI on the fork and how merging works](#ci-on-the-fork-and-how-merging-works). (documented and enforced; `gitlab-org/gitlab:scripts/lint/commit_linter.rb@236ced52`, `gitlab-org/gitlab:lefthook.yml@43ecb41e`)
- Squash is on by default and the squash message is built from the first commit. Make your first commit the one that describes the whole MR, with a body and the `Changelog:` and `EE:` trailers: the squash template is `%{first_commit}`, the full message of the oldest commit whatever its shape, and Danger lints the oldest commit with a body as the squash message, so the two agree only when the first commit has a body. Danger fails the job on problems in that commit and only warns on the others. A maintainer asked a contributor to move a trailer that sat on the second commit. (enforced; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/plugins/commit_messages.rb@7dccad2f`, `gitlab-org/gitlab:doc/user/project/merge_requests/commit_templates.md@ae75c0d9`, `gitlab-org/gitlab:doc/development/changelog.md@8ecba73c`, [!259951](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259951), [!258074](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/258074))
- Because the first commit's message becomes the squash message, keep it true to the final diff: if review removes something the first commit describes, reword that commit before merge. Do it in the same push as the review fix that makes it untrue: rebuild the branch with the first commit's tree under the new message, put the fix on top, and push once with `--force-with-lease`; rewording later costs a second force-push, which aborts auto-merge or the merge train. When review redesigns the change, replace the first commit instead of adding one, so the old message cannot reach master. (documented; observed, 4 MRs and a reviewer's warning on a fifth, [!266046](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/266046), that its squash would carry an outdated message; `gitlab-org/gitlab:doc/development/changelog.md@8ecba73c`, [!265814](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/265814), [!266080](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/266080), [!265435](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/265435), [!265411](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/265411))
- Keep squash enabled if the MR has "Apply N suggestion(s) to N file(s)" commits, and do not push `fixup!` or `squash!` commits unless squash is on or the MR is a draft; Danger fails both when squash is off. (enforced; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/plugins/commit_messages.rb@7dccad2f`, [!260276](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260276), [!259764](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259764))
- Keep the MR to 10 or fewer logically organized commits. Push review feedback as separate commits and do not squash them until the MR is ready, because reviewers read the follow-up commits. danger-review can fail on MRs with more than 20 commits. (documented; `gitlab-org/gitlab:doc/development/contributing/merge_request_workflow.md@c7c8aec1`, `gitlab-org/gitlab:doc/development/code_review.md@46d16a14`)
- Title the MR as a plain sentence saying what changes, without a Conventional Commits prefix; that is the shape of merged community MRs. (observed, 3 MRs; [!259859](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259859), [!261200](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261200), [!262693](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/262693))

## MR description and templates

- For code, use `.gitlab/merge_request_templates/Default.md` and fill every section: what the MR does and why, references (`Closes <full issue URL>`), Before and After screenshots for any UI change, numbered steps to validate locally (including feature flags to enable), and the acceptance checklist link. Its headings, in order, are `## What does this MR do and why?`, `## References`, `## Screenshots or screen recordings`, `## How to set up and validate locally` and `## MR acceptance checklist`; keep them as written. Reviewers validate from those steps. (documented; `gitlab-org/gitlab:.gitlab/merge_request_templates/Default.md@4529e892`, [!256644](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/256644), [!261103](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261103))
- The template requires screenshots for UI changes and strongly recommends them for every other MR. A utility fix that changes what a component renders (a label cut one character sooner, a count that now reads `1m`) is a UI change for that rule, so add Before and After images; a component spec that reads the rendered text shows the effect and is worth keeping, but it does not replace them. Say in the description how each image was made. (documented; `gitlab-org/gitlab:.gitlab/merge_request_templates/Default.md@4529e892`)
- Any signed-in user can attach an image to a description in a public project without a role: `POST /projects/:id/uploads` (form field `file`) checks nothing beyond read access, and the `markdown` value of its answer (`![name](/uploads/<secret>/<name>)`) goes into the description. `GET /projects/:id/uploads/<secret>/<name>` returns the file to a user without a role too, although the API page lists Guest as a prerequisite, so read the upload back and compare its checksum with your file. Listing a project's uploads needs the Maintainer role. (enforced; documented, with a difference between the page and the code; observed, 2 MRs; `gitlab-org/gitlab:lib/api/markdown_uploads.rb@b5e2ccb5`, `gitlab-org/gitlab:doc/api/project_markdown_uploads.md@9b9b233e`, [!264894](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/264894), [!264895](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/264895))
- The Default template's "What does this MR do and why?" section is the variable `%{first_multiline_commit}`, which GitLab fills with the full message of the first commit that has a body when the MR is first saved from the web form. Write that commit's body so it can open the description, and replace the literal variable if you paste the template or create the MR through the API (references/commits-and-descriptions.md, MR descriptions). (documented; `gitlab-org/gitlab:.gitlab/merge_request_templates/Default.md@4529e892`, `gitlab-org/gitlab:doc/user/project/description_templates.md@5c0f47b0`)
- For a docs-only change, use `Documentation.md` (What does this MR do?, Related issues, author and reviewer checklists). (documented; `gitlab-org/gitlab:.gitlab/merge_request_templates/Documentation.md@ba390ce8`)
- `AGENTS.md` has an agent read `.ai/merge-requests.md` for merge request work and `.ai/git.md` for commits; both bind a person too. In "How to set up and validate locally" list only manual steps a reviewer can follow (a feature flag to enable, a Rails console snippet, a page to visit), never commands that run specs or linters, which CI runs; if you could not follow those steps yourself, as without a GDK ([Test environment](#test-environment)), say so in that section and name the specs that cover the same path (references/local-environment.md, section 5); put what you ran elsewhere, for example in a collapsed block under the first section. Leave out the `/assign me` and `/milestone` lines `.ai/merge-requests.md` asks for: they do nothing without a role (Labels and milestone). Write full URLs, not short references such as `!123` or `#123`, in the MR title and description as well as in commits, as `.ai/git.md` asks, saying that short references render as plain text outside GitLab. A comment written with an agent states its point first and puts the reasoning and evidence in a `<details>` block (`AGENTS.md`, "AI-authored GitLab comments"). (documented; `gitlab-org/gitlab:AGENTS.md@6206e089`, `gitlab-org/gitlab:.ai/merge-requests.md@66453fa0`, `gitlab-org/gitlab:.ai/git.md@4a0d6aba`)
- Delete the template's HTML comments. The top comment suggests a CI-skip marker in the title while the MR is not ready; if you use it, remove it and push when you want a pipeline, because editing the title alone starts nothing. The template's `/label` and `/assign` quick actions only work for users allowed to set those fields. (documented; `gitlab-org/gitlab:.gitlab/merge_request_templates/Default.md@4529e892`, `gitlab-org/gitlab:AGENTS.md@6206e089`)
- If the change alters API behavior a client can observe (a status code, a field, a parameter), say so in the description with your reasoning against the API style guide, so a maintainer can accept it or ask for an additive alternative. (documented; `gitlab-org/gitlab:doc/development/contributing/merge_request_workflow.md@c7c8aec1`, [!261732](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261732), [!260458](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260458))
- Above 500 changed lines, explain why the MR cannot be split; otherwise split it by concern or stack MRs. Touching several CODEOWNERS sections multiplies the approvals you need. An explanation that most of the lines are specs and fixtures does not settle it: reviewers count the separate concerns they must approve at once, and asked for the core change with its docs first and each further behaviour change, mailer or audit event as a follow-up or a stacked MR (references/commits-and-descriptions.md, MR descriptions). (documented; observed, 1; `gitlab-org/gitlab:doc/development/contributing/merge_request_workflow.md@c7c8aec1`, [!255300](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255300), [!265240](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/265240#note_4094622394))
- Two files can need two approvers inside one section too. Each file takes its owners from the last CODEOWNERS line it matches in each section, and each such line is a rule that needs one of its owners; one approval counts for every line whose owners include the approver. A new spec falls under `/spec/` (the `@gitlab-org/maintainers/rails-backend` and `@gl-dx/maintainers` groups), so a change to `scripts/lint-doc.sh` (owned by `@gitlab-org/technical-writing/tw-docops` and `@gitlab-org/tw-leadership`) that adds a spec under `spec/scripts/` needs an approval from each side, all within `[Maintainers]`. Plan for both reviews before you post the ready command. (enforced; documented; observed, 1 MR; `gitlab-org/gitlab:.gitlab/CODEOWNERS@8d29a90b`, `gitlab-org/gitlab:doc/user/project/codeowners/reference.md@dee712e7`, [!256936](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/256936))
- Link the issue as `Closes https://gitlab.com/gitlab-org/gitlab/-/issues/<iid>` at the start of a line, and judge whether it is linked by the `linked-issue` label and your description. The MR API's `closes_issues` list can stay empty for `Closes gitlab-org/gitlab#<iid>` or `Closes #<iid>` because issues are work items, while the community automation account that adds `linked-issue` (not gitlab-bot) still adds the label. (observed, 3 MRs; [!261343](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261343), [!261288](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261288), [!263036](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/263036); see references/commits-and-descriptions.md, Linking the issue)

## Changelog

- Add `Changelog: added|fixed|changed|deprecated|removed|security|performance|other` to a commit when the change is visible to users, changes a REST or GraphQL contract, adds a database migration or fixes a security issue. Leave it out for docs-only, developer-only and pure refactor changes. Danger fails the MR when it adds a migration or removes a feature flag without the trailer; otherwise its "CHANGELOG missing" note is optional. (enforced; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/plugins/changelog.rb@36e1b034`, `gitlab-org/gitlab:doc/development/changelog.md@8ecba73c`, [!255704](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255704))
- `EE: true`: the changelog guide reserves it for changes that exist only in EE, while Danger warns when the MR has a `Changelog:` trailer, changes files under `ee/` and lacks `EE: true` (unless the entry is required, as for a migration). These conflict. Follow the guide (leave it out when the change also affects CE, for example when only EE specs changed) and answer the Danger warning in a thread; reviewers accepted that on three MRs. If a reviewer asks you for the trailer, add it. (documented with a conflicting Danger warning, 6 MRs; `gitlab-org/gitlab:doc/development/changelog.md@8ecba73c`, `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/plugins/changelog.rb@36e1b034`, [!256936](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/256936), [!260458](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260458), [!261813](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261813))
- Behind a feature flag: no changelog entry while the flag is off by default; add one when the flag is enabled by default or removed, or when the MR adds a migration. For a community contribution the guides disagree: `.ai/git.md` ("When to skip") and the feature flag guide give a change behind a default-off flag no entry, while the changelog guide says any contribution from a community member "may have a changelog entry regardless of these guidelines if the contributor wants one". If you keep an entry under that exception, say so in the description. (documented, with a difference between the guides; `gitlab-org/gitlab:doc/development/feature_flags/_index.md@ca626558`, `gitlab-org/gitlab:.ai/git.md@4a0d6aba`, `gitlab-org/gitlab:doc/development/changelog.md@8ecba73c`)

## Test environment

Specs, RuboCop, the commit linter and the GraphQL, OpenAPI and permissions generators run in a plain checkout of the community fork, without the GDK. The test setup configures and starts its own services when the first spec runs, and CI runs the same specs from a plain checkout prepared by `scripts/prepare_build.sh`, so doing what that script does is the closest you get to CI. With Vite off (the default), controller, request, feature, mailer and view specs also need the application CSS built once, with `yarn install` and then `yarn build:css` on the Node and Yarn versions `.tool-versions` names ([Local checks before pushing](#local-checks-before-pushing)). Feature specs tagged `:js` also run a JavaScript-capable headless browser: run those in a GDK. When the change needs the running application, or adds a migration (below), use a GDK instead ([Fork and setup](#fork-and-setup)). (documented; enforced; `gitlab-org/gitlab:doc/development/testing_guide/best_practices.md@5f205b37`, `gitlab-org/gitlab:scripts/prepare_build.sh@0031b508`, `gitlab-org/gitlab:spec/support/helpers/test_env.rb@3afa7a66`)

- Ruby: `.ruby-version` names Ruby 3.4.10 and `.tool-versions` lists `ruby 3.4.10 3.3.11`, keeping 3.3.11 for one milestone for older branches ([!259981](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259981), merged 2026-10-14). MR pipelines and merge trains run `RUBY_VERSION_DEFAULT` from `.gitlab/ci/version.yml` (3.3.12 at the pin), and a community MR's pipelines always do (the `gems <name>` child pipelines of a change under `gems/` run both Rubies; see [CI on the fork and how merging works](#ci-on-the-fork-and-how-merging-works)): the workflow rule for MRs labelled `Community contribution` comes before the opt-in rule for `pipeline:run-with-ruby-next`, and the first matching rule wins, so that label cannot move a community MR to 3.4; the pipeline's name says which Ruby ran, for example `Ruby 3.3.12 MR (community contribution) [...]`. So run the specs you add or change on 3.3, as references/local-environment.md, section 1 says, and every other Ruby command in this file under the same Ruby: in the checkout mise puts the first Ruby `.tool-versions` lists, 3.4.10, first on `PATH`, so a bare `bundle exec ...`, `bin/rake ...` or lefthook hook runs where your 3.3.11 bundle is not installed and stops on a missing gem. Prefix each with `mise exec ruby@3.3.11 --` (`bundle install`, `bin/rspec <spec>`, and the `rake` and `rubocop` commands below); installing the bundle under both Rubies only lets a bare command start, on 3.4.10, which a community MR's pipelines do not run. A GDK is the other way round: it installs the bundle in its `gitlab/` directory with `mise exec -- bundle install`, so under 3.4.10 alone; there, run `mise exec ruby@3.3.11 -- bundle install` in `gitlab/` once before you use the prefix, or every prefixed command, the migration below included, stops on a missing gem. The lefthook hooks are not reached that way: Git runs a hook from the `git commit` or `git push` that invokes it, with that command's environment, so the hooks' `bundle exec` commands run under the Ruby of that `git` command, and the prefix that `bundle exec lefthook install` needs to find the bundle does not carry over to the hooks. Commit and push with `mise exec ruby@3.3.11 -- git commit` and `mise exec ruby@3.3.11 -- git push`. 3.3.11 is the nearest precompiled build: `versions.txt` has no 3.3.12, which the plugin compiles from source. The `.ruby-version` Ruby, 3.4.10, is what `pipeline:run-with-ruby-next` pipelines run, and a community MR does not get those. `mise install` in the checkout installs both listed Rubies from GitLab's precompiled builds: `mise.toml` names GitLab's Ruby plugin and sets `USE_PRECOMPILED_RUBY`, builds exist for Linux amd64 and arm64 and macOS arm64, and elsewhere, or for a version with no build, the plugin compiles from source. Native gems need the build packages the GDK lists for your system (`packages_debian.txt` on Debian). (enforced; documented; `gitlab-org/gitlab:.ruby-version@00dd3e10`, `gitlab-org/gitlab:.tool-versions@00dd3e10`, https://mise.jdx.dev/dev-tools/versions.html#multiple-versions, `gitlab-org/gitlab:.gitlab/ci/version.yml@ff3dce1a`, `gitlab-org/gitlab:.gitlab-ci.yml@bfb0b760`, `gitlab-org/gitlab:mise.toml@6d3761d0`, `gitlab-org/quality/tooling/asdf-gitlab-ruby:README.md@350cd4c6`, `gitlab-org/quality/tooling/asdf-gitlab-ruby:versions.txt@c27d4bcb`, `gitlab-org/quality/tooling/asdf-gitlab-ruby:bin/install@34a8f27a`, `gitlab-org/gitlab-development-kit:packages_debian.txt@bdf2f816`, `gitlab-org/gitlab-development-kit:support/makefiles/Makefile.gitlab.mk@75fea94c`, `gitlab-org/gitlab-development-kit:support/bundle-install@30190863`, `gitlab-org/gitlab:lefthook.yml@43ecb41e`, https://git-scm.com/docs/githooks, https://gitlab.com/gitlab-org/gitlab/-/pipelines/2975901100)
- Name the Ruby beside any output you paste. Output from either Ruby is fine, but Ruby 3.4 changed error messages and backtraces: an opening single quote replaces the backtick (`bignum too big to convert into 'long'` on 3.4, `` `long' `` on 3.3), and backtraces name the class before the method, so without the version a reviewer on the other Ruby sees text that does not match. (documented; observed, 2; `gitlab-org/gitlab:.tool-versions@00dd3e10`, `gitlab-org/gitlab:.ruby-version@00dd3e10`, https://github.com/ruby/ruby/blob/v3_4_0/NEWS.md, [!264870](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/264870), [#635966](https://gitlab.com/gitlab-org/gitlab/-/issues/635966))
- Specs with time limits fail on a slow or loaded machine without saying so. Banzai gives up on a filter after 2 seconds (`RENDER_TIMEOUT`) and on sanitization after 5, and skips the remaining filters once a pipeline has run 5 seconds (`MAX_PIPELINE_SECONDS`), so an example that renders Markdown can get the "Rendering aborted due to complexity issues" paragraph or a document without the elements it looks for; the "is not long running" examples of `full_pipeline_spec.rb` wrap rendering in a 30-second `Timeout` (`BANZAI_FILTER_TIMEOUT_MAX`); and GraphQL stops a query after `graphql_timeout`, 30 seconds by default, so a request spec that selects a large type can answer `null` with timeout errors. Coverage instrumentation slows them too. Before you report such a failure, or quote an example count from a run that had one, rerun the file alone, and say in the description which run the figures come from. (enforced; `gitlab-org/gitlab:gems/gitlab-banzai/lib/banzai/filter/concerns/timeout_filter_handler.rb@347b3009`, `gitlab-org/gitlab:gems/gitlab-banzai/lib/banzai/filter/concerns/pipeline_timing_check.rb@4b553a00`, `gitlab-org/gitlab:spec/support/shared_examples/lib/banzai/filters/filter_timeout_shared_examples.rb@9a629bdc`, `gitlab-org/gitlab:spec/lib/banzai/pipeline/full_pipeline_spec.rb@880a5356`, `gitlab-org/gitlab:config/initializers/1_settings.rb@5d9d8894`, `gitlab-org/gitlab:app/graphql/gitlab_schema.rb@59789479`)
- Services and config files: start the images CI starts, the same way. CI's PostgreSQL service is the public `registry.gitlab.com/gitlab-org/gitlab-build-images:postgres-17` (`PG_VERSION` 17), started with `-c fsync=off -c synchronous_commit=off -c full_page_writes=off -c max_locks_per_transaction=256` (the spec jobs' `.use-pg17` takes the service from `.postgres-auto-explain-service`, which also sets six logging and `auto_explain` settings) and trust authentication (`POSTGRES_HOST_AUTH_METHOD: trust`), which the test entries rely on, since they connect as `postgres` with no password; its Redis is `redis:7.2-alpine`. Do not leave out `max_locks_per_transaction=256`: an initializer makes `db/structure.sql` load in a single transaction (`--single-transaction`), which holds a lock on each of the roughly 7,500 tables, indexes and sequences it creates until it commits, and the PostgreSQL documentation says to raise the default of 64 for transactions that touch many tables. Below it the load can stop with `ERROR: out of shared memory`, more easily on a server another spec run is using. Create the untracked config files the way `scripts/prepare_build.sh` does: `config/gitlab.yml`, `config/cable.yml` and `config/resque.yml` from their `.example` files, pointed at your Redis, and `config/database.yml` from `config/database.yml.postgresql`. Do not leave out `config/cable.yml`: the ActionCable initializer starts without it, but saving a merge request diff publishes a GraphQL subscription through ActionCable, so every spec that creates one fails with `NoMethodError: undefined method 'fetch' for nil`. `config/resque.yml` alone configures every Redis store, since each store falls back to it; leave out `config/redis.yml`, whose example points the clustered stores at a Redis Cluster on `localhost:7001` that CI provides and a laptop does not. (enforced; documented; `gitlab-org/gitlab:.gitlab-ci.yml@bfb0b760`, `gitlab-org/gitlab:.gitlab/ci/global.gitlab-ci.yml@5c5f18a0`, `gitlab-org/gitlab:.gitlab/ci/rails/shared.gitlab-ci.yml@5f205b37`, `gitlab-org/gitlab:config/initializers/structure_load_in_transaction.rb@fece0e20`, `gitlab-org/gitlab:db/structure.sql@50e255ea`, https://www.postgresql.org/docs/17/runtime-config-locks.html, `gitlab-org/gitlab:scripts/prepare_build.sh@0031b508`, `gitlab-org/gitlab:config/database.yml.postgresql@7fe56892`, `gitlab-org/gitlab:config/cable.yml.example@81e79e88`, `gitlab-org/gitlab:config/redis.yml.example@dd2bfa4b`, `gitlab-org/gitlab:lib/gitlab/redis/wrapper.rb@8c6ad10a`, `gitlab-org/gitlab:config/initializers/action_cable.rb@ee76f586`, `gitlab-org/gitlab:app/models/merge_request_diff.rb@81de8c1d`, `gitlab-org/gitlab:app/graphql/graphql_triggers.rb@8b1dc928`, `gitlab-org/gitlab:lib/gitlab/graphql/subscriptions/action_cable_with_load_balancing.rb@a3d2a429`, [!261569](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261569))
- Leave `config/secrets.yml` absent before the first boot: the secrets initializer generates every missing secret (a 128-character `db_key_base`) and writes the file. (enforced; `gitlab-org/gitlab:config/secrets.yml.example@a5c78650`, `gitlab-org/gitlab:config/initializers/2_secret_token.rb@5dac775e`, `gitlab-org/gitlab:config/settings.rb@5dac775e`, `gitlab-org/gitlab:config/initializers/attr_encrypted_patch.rb@c52f2bdf`, [!261569](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261569))
- Test database: keep `main` and `ci` on one database as `config/database.yml.postgresql` has them (`ci` with `database_tasks: false`), and remove the `geo` and `embedding` entries unless you run specs that need them, since CI sets those up only for its `rspec-ee`, `geo` and `db:setup-ee` jobs. CI's default is decomposed instead (`DECOMPOSED_DB` and `SEC_DECOMPOSED_DB` are true, so it copies `config/database.yml.decomposed-sec-postgresql`), which one database does not reproduce. Create and load the test database with `RAILS_ENV=test bundle exec rake db:prepare gitlab:db:lock_writes`, the tasks CI's `setup_db` runs. `db:schema:load` over a loaded database fails with `schema "gitlab_partitions_dynamic" already exists`, because `db/structure.sql` creates its schemas without `IF NOT EXISTS`; drop the database first. After a rebase that changed `db/structure.sql`, the next spec run rebuilds the test database itself (`maintain_test_schema!`) and takes longer. (enforced; `gitlab-org/gitlab:.gitlab-ci.yml@bfb0b760`, `gitlab-org/gitlab:scripts/utils.sh@07677afa`, `gitlab-org/gitlab:config/database.yml.postgresql@7fe56892`, `gitlab-org/gitlab:db/structure.sql@50e255ea`, `gitlab-org/gitlab:spec/spec_helper.rb@ff7b7a58`)
- A migration needs `db/structure.sql` and its `db/schema_migrations/<timestamp>` checksum file written by running it, not by hand: the migration style guide runs `bundle exec rails db:migrate` (here `mise exec ruby@3.3.11 -- bundle exec rails db:migrate`) on your local development database, which the GDK provides and the test database tasks above, run with `RAILS_ENV=test`, do not create (`config/database.yml.postgresql` names it `gitlabhq_development`). Where that database's schema has drifted from `master`, the guide regenerates a clean dump with `scripts/regenerate-schema`, or, when that adds other differences, rebases on `master`, rolls your migration back with the `db:migrate:down:main` task and `VERSION=<migration ID>`, checks out `db/structure.sql` from `origin/master` and migrates again with `db:migrate:main` and the same `VERSION`. Check before you commit that the `db/structure.sql` diff holds only your migration's change. Until preparing that database without the GDK has been tried ([Open questions](#open-questions)), run the migration in a GDK. (documented; `gitlab-org/gitlab:doc/development/migration_style_guide.md@d0487b2a`, `gitlab-org/gitlab:config/database.yml.postgresql@7fe56892`)

(enforced; `gitlab-org/gitlab:spec/support/helpers/test_env.rb@3afa7a66`, `gitlab-org/gitlab:spec/support/helpers/gitaly_setup.rb@9d0f2c1e`, `gitlab-org/gitlab:config/environments/test.rb@e55a9afd`)

## Local checks before pushing

Install the hooks with `mise exec ruby@3.3.11 -- bundle exec lefthook install`, and commit and push as [Test environment](#test-environment) says, so that they run under the CI Ruby. The pre-push hooks run danger_local, RuboCop on changed Ruby files, haml-lint, eslint, prettier, stylelint, markdownlint and Vale on docs, the commit message linter, gettext diff, GraphQL docs and introspection checks, OpenAPI v3 `check_docs`, cells routes checks, migration checks, permissions validation and secrets detection: the same checks the MR pipeline runs. (documented; `gitlab-org/gitlab:lefthook.yml@43ecb41e`) The hooks diff against `origin/master`, and the pre-push commit message hook runs the linter with no `COMMIT_LINT_BASE`, so it lints the first commit ahead of `origin/master`. With the remotes of references/workflow.md, section 6, `origin` is the community fork and `origin/master` its mirror as you last fetched it: after `git fetch upstream` and a rebase the hook can lint a `master` commit instead of yours and pass. Run `git fetch origin master` before pushing, and push with `COMMIT_LINT_BASE=upstream/master mise exec ruby@3.3.11 -- git push`; a hook inherits the environment of the `git` command that runs it. (enforced; `gitlab-org/gitlab:lefthook.yml@43ecb41e`, `gitlab-org/gitlab:scripts/lint/commit_linter.rb@236ced52`, https://git-scm.com/docs/githooks)

Commands to know (run each Ruby command under `mise exec ruby@3.3.11 --`, as [Test environment](#test-environment) says):

- `bundle exec rubocop <changed files>`: reviewers hold approval until a red rubocop job is fixed. (observed, 3 MRs; [!261264](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261264), [!259951](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259951))
- `bin/rspec <spec files>`, in a GDK or in the [test environment](#test-environment); `FOSS_ONLY=1 bin/rspec <spec>` to run as FOSS. Outside CI the spec setup sets `filter_run focus: true` with `run_all_when_everything_filtered`, and RSpec applies a `file:line` filter to its own file but the focus filter to every file without one, so `bin/rspec a_spec.rb b_spec.rb:37` runs `b_spec.rb:37` and nothing of `a_spec.rb`: give a `file:line` run its own `rspec` call, and check the example count. (enforced; `gitlab-org/gitlab:spec/support/rspec.rb@6cf2b6ae`, `gitlab-org/gitlab:spec/spec_helper.rb@ff7b7a58`, https://github.com/rspec/rspec-core/blob/v3.13.1/lib/rspec/core/filter_manager.rb#L34-L55)
- An RSpec summary line does not prove a clean run: quote it only with the exit status (references/local-environment.md, section 5). Here LabKit's field validator can also end a run whose examples all passed with status 2 (next bullet). (enforced; `gitlab-org/gitlab:Gemfile.lock@5d2c9b6b`, `gitlab-org/ruby/gems/labkit-ruby:lib/labkit/logging/field_validator.rb@8a51c71a`)
- `.labkit_logging_todo.yml` is rewritten by the specs themselves. Outside CI, LabKit's field validator removes from it, when RSpec exits, every listed offense whose call site the run saw log the standard field without the deprecated one, and prints "Thank you for improving our logging standards! ... Please commit the changes", whether or not your MR touches logging. Run `git status` before each commit and restore the file (`git checkout HEAD -- .labkit_logging_todo.yml`) unless your change fixed that logging. A local run whose code logs a deprecated field the file does not list exits with status 2 after a summary with no failures and LabKit's "New Offenses Detected" report, which names each call site and the field to use instead: fix the call sites in your change, and quote the run with that status and the reason. (enforced; `gitlab-org/gitlab:.labkit_logging_todo.yml@876484bc`, `gitlab-org/gitlab:Gemfile.lock@5d2c9b6b`, `gitlab-org/ruby/gems/labkit-ruby:lib/labkit/logging/field_validator.rb@8a51c71a`, `gitlab-org/ruby/gems/labkit-ruby:lib/labkit/logging/field_validator/registry.rb@1dcb8ec5`)
- Specs that `require 'fast_spec_helper'` skip gem loading, the Rails boot and the GitLab Shell and Gitaly setup, and load in about a second, so they run with Ruby and the bundle alone: no `config/database.yml`, PostgreSQL, Redis or `tmp/tests`. `fast_spec_helper` steps aside only when `spec_helper` was loaded first, so when one `rspec` call mixes both kinds, load `spec_helper` first (`-r spec_helper`) or run them as separate calls. Specs that require `spec_helper` boot Rails. With Vite off (the default), controller, request, feature, mailer and view specs also need the application CSS built once in your checkout, or RSpec stops at startup naming that command: `yarn build:css` compiles the styles with the `sass`, PostCSS and Tailwind packages, so it needs the Node and Yarn versions `.tool-versions` names and a `yarn install` first. Feature specs tagged `:js` also run a JavaScript-capable headless browser: run those in a GDK ([Fork and setup](#fork-and-setup)). Say in the description which specs you left to the pipeline. (documented; enforced; `gitlab-org/gitlab:doc/development/testing_guide/best_practices.md@5f205b37`, `gitlab-org/gitlab:spec/fast_spec_helper.rb@ff7b7a58`, `gitlab-org/gitlab:spec/support/built_css_check.rb@c4602d49`, `gitlab-org/gitlab:package.json@178164c6`, `gitlab-org/gitlab:scripts/frontend/build_css.mjs@82f8a56c`, `gitlab-org/gitlab:scripts/frontend/lib/compile_css.mjs@2a9b71e7`, `gitlab-org/gitlab:.tool-versions@00dd3e10`)
- `bundle exec rake danger_local`, which the pre-push hook runs, runs `danger dry_run`: it compares `origin/master` with `HEAD` unless `DANGER_LOCAL_BASE` (and `DANGER_LOCAL_HEAD`) name other commits, and it deletes and recreates the branches `danger_base` and `danger_head` in your repository. With the remotes of references/workflow.md, section 6, `origin/master` is the fork's mirror as last fetched, so set `DANGER_LOCAL_BASE=upstream/master` after you fetch, as for `COMMIT_LINT_BASE`. (enforced; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/gitlab/dangerfiles/tasks/main.rake@0399c050`, `gitlab-org/ruby/gems/gitlab-dangerfiles:README.md@c8e0ba71`, https://github.com/danger/danger/blob/v9.6.1/lib/danger/request_sources/local_only.rb#L32-L40, https://github.com/danger/danger/blob/v9.6.1/lib/danger/danger_core/environment_manager.rb#L23-L30, `gitlab-org/gitlab:lefthook.yml@43ecb41e`, `gitlab-org/gitlab:Gemfile.lock@5d2c9b6b`)
- Frontend: `yarn run lint:eslint`, `yarn jest <spec>`, `yarn run prettier --check`. Jest specs that import from `test_fixtures/` read files generated under `tmp/tests/frontend/fixtures-ee/`, and without them those suites fail to load. (documented; `gitlab-org/gitlab:doc/development/testing_guide/frontend_testing.md@29bf3965`)
- **For the frontend fixtures, download the ones CI generated**, which needs neither Rails nor a GDK. From the repository root, `scripts/frontend/download_fixtures.sh` walks your branch's history (50 commits by default; `--max-commits`, `--branch master`) and extracts the first package it finds into `tmp/tests/frontend/`. ## CI on the fork and how merging works

- Pushes from the community fork run a pipeline in the fork, and fork pipelines run only the predictive RSpec and Jest jobs. A green fork pipeline does not prove the full suite passes. To get the whole suite earlier, add `pipeline:run-all-rspec` or `pipeline:run-all-jest` with `@gitlab-bot label` before your next push: the label is read when a pipeline is created, so do not push only to start one (references/review.md, section 11). (documented; `gitlab-org/gitlab:doc/development/pipelines/_index.md@6206e089`, `gitlab-org/quality/triage-ops:triage/processor/community/command_mr_label.rb@46a48236`)
- A change under `gems/<name>/` is tested in a child pipeline named `gems <name>`. In a community-fork pipeline it is triggered by changes to that gem or to the shared gem CI files, `Gemfile.lock`, `.rubocop.yml` and `rubocop/`; canonical pipelines instead run `gems:test`, a child pipeline that `gems:dependency_graph` generates with one `gems <name>` trigger for each changed gem and each in-repo gem that depends on it, so also run the specs of the gems that depend on yours. Its Rubies come from `.gitlab/ci/version.yml`, not `.ruby-version`: `RUBY_VERSION_DEFAULT` (3.3.12, the older one) and `RUBY_VERSION_NEXT` (3.4.10). Every job first runs `gem update --system` and installs the Bundler the gem's `Gemfile.lock` names under `BUNDLED WITH`; do the same in a Ruby you own. RuboCop, `bundle lock --add-checksums` and `RAILS_ENV=test bundle exec rspec` from the gem directory run on both Rubies (RSpec once per Gemfile the gem declares), but `validate-gem` runs on the default Ruby only, and its `scripts/validate-monorepo-gem` checks rubygems.org (that the name exists, that `gitlab_rubygems` owns it, the reserved stub), not your branch, so do not present it as a test. Run the same commands in `gems/<name>` with the gem's own `Gemfile.lock`, on both Rubies. To rerun a gem's specs outside your checkout, the gem's directory and the path dependencies its `Gemfile` names are enough (`gems/gitlab-utils` needs `gems/gitlab-rspec`: `git archive <sha> gems/gitlab-utils gems/gitlab-rspec | tar -x -C <dir>`); its RuboCop also needs `gems/config` and the root `rubocop/` directory, which `gems/config/rubocop.yml` requires. (enforced; observed, 2 MRs; `gitlab-org/gitlab:gems/gem.gitlab-ci.yml@25df617c`, `gitlab-org/gitlab:.gitlab/ci/templates/gem.gitlab-ci.yml@bfb0b760`, `gitlab-org/gitlab:.gitlab/ci/gems.gitlab-ci.yml@897f550a`, `gitlab-org/gitlab:.gitlab/ci/version.yml@ff3dce1a`, `gitlab-org/gitlab:.ruby-version@00dd3e10`, `gitlab-org/gitlab:scripts/validate-monorepo-gem@07a5414f`, `gitlab-org/gitlab:gems/gitlab-utils/Gemfile@4278b190`, `gitlab-org/gitlab:gems/gitlab-utils/.rubocop.yml@f96dc6c3`, `gitlab-org/gitlab:gems/config/rubocop.yml@907eeeef`, https://gitlab.com/gitlab-org/gitlab/-/pipelines/2969962232, https://gitlab.com/gitlab-community/gitlab-org/gitlab/-/pipelines/2968280552)

Pipeline tier labels follow approvals (`pipeline::tier-1` with none, `pipeline::tier-2` while approvals are missing, `pipeline::tier-3` once all are in, and `pipeline:mr-approved` from the first approval on), and only upward: an approval withdrawn or removed by a push leaves the labels as they were, so read the approvals, not the labels, to know whether the MR is approved (enforced; observed, 1: [!260459](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260459)). ## Code rules reviewers apply

- Write code in US English, as the code style guide says ("Code should be written in US English"); under `doc/` Vale also tests it ([Style rules writers apply most](#style-rules-writers-apply-most)). (documented; `gitlab-org/gitlab:doc/development/contributing/style_guides.md@1aa6924f`)

### API and GraphQL contracts

- Do not make breaking changes to REST API v4: do not remove or rename fields, arguments or enum values, change a field's type, add a required argument, tighten auth, or change any status code other than 500. Add a new field, parameter or endpoint and deprecate the old one. An MR that changed an endpoint's response was closed and redone as a new endpoint plus a deprecation. A change from a 500 to another supported status code is not a breaking change (the guide calls it a bug fix); say so in the description. Maintainers have accepted changes to other status codes case by case after explicit discussion, so do not assume one will be accepted without that discussion. (documented; `gitlab-org/gitlab:doc/development/api_styleguide.md@5bc644d9`, [!255239](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255239), [!255702](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255702))
- To deprecate a REST endpoint, add `deprecated true` and a `detail` naming the version and replacement to its Grape `desc` block, update the API docs, and use `Changelog: deprecated`. (documented; `gitlab-org/gitlab:doc/development/api_styleguide.md@5bc644d9`, [!255704](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255704))
- Follow the status codes of the endpoint family you extend; for example a POST action on a merge request answers 201, and a refusal because of state answers 409 through `conflict!`. (observed, 1 MR; [!255702](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255702))
- In GraphQL never remove or rename a field, argument or enum value, and do not change an argument's type (for example String to an enum). Deprecate with `deprecated: { reason:, milestone: }`. (documented; `gitlab-org/gitlab:doc/development/api_graphql_styleguide.md@c527da35`, [!260459](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260459))
- Ship GraphQL backend changes and the frontend that uses them in separate MRs, backend first, and mark new fields the frontend consumes with `@gl_introduced`. During a rolling deploy an unknown field fails the whole query. Danger warns when one MR changes both. (enforced; `gitlab-org/gitlab:tooling/danger/multiversion.rb@2af70304`, [!261373](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261373))

The MR acceptance checklist asks you to confirm that the change is backwards compatible across updates, or that this does not apply; Danger's multiversion check fires only for a GraphQL backend change beside a frontend one, so nothing flags an HTML change. (documented; enforced; `gitlab-org/gitlab:doc/development/multi_version_compatibility.md@50d914c3`, `gitlab-org/gitlab:doc/development/code_review.md@46d16a14`, `gitlab-org/gitlab:tooling/danger/multiversion.rb@2af70304`)

### REST API pages

- Follow the REST API template: description metadata starting "REST API to", intro starting "Use this API to", operation titles with List all, Retrieve, Create, Update, Delete, then the attribute table, the success line, the response attribute table, the example request and the example response. (documented; `gitlab-org/gitlab:doc/development/documentation/restful_api_styleguide.md@6c57ec5a`, [!255702](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255702)) The success line reads, with the right code and relative path:

  ```markdown
  If successful, returns [`200 OK`](rest/troubleshooting.md#status-codes) and the following response attributes:
  ```
- In attribute tables list path attributes first, then required ones, then the rest alphabetically; do not start a description with "The"; sort response attributes alphabetically with dot notation for nested keys. When you document a field, update every example response and table on the page that shows the same entity. (documented and observed; `gitlab-org/gitlab:doc/development/documentation/restful_api_styleguide.md@6c57ec5a`, [!254540](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/254540))
- Write curl examples with long options only, `--request <METHOD>` first even for GET, `--header "PRIVATE-TOKEN: <your_access_token>"` and a double-quoted `--url`. `lint-doc.sh` fails on short options; the order is enforced by reviewers. (enforced and documented; `gitlab-org/gitlab:scripts/lint-doc.sh@19f194a7`, [!260487](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260487))
- Most Markdown REST API pages are being replaced by the generated OpenAPI spec, and writers asked contributors not to expand them. Ask in the issue or MR before adding sections to one. (observed, 2 MRs; [!259766](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259766), [!260668](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260668))

**pre-merge-checks: "Expected to have a latest pipeline that ran in project #278964 but got none!"**
- Cause: no pipeline of the MR other than merge train ones has run in gitlab-org/gitlab. The check skips the fork's pipelines and the train's own, so it finds none when every earlier pipeline ran in the fork.
- Fix: do not push. Ask the approving maintainer to start a pipeline from the MR's Pipelines tab and set auto-merge again once it is green.
- Who can fix it: a maintainer or member.
- Sources: `gitlab-org/gitlab:scripts/pipeline/pre_merge_checks.rb@054e3432`, [!261200](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261200), [!261264](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261264), `gitlab-org/gitlab:doc/development/pipelines/_index.md@6206e089`

**pre-merge-checks fails because the latest pipeline is older than 16 hours or not tier 3**
- Cause: approval came after the last full pipeline, or the pipeline started before the tier-3 label was applied.
- Fix: read the job log for the failed condition, then ask a maintainer to run a new pipeline after the final approval and re-add the MR to the train. Mention the 16-hour window if the merge will wait overnight. Do not ask for a retry: retried jobs stay in the same pipeline, whose name keeps its tier and types, so a pipeline named `tier:1` or `tier:2`, or whose `types:` list starts with a `predictive` type (outside a `spec-only` pipeline), fails the check again even when it turns green. A failed pipeline does not cancel auto-merge (references/review.md, section 9): when `merge_when_pipeline_succeeds` still reads true, the new pipeline is the only thing to ask for.
- Who can fix it: a maintainer or member.
- Sources: `gitlab-org/gitlab:scripts/pipeline/pre_merge_checks.rb@054e3432`, `gitlab-org/gitlab:scripts/pipeline/set_pipeline_name.rb@aaf0935a`, `gitlab-org/gitlab:doc/user/project/merge_requests/auto_merge.md@99807d18`, [!243463](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/243463), [!261348](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261348), [!258795](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/258795), [!261675](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261675)

**Adding GitLabDuo as reviewer returns error DCR4003**
- Cause: the Duo review runs as the Code Review Flow's service account, but GitLab first checks the requester's permission to create the review pipeline in `gitlab-org/gitlab`, which takes the Developer role there; Developer access to the community fork does not count.
- Fix: request it through the contributor platform link (above), which has gitlab-bot request Duo, rather than asking your reviewer; the same link gets Duo's new review after Duo requested changes, where re-requesting Duo yourself also ends in DCR4003 (references/troubleshooting.md, GitLab Duo). Duo is not the human reviewer the MR needs either way.
- Who can fix it: you, through the platform.

## Why MRs here were closed

- Duplicates: another MR for the same issue was already in review or approved ([!257229](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/257229), [!260833](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260833), [!262351](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/262351)), or `master` had already made the change ([!261288](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261288)). Search open MRs for the issue number and rebase before pinging.
- Product or design decisions: the consumer of the change was dropped or undefined ([!257752](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/257752), [!257759](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/257759), [!261534](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261534)), the API had to come first ([!261373](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261373)), or an existing global mechanism already solved it ([!262415](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/262415)). Agree on the approach and the consumer in the issue first.
- Wrong premise: the framework already provided the behavior ([!260686](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260686)). Verify current behavior on `master` and put that evidence in the description.
- Breaking change: changing an existing endpoint's response was redone as a new endpoint plus a deprecation ([!255239](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255239)).
- Issue rules: a shared docs issue allowed one file per contributor ([!261632](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261632)).
- Stale: a draft never marked ready ([!256039](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/256039)), and a typo fix that also changed release-note metadata whose review went unanswered ([!247709](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/247709)).
- Experiments and test MRs opened against the canonical project are closed as noise; experiment in your own fork (see references/why-mrs-get-closed.md, section 4).
