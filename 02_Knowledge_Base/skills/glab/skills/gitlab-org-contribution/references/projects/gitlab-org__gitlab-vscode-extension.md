# gitlab-org/gitlab-vscode-extension

GitLab Workflow, the VS Code extension, in TypeScript. Conventional commits are linted and semantic-release turns them into the changelog and a release. Many language features live in `gitlab-org/editor-extensions/gitlab-lsp` instead, and project detection lives in both (see Before you start).

| Fact | Value |
| --- | --- |
| Default branch | `main` |
| Language | TypeScript |
| Fork to use | Community fork `gitlab-community/gitlab-org/gitlab-vscode-extension` |
| Merge settings | Squash default on, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | Conventional Commits, checked by `lint-commit` |
| MR template | `.gitlab/merge_request_templates/Default.md` |
| Changelog | semantic-release (`release.config.js`); nothing to edit |
| Contributor docs | `CONTRIBUTING.md`, `docs/developer/` (commits, coding guidelines, architecture) |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Before you start

- Check which repository owns the behavior. Code completion, Duo Chat and other language features usually live in `gitlab-org/editor-extensions/gitlab-lsp`; MRs opened here for those were closed and moved. Remote parsing lives in both: the extension's own parser (`src/desktop/git/git_remote_parser.ts`) drives project detection for the sidebar and the MR and issue views, and gitlab-lsp has a separate one for its features. A reviewer pointed out that a project-detection fix covering only the extension reaches half of it; on !3366 and !3365 reviewers opened separate gitlab-lsp work items and proposed a different design, so agree in the issue how both repositories will be covered before writing the MR. (observed, 4 MRs; [!3286](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3286), [!3155](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3155), [!3366](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3366), [!3365](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3365), `gitlab-org/gitlab-vscode-extension:src/desktop/git/git_remote_parser.ts@bd52507c`)
- Link an issue even for a small fix. The MR template says the project "only accepts merge requests related to open issues" and that a bug fix needs one with steps to reproduce, while `CONTRIBUTING.md` lets a trivial change (a typo, or a bug fix of about 20 lines) go straight to an MR and asks for an issue first for a large one. 18 of the last 22 merged community MRs carried `linked-issue`, and issues their authors filed shortly before the MR were accepted. (documented, with a difference between the two; observed, 22 MRs; checked 2026-10-21; `gitlab-org/gitlab-vscode-extension:.gitlab/merge_request_templates/Default.md@f2b2cc21`, `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`, [!3332](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3332), [!3215](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3215), [!3078](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3078))
- `CONTRIBUTING.md` points newcomers to issues labelled `Accepting merge requests`, which no open issue carried on 2026-10-21; recently merged community MRs took issues labelled `Seeking community contributions` or `quick win` instead. (documented; observed, 3 MRs; `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`, [!3398](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3398), [!3358](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3358), [!3418](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3418))
- Confirm the bug against current behavior first: one MR was closed because the behavior was partly intended and partly fixed elsewhere. (observed, 1 MR; [!3219](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3219))
- Branch from current `main` for each MR; an MR carrying another branch's files was closed. (observed, 1 MR; [!3069](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3069))

## Commits and changelog

- Make the MR produce Conventional Commits on `main`: a conventional MR title with squash on (the default) or conventional messages on every commit with squash off. `lint-commit` checks the title when squash is on and every commit otherwise, and does not run for `Draft:` titles or docs-only MRs. On top of `config-conventional` it enforces a header of at most 72 characters and a blank line before body and footer, warns on body lines over 100 characters, does not check subject case, and ignores reverts, `fixup!` and `squash!` commits, "Merge branch" commits and the commits GitLab Dependency Management writes. (enforced; `gitlab-org/gitlab-vscode-extension:docs/developer/commits.md@57f553e1`, `gitlab-org/gitlab-vscode-extension:scripts/commit-lint/lint.js@c9d32085`, `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`)
- An MR that changes nothing under `src`, `scripts`, `test`, `webviews`, `danger`, `mise`, `.gitlab` or `.vscode`, and no root `.js`, `.json`, `.yaml` or `.toml` file, dot file or `Dangerfile`, gets a "Docs-only pipeline" that skips `lint-commit` and the tests. Keep the title conventional anyway: semantic-release still reads the squash commit. (enforced; `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`)
- The project's suggestion commit message is conventional ("chore: Apply N suggestion(s) to N file(s)"), so applying a reviewer's suggestion in the UI keeps `lint-commit` passing even with squash off. (enforced, project setting checked 2026-10-21; observed, 1 MR; [!3417](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3417))
- If you work from a personal fork, set up pull mirroring of the upstream `main` (or update your fork's `main`): an outdated fork `main` makes commitlint lint commits that are not yours ([issue 288](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/issues/288)). (documented; `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`)
- Run `lint-commit` locally before pushing. `scripts/commit-lint/lint.js` reads its inputs from environment variables, which its header says you can set to test it, and refuses to run unless `CI` is set. After the root install (which installs `scripts/commit-lint`), run `node lint.js` in `scripts/commit-lint` with `CI=true`, `LAST_MR_COMMIT=$(git rev-parse HEAD)`, `CI_MERGE_REQUEST_DIFF_BASE_SHA` set to the merge base with the upstream `main` (`git merge-base <upstream remote>/main HEAD`; your fork's `main` may be behind), and either `CI_MERGE_REQUEST_SQUASH_ON_MERGE=true` with `CI_MERGE_REQUEST_TITLE="<MR title>"` (lints the title) or `CI_MERGE_REQUEST_SQUASH_ON_MERGE=false` (lints every commit from the base). (documented in the code; enforced; `gitlab-org/gitlab-vscode-extension:scripts/commit-lint/lint.js@c9d32085`, `gitlab-org/gitlab-vscode-extension:scripts/commit-lint/lint.sh@9cfb654e`, [issue 288](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/issues/288))
- Tick the matching box under "What CHANGELOG entry will this MR create?" (feat, fix or none) and make the commit type agree; semantic-release generates the changelog and version from it. Do not edit a changelog file. (enforced; `gitlab-org/gitlab-vscode-extension:.gitlab/merge_request_templates/Default.md@f2b2cc21`, `gitlab-org/gitlab-vscode-extension:release.config.js@0558a1aa`)

## Local checks before pushing

- Node 22.20.0 is pinned in `mise/config.toml` and is the CI image (`node:22.20.0`). Install with `npm ci`, as CI does (`npm ci --cache "$CI_PROJECT_DIR/.npm" --prefer-offline`); `npm install`, which `CONTRIBUTING.md` gives for development, may rewrite `package-lock.json`. The root `postinstall` runs the same npm command in `webviews/vue3`, `webviews/vue2` and `scripts/commit-lint`, then formats `package.json` with Prettier, so one root install sets up all four. `--ignore-scripts` skips all of that, and `npm run lint` (which also lints both webviews) and the commit linter then lack their dependencies. (enforced; `gitlab-org/gitlab-vscode-extension:mise/config.toml@1b25b697`, `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`, `gitlab-org/gitlab-vscode-extension:package.json@70d571bd`, `gitlab-org/gitlab-vscode-extension:scripts/postinstall.mjs@43274317`, `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`)
- Then run `npm run lint` (`npm run autofix` fixes formatting), the unit tests and the type check below. A reviewer asked for `tsc --noEmit` and `npm run lint` after a failed pipeline. (observed, 2 MRs; [!3062](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3062), [!3063](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3063))
- `npm run test:unit` is Jest over `src` only (`roots: ['src']`, `webviews/` ignored), and the suite is slow: the `test-unit` job, which adds coverage, ran about 30 minutes on a `main` pipeline (checked 2026-10-22). Run `npx jest <your test files>` first and the full suite once. The webviews have their own suites, run by `test-webview` (`cd webviews/vue3`, `npm run test`, Vitest) and `test-webview2` (`cd webviews/vue2`, `npm run test`, Jest); run them when you touch `webviews/`. No job runs only the type check: `tsc` runs inside `npm run build:desktop` (the `test-integration` job) and `npm run build:browser` (`tsc --noEmit`, the `test-browser-build` job), so a type error shows up as a failed integration or browser build; `npx tsc --noEmit -p .` finds it locally. (enforced; observed, 1 job; `gitlab-org/gitlab-vscode-extension:jest.config.js@4143147a`, `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`, `gitlab-org/gitlab-vscode-extension:scripts/utils/desktop_jobs.mjs@e6637d42`, `gitlab-org/gitlab-vscode-extension:scripts/utils/browser_jobs.mjs@e6637d42`, `gitlab-org/gitlab-vscode-extension:docs/developer/writing-tests.md@b3fe31b7`, https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/jobs/17364268958)
- `npm run test:integration` builds the desktop bundle, then `test/run_test.ts` downloads VS Code 1.106.0 (pinned in that file, not read from `engines.vscode`) and runs the suite in it. On Linux it needs a display and the libraries the `test-integration` job installs (`xvfb libxtst6 libnss3 libgtk-3-0 libxss1 libasound2 libsecret-1-0 libgbm-dev git`, Xvfb on `:99` with `DISPLAY=:99.0`), and `CONTRIBUTING.md` warns that it might not run while another VS Code instance is open. (enforced; documented; `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`, `gitlab-org/gitlab-vscode-extension:test/run_test.ts@1b25b697`, `gitlab-org/gitlab-vscode-extension:package.json@70d571bd`, `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`)
- `check-docs-markdown` lints `docs/` and the root Markdown files in the docs-gitlab-com lint image (`registry.gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/lint-markdown:<tag>`, the tag naming the tool versions): `vale --minAlertLevel error docs README.md`, `markdownlint-cli2 'docs/**/*.md' README.md CONTRIBUTING.md` and `lychee --offline --include-fragments`. Run those lines from the repository root in the tag the job names when you change docs. (enforced; `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`)
- Regenerate `ci_variables.json` with `npm run update-ci-variables`; it is scraped from GitLab's docs, so never edit it by hand. (documented; `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`, [!3385](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3385))
- Commit `package-lock.json` with any `package.json` change: `package-lock-integrity` runs `npm install --ignore-scripts` and fails when the lockfile changes ("package-lock.json is out of sync with package.json. Run npm install locally to fix it."). The `lint` job undoes the postinstall's Prettier rewrite of `package.json` (`git checkout .` after `npm ci`) before `npm run lint`, whose `prettier --check` covers `package.json`, so if `git status` shows `package.json` changed after your install, commit the formatted version. (enforced; `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`, `gitlab-org/gitlab-vscode-extension:package.json@70d571bd`)
- Keep each MR small enough to review in one sitting; a dependency bump without the lockfile and an oversized MR both went stale and were closed. (observed, 2 MRs; [!3082](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3082), [!3065](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3065))

## Code and description

- When you change a GraphQL query, keep it working on older GitLab versions (feature-detect or fall back). The `GraphQL` label Danger asks for is added by the project's Danger bot once a maintainer runs the canonical pipeline, so there is nothing to ask for. Put code shared with the Web IDE under `src/common`, and put multi-MR features behind a feature flag. (enforced; observed, 3 MRs; `gitlab-org/gitlab-vscode-extension:danger/graphql_compatibility/Dangerfile@8bdab537`, `gitlab-org/gitlab-vscode-extension:docs/developer/coding-guidelines.md@57f553e1`, [!3399](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3399), [!2622](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/2622), [!2603](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/2603), [!2390](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/2390))
- From the community fork the MR pipeline runs in the fork, and danger-review works there. Before approving or starting the merge train, a maintainer runs a merged results pipeline in the canonical project, and Danger posts again; you need not ask for an upstream pipeline when the fork pipeline is green. The danger-review failure under Troubleshooting is a personal-fork problem. (observed, 1 MR; [!3399](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3399))
- For any visible change, add before and after screenshots and request a UX review; for behavior changes, write the manual test steps you ran in VS Code. The template also has checkboxes for Web IDE interoperability and end-to-end testing. (observed, 2 MRs; [!3228](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3228), [!3029](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3029))
- `.gitlab/CODEOWNERS` covers only documentation, so pick code reviewers from Danger's roulette comment or the history of the touched files; reviewers often hand a review to a colleague with more context. In the last 22 merged community MRs (January to October 2026) the first human note or approval came a median of about 0.7 days after the review request and about 2 days after opening. (enforced; observed, 22 MRs; checked 2026-10-21; `gitlab-org/gitlab-vscode-extension:.gitlab/CODEOWNERS@72651cf3`, [!3418](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3418), [!3398](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3398), [!3385](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3385))

## Troubleshooting

**danger-review fails: "Authentication by CI/CD job token not allowed from gitlab-vscode-extension to project #<your fork>"**
- Cause: Danger uses the CI/CD job token, which a personal fork does not accept from the parent project.
- Fix: open the MR from the community fork, or say danger-review fails only for this reason and ask the reviewer to check the Danger items.
- Who can fix it: you.
- Sources: [!3332](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3332)

**`test-integration-web` fails with "PLAYWRIGHT_ACCESS_TOKEN environment variable is not set", or the end-to-end jobs are missing**
- Cause: the token is not set in the community fork either. `test-integration-web` is `allow_failure`; `test-e2e` and `test-e2e-chat` are created only when `TEST_GITLAB_TOKEN` is set, so fork pipelines lack them, and they are `allow_failure` even in the canonical pipeline; `test-e2e-windows` is manual except on `main` and merge trains. A merged community MR's canonical pipeline passed with `test-e2e`, `test-e2e-chat` and `test-integration-web` all failed.
- Fix: nothing; do not change CI to skip them. Mention these failures only if a reviewer asks.
- Who can fix it: nobody needs to.
- Sources: `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`, https://gitlab.com/gitlab-community/gitlab-org/gitlab-vscode-extension/-/jobs/17109970821, https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/pipelines/2938606394, [!3399](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3399)

**`lint-commit` reports commits that are not yours**
- Cause: your fork's `main` is behind upstream.
- Fix: mirror or update your fork's `main`, rebase, push.
- Who can fix it: you.
- Sources: [issue 288](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/issues/288)

**Danger: "Labels missing: please ask a reviewer or maintainer to add ~"GraphQL""**
- Cause: the diff changes a GraphQL query, and Danger in the community-fork pipeline cannot set labels.
- Fix: make sure the query works or falls back on older GitLab versions; the project's Danger bot adds the label in the canonical pipeline a maintainer runs.
- Who can fix it: nobody needs to.
- Sources: [!3399](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3399), [!2622](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/2622), [!2603](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/2603)

**`npm run test:integration` fails locally with "Error: No project after 5s"**
- Cause: the test setup waits a fixed 5 seconds for the extension to detect the test project, which a slow or loaded machine can miss; another open VS Code instance can also stop the run.
- Fix: close other VS Code windows and rerun on an idle machine, or run the job's script in the CI image (`node:22.20.0` with the packages and Xvfb the job sets up), before changing code.
- Who can fix it: you.
- Sources: `gitlab-org/gitlab-vscode-extension:test/integration/test_infrastructure/initialize_test_environment.js@baa1c78a`, `gitlab-org/gitlab-vscode-extension:.gitlab-ci.yml@1b25b697`, `gitlab-org/gitlab-vscode-extension:CONTRIBUTING.md@dfb7df9c`

**`npm ci` fails with "Downloading ripgrep failed after multiple retries: Error: Request failed: 403"**
- Cause: the `@gitlab-org/gitlab-lsp` dependency pulls `@vscode/ripgrep` 1.17.1, whose postinstall fetches its binary through the GitHub releases API. GitHub allows 60 unauthenticated requests per hour per IP address and answers 403 or 429 past that, so a shared address or a restricted network hits it.
- Fix: set `GITHUB_TOKEN` (the postinstall sends it to api.github.com) and install again. `--ignore-scripts` also gets past it, but skips the webview and commit-linter installs, so say in the MR which checks you could not run.
- Who can fix it: you.
- Sources: `gitlab-org/gitlab-vscode-extension:package-lock.json@70d571bd`, https://registry.npmjs.org/@vscode/ripgrep/-/ripgrep-1.17.1.tgz (`lib/postinstall.js`, `lib/download.js`), https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api

## Why MRs here were closed

- Stale after reviewers asked for a description, tests, a rebase or scoping ([!2390](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/2390), [!3029](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3029), [!3046](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3046), [!3065](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3065), [!3082](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3082)); one whose only review request was a Duo review that failed on credits ([!3229](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3229)).
- Belonged in another repository ([!3155](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3155), [!3286](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3286)).
- Superseded by a maintainer fix ([!3219](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3219), [!3261](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3261)).
- Opened against the upstream project by mistake, or with no changes pushed ([!3162](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3162), [!3071](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3071)).
