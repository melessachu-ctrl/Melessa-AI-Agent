# gitlab-org/api/client-go

GitLab's official Go client for the REST API (plus a few GraphQL-backed services), published as `gitlab.com/gitlab-org/api/client-go/v3`, with a second module (`config/`) in the same `go.work` workspace. Every merge to `main` is released by semantic-release within minutes, and the version bump comes from the MR's labels, not the commit message. The maintainer team is small and reviews every change by hand.

| Fact | Value |
| --- | --- |
| Default branch | `main`; breaking changes target the next-major branch (`release-client-4.0` at the time of writing) |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/api/client-go` |
| Merge settings | Squash default on, squash message template `%{title}` plus a `Changelog:` trailer, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | Conventional Commits with the service file name as scope (no commitlint job) |
| MR template | None |
| Changelog | Generated by semantic-release from MR titles and labels; never edit it |
| Contributor docs | `CONTRIBUTING.md`, `AGENTS.md`, `docs/guides/AddingAPISupport.md`, `docs/release-<N>.0-migration.md` |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Fork and setup

- Open the MR from the community fork and decide that before you open it. In the community fork the lint jobs get large runners and dependency-scanning runs; from a personal fork dependency-scanning is skipped, which makes the security policy bot report a scan mismatch. Moving later means closing the MR and opening a new one. (documented; `gitlab-org/api/client-go:CONTRIBUTING.md@723fdfca`, `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`, [!3033](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3033), [!2978](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2978))
- Install the toolchain pinned in `.tool-versions` with mise (Go, golangci-lint 2.15.0, gofumpt 0.8.0, buf 1.55.1), run `make setup`, and run targets through mise (`mise exec -- make reviewable`) so formatter and linter versions match CI. (documented; `gitlab-org/api/client-go:.tool-versions@c3cad247`, `gitlab-org/api/client-go:AGENTS.md@723fdfca`)
- Before you write code, fetch the latest `main` and search open and recently merged MRs for the same change; `main` moves several times a day. One MR was closed minutes after opening because a change to the same Settings fields had merged nine minutes earlier. (observed, 2 MRs; [!3019](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3019), [!3084](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3084))
- An issue is optional for a bug fix or for adding something the public API docs describe; open one first when you are unsure the change fits. In practice 10 of the last 22 merged community MRs carried `linked-issue`, and those without one merged about as fast (median 4.6 days against 4.3; observed, 22 MRs; checked 2026-10-21; [!3093](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3093), [!3126](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3126)). To take an issue, use `https://contributors.gitlab.com/manage-issue?action=work&projectId=65271576&issueIid=<iid>`, which assigns it to you. (documented; `gitlab-org/api/client-go:CONTRIBUTING.md@723fdfca`, [#2314](https://gitlab.com/gitlab-org/api/client-go/-/issues/2314), [#2308](https://gitlab.com/gitlab-org/api/client-go/-/issues/2308))

## Commits and title

- Title the MR as a Conventional Commit with the service file name in snake_case as scope: `feat(group_milestones): add web_url field to GroupMilestone`, `fix(search): accept nil SearchOptions in every search method`; use `docs(...)`, `test:`, `ci:` or `refactor(...)` for those kinds of change. Write commits the same way. Squash uses the MR title, so the title becomes the commit on `main` and the line in `CHANGELOG.md`. (documented; `gitlab-org/api/client-go:docs/guides/AddingAPISupport.md@b13c901d`, [!3043](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3043), [!3100](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3100))
- For a breaking change, mark the commit with `!` and add a `BREAKING CHANGE:` footer saying what callers must change, in addition to targeting the next-major branch. The release type itself still comes from the label. (observed, 2 MRs; [!2996](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2996), [!3014](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3014))

## MR description

- There is no template. Say what changed and why, link the GitLab API docs page and anchor for each endpoint or field, link the issue with `Closes` or `Fixes` when there is one, say whether the change is breaking, and say how you tested it. A common shape is three sections: What does this MR do?, Is this a breaking change?, How was this tested? A one-line description is accepted for a one-field change that links its issue and docs page. (observed, 30 MRs; [!3126](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3126), [!3106](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3106), [!3100](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3100))
- Answer the breaking-change question precisely: a corrected JSON tag compiles the same but changes the decoded value, and changing tags or return types can break callers that marshal the struct. (observed, 3 MRs; [!3046](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3046), [!2996](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2996))
- When a field or parameter is missing from the GitLab API docs, give reviewers something to check: the OpenAPI document (`doc/api/openapi/openapi_v3.yaml`), the Grape entity or params line at a pinned commit, or a reproducible request against gitlab.com, and say that the docs page lacks it. (observed, 4 MRs; [!3043](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3043), [!3049](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3049), [!2978](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2978))

## Labels and releases

- Set the type label yourself right after opening: `@gitlab-bot label ~"type::feature"` for new fields, methods or options, `~"type::bug"` for fixes, `~"type::maintenance"` for docs, tests and CI. semantic-release reads labels: `breaking change` gives a major, `type::feature` a minor, `type::bug` a patch, `type::maintenance` no release. An MR without one of them triggers no release. A decoding fix that changes nothing at compile time stays a bug. (enforced; `gitlab-org/api/client-go:.releaserc.json@c31b900a`, `gitlab-com/gl-infra/semantic-release-merge-request-analyzer:README.md@a6a80aff`, [!3046](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3046), [!3139](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3139))
- Check the type label after opening: triage-ops copies the `type::` label from the issue your description references, which can leave `type::maintenance` on a feature. Set the right one; a scoped label replaces the copy. (enforced; `gitlab-org/quality/triage-ops:triage/processor/apply_labels_from_related_issue.rb@b4d49ec8`)
- You cannot add `breaking change`; a maintainer adds it when they decide a change is breaking. Ignore the bot's breaking change checklist that follows; it is for maintainers. (enforced; `gitlab-org/quality/triage-ops:triage/processor/community/command_mr_label.rb@46a48236`, [!3014](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3014))
- An ML pass guesses `devops::`, `group::` and `Category:` labels the night after you open the MR, often with a group unrelated to client-go. It does not block merging; correct it with `@gitlab-bot label` if it matters to you. (observed, 36 MRs; [!3090](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3090), [!3044](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3044))
- Never edit `CHANGELOG.md`. After merge there is nothing to do: semantic-release tags a version, updates the changelog and comments "This MR is included in version X". A `type::maintenance` MR ships with the next feature or bug release. Merged and released are different events, so check that comment (or the tags containing the merge commit) before telling anyone it is released. (enforced; `gitlab-org/api/client-go:.releaserc.json@c31b900a`, [!3067](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3067), [!3040](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3040))

## Local checks before pushing

- Run `make reviewable` before every push. It runs setup, generate, fmt, lint and test, which mirror the CI jobs verify-generated-code, golangci-lint, buf-lint and tests:unit. (enforced; `gitlab-org/api/client-go:Makefile@b8968d77`, `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`)
- `make test` is `go test work -race`, which tests every module in `go.work` (the root and `config/`); `go test ./...` from the root leaves `config/` out, as it does any nested module. `make lint` runs golangci-lint once per module (`go list -f '{{.Dir}}' -m | xargs golangci-lint run`), as the golangci-lint job does, then `buf format --exit-code` and `buf lint`, so it needs buf even when no proto changed. (enforced; `gitlab-org/api/client-go:Makefile@b8968d77`, `gitlab-org/api/client-go:go.work@a8e6b939`, `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`)
- Whenever you add a service, add or change a method, or change a signature, run `make generate` and commit the regenerated files under `testing/`. Never edit `*_mock.go`, `*_generated.go` or `*_generated_test.go` by hand; verify-generated-code fails on any diff. (enforced; `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`, `gitlab-org/api/client-go:AGENTS.md@723fdfca`, [!3134](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3134))
- Format with gofumpt. After applying a review suggestion from the web UI, pull the commit and run `make fmt` before pushing anything else, or type the suggestion in locally: a UI suggestion carried spaces where gofmt puts a tab, and lint and verify-generated-code both failed. (enforced; `gitlab-org/api/client-go:.golangci.yml@e92a3cd6`, [!3041](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3041))
- Stay compatible with the two Go releases the project supports (the `go` directive in `go.mod` is the floor); tests:unit runs both with `-race`. (enforced; `gitlab-org/api/client-go:README.md@95aa8491`, `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`)
- Integration tests live in `gitlab_test/` (build tag `integration`). `make testacc-up` starts the `gitlab-ee-no-license` service by default (the EE image without a license, on port 8095, with the token `glpat-ACCTEST1234567890123`); `make testacc-up SERVICE=gitlab-ee` starts the licensed instance CI uses and needs `Gitlab-license.txt` at the repository root. `make test-integration` passes neither the token nor the URL to the tests: every test calls `SetupIntegrationClient`, which skips unless `GITLAB_TOKEN_TEST` is set and otherwise uses `https://localhost:8095/api/v4`, so export `GITLAB_TOKEN_TEST=glpat-ACCTEST1234567890123` and `GITLAB_BASE_URL=http://127.0.0.1:8095/api/v4`, as the CI job sets its own, or the whole suite skips. `docs/guides/AddingAPISupport.md` calls the container a community edition instance and says `make test-integration` runs the tests; it is EE without a license, and the tests skip without that variable. On the unlicensed default the licensed tests do not skip yet: `HasPremiumOrUltimateLicense` reads the plan of the null license GitLab answers, and the whole `gitlab_test` binary panics at the first licensed test until [!3148](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3148) merges (open, checked 2026-10-22). Until then narrow the run to your tests (`go test -race -tags=integration -run '<YourTest>' ./gitlab_test/...`), or use a license. The suite also leaves objects behind (a group with a fixed path), so a second run against the same instance fails: run `make testacc-down`, which removes the volumes, and `make testacc-up` between runs. (enforced; documented, with a conflict; observed, 1 MR; `gitlab-org/api/client-go:Makefile@b8968d77`, `gitlab-org/api/client-go:docker-compose.yml@fd1bbe96`, `gitlab-org/api/client-go:gitlab_test/utils_test.go@e92a3cd6`, `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`, `gitlab-org/api/client-go:docs/guides/AddingAPISupport.md@b13c901d`, [!3148](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3148))

## Code rules reviewers and Duo apply

- Only add support for APIs that GitLab documents publicly. Do not add experimental, beta or undocumented endpoints; open an issue first if unsure and expect the answer to be no. An MR exposing an experimental endpoint owned by another group was closed: adding it would expose it to every downstream consumer. (documented; `gitlab-org/api/client-go:CONTRIBUTING.md@723fdfca`, `gitlab-org/api/client-go:.gitlab/issue_templates/Request New API or Endpoint.md@138737e6`, [!2993](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2993))
- Implement endpoints the way `docs/guides/AddingAPISupport.md` and the neighbouring methods do: `return do[T](s.client, withMethod(...), withPath(...), withAPIOpts(opt), withRequestOpts(options...))`, project and group IDs as `any`, `options ...RequestOptionFunc`, return `(*T, *Response, error)`, add the method to the service interface and keep the `var _ Interface = (*Service)(nil)` check. `AGENTS.md` and the Duo instructions still describe the older `NewRequest` plus `PathEscape` pattern; where they disagree, the guide and the surrounding code win. (documented, with a conflict between documents; `gitlab-org/api/client-go:docs/guides/AddingAPISupport.md@b13c901d`, `gitlab-org/api/client-go:AGENTS.md@723fdfca`, [!3134](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3134))
- Give every List endpoint its own options struct embedding `ListOptions` even when it adds nothing, give each new endpoint its own options struct, and give a new endpoint's response its own struct. (documented; `gitlab-org/api/client-go:docs/guides/AddingAPISupport.md@b13c901d`, [!3134](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3134))
- Place new fields and methods in the order the API docs list them; where a struct already uses another order (Settings is alphabetical), follow the file. (documented; `gitlab-org/api/client-go:CONTRIBUTING.md@723fdfca`, `gitlab-org/api/client-go:.gitlab/duo/mr-review-instructions.yaml@49d50c93`, [!3144](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3144))
- In response structs use plain values and plain slices (`[]T`), and a pointer only when nil means something the zero value cannot say (an absent date). In request options structs make every field a pointer. Maintainers asked three contributors to change new response pointers to plain values. (documented; `gitlab-org/api/client-go:docs/guides/AddingAPISupport.md@b13c901d`, [!3051](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3051), [!3048](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3048))
- Never declare a new slice as a pointer to a slice. When a JSON body must send an explicit empty list, tag the field `omitzero` instead of `omitempty`. Leave existing `*[]T` fields alone, because changing them is breaking. The rule is not linted, so follow the document rather than the nearest example. (documented; `gitlab-org/api/client-go:CONTRIBUTING.md@723fdfca`, `gitlab-org/api/client-go:AGENTS.md@723fdfca`, [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063))
- Use `int64` for every number and `any` instead of `interface{}`. Do not change an existing `int` to `int64` on `main`; that is breaking. (documented; `gitlab-org/api/client-go:AGENTS.md@723fdfca`, [!3076](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3076))
- Model an enumeration as a named string type with constants (the `...Value` types in `types.go`). Adding constants is a feature; retyping an existing string field to the named type is breaking. (observed, 4 MRs; [!2993](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2993), [!3138](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3138), [!3013](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3013))
- Give every exported symbol a doc comment that starts with its name, in the present tense, comment lines under 80 characters, ending with a `GitLab API docs:` line pointing at `https://docs.gitlab.com/api/<page>/#<anchor>` (no `/ee/`, no `.html`, trailing slash). Check the anchor against the live page's headings, because GitLab renames them; several merged MRs only repaired anchors. Spell "GitLab" with that capitalization. (documented and observed, 5 MRs; `gitlab-org/api/client-go:CONTRIBUTING.md@723fdfca`, `gitlab-org/api/client-go:.gitlab/duo/mr-review-instructions.yaml@49d50c93`, [!3085](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3085), [!3103](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3103))
- Put a service method's doc comment, `GitLab API docs:` line included, on the method in the service interface, not on the concrete implementation: a maintainer-filed issue made this the convention, refactor MRs are moving the existing comments, and reviewers ask you to move the comments of the file you touch, following a file already migrated. A `Deprecated:` note stays on the concrete method as well, so staticcheck still warns callers of the concrete type. (documented in an issue; observed, 2 MRs; [#2167](https://gitlab.com/gitlab-org/api/client-go/-/issues/2167), [!3140](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3140), [!3086](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3086#note_4036214108))
- Deprecate instead of removing: add a `Deprecated:` paragraph naming the replacement and the major that removes it (`Deprecated: ... use ListPipelineTriggerJobs instead. To be removed in client-go v4.0.`) and keep the old symbol working. When a method has the wrong signature, add a sibling (a `WithOptions` or V2 variant) and deprecate the old one. (observed, 3 MRs; [!3134](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3134), [!3082](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3082))
- Mark fields that back experimental GitLab features with a comment saying they may change outside major releases (`// Experimental field - may change outside of major releases`). (observed, 2 MRs; [!3041](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3041), [!3100](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3100))
- Do not add client-side validation for rules the server enforces; document the rule in the field comment and say the server returns 400 otherwise. (observed, 1 MR; [!3092](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3092))
- Do not add fields for settings GitLab removed or deprecated, and when a response field is a map, be ready to show whether its keys are an open set (keep the map and say so) or an enumeration (model a struct). (observed, 1 MR; [!3085](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3085))
- Be ready to say who needs a change. Reviewers questioned a response field users could not act on and nobody had needed, asked why fields were duplicated across structs, and said that if other places having it was the only reason, "that's probably a bug rather than a design choice". Name the caller or the API behaviour that needs it; an existing pattern alone does not justify one. (observed, 2 MRs; [!3132](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3132#note_4036248594), [!3085](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3085#note_4015914749))
- When a fix would change behavior for existing callers on `main`, ship it as an opt-in client option, off by default, that becomes the default in the next major and is removed in the one after. Keep such library behavior changes in MRs of their own, separate from field syncs. (observed, 2 MRs; [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063), [!3065](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3065))
- When a maintainer would rather keep today's behavior until users report the case, offer to narrow the MR to the defect alone, leaving every input that works today as it was, instead of an opt-in option; once they agree, retitle the MR, rewrite its description and, if the kind of change moved, set the matching `type::` label, since the label decides the release ([Labels and releases](#labels-and-releases); references/review.md, sections 6 and 7). (observed, 1 MR; [!3143](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3143#note_4080562310))
- Keep the default field selection of the GraphQL-backed work item methods on the Enterprise Edition fields; CE callers pass the CE field list. This default was agreed with the owning product team. (observed, 1 MR; [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063))

## Breaking changes

- Changing a method's return type or parameters, changing a field's type, removing a field or method, and changing the JSON shape of a non-experimental struct are breaking. Keep them off `main`: target the next-major branch, add an entry to that release's `docs/release-<major>.0-migration.md`, and if the branch does not exist yet, wait for a maintainer to create it. Adding fields or methods is not breaking, and neither is a struct losing `==` comparability because it gained a slice or map. (documented; `gitlab-org/api/client-go:README.md@95aa8491`, `gitlab-org/api/client-go:.agents/skills/quick-win-instructions/SKILL.md@2fb4c15a`, [!2996](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2996), [!3076](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3076))
- Major releases come roughly every six months with the Go release cycle, so a breaking MR may wait months. A draft left waiting is closed by the stale policy; ask a maintainer to add `automation:prevent-auto-close`, or reopen and retarget when the branch exists. (observed, 1 MR; [!3014](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3014))

## Tests

- Add unit tests in the service's `_test.go` for every new or changed method: `t.Parallel()`, `mux, client := setup(t)`, `testMethod`, testify `assert` or `require`, large fixtures in `testdata/` loaded with `mustWriteHTTPResponse`. Never use `t.Errorf`, `t.Fatal` or `reflect.DeepEqual`; golangci-lint enforces paralleltest, tparallel, testifylint and forbidigo. (enforced; `gitlab-org/api/client-go:.golangci.yml@e92a3cd6`, `gitlab-org/api/client-go:AGENTS.md@723fdfca`, [!3139](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3139))
- For every new request option, assert the request body or query it produces on every method that accepts it. (observed, 2 MRs; [!3048](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3048), [!3138](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3138))
- Prefer one scenario per test function for API tests; table-driven tests are fine for many simple variations. GIVEN/WHEN/THEN comments: `AGENTS.md` asks for them everywhere, the Duo instructions only for complex tests, and reviews apply the narrower wording. (documented, with a conflict; `gitlab-org/api/client-go:AGENTS.md@723fdfca`, `gitlab-org/api/client-go:.gitlab/duo/mr-review-instructions.yaml@49d50c93`, [!3106](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3106))
- For undocumented endpoints, GraphQL mutations or library-level behavior changes, expect to add integration tests in `gitlab_test/<service>_integration_test.go`, and run them locally; fork pipelines never run them. A maintainer also asked for a response-decoding bug to be recreated in an integration test, and the author added one; if no API call can reproduce a defect, say so in the description. (documented; observed, 1 MR; `gitlab-org/api/client-go:docs/guides/AddingAPISupport.md@b13c901d`, [!2978](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2978), [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063), [!3082](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3082#note_4036196718))
- For a fix whose reason is a specification (an RFC, a header grammar) rather than a failure seen against GitLab, a maintainer asked whether it breaks anything today and for a failing test that confirms the fix. Answer that question plainly in the description, saying whether GitLab itself sends the input, and include from the start a test through the public client path that fails on `main`. (observed, 1 MR; [!3143](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3143#note_4064201956))

## CI on the fork

- Your fork pipeline runs lint, generated-code and unit tests. The merge train (and any merged results pipeline a maintainer starts in the parent) also runs `tests:integration` against a licensed GitLab EE container. Only maintainers can start or rerun the canonical pipelines. (enforced; `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`, [!3048](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3048))
- Since 2026-10-22 a fork pipeline runs `danger-review` from the `gitlab-org/components/danger-review` component, which works there and posts Danger's comment, reviewer roulette included, from a group service account; `autolabels` and the project's own `danger-review` run only in the canonical project. A branch based on an older `main` still runs the old configuration, where both jobs fail in the fork (`secrets_provider_not_found` in the community fork, `script_failure` in personal forks) and Danger posts nothing. They are `allow_failure` either way: do not retry them, judge the pipeline by golangci-lint, buf-lint, verify-generated-code and tests:unit, and set the type label yourself. (enforced; observed, 1 MR in the community fork; `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`, `gitlab-org/api/client-go:Dangerfile@4a19d44b`, [!3083](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3083#note_4070463040), [!3041](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3041))

## Requesting review and choosing reviewers

- Ask for review with `@gitlab-bot ready @<maintainer>`, naming one client-go maintainer. Find them under the `*` rule of `.gitlab/CODEOWNERS` and pick the one who merged recent MRs touching the same file, or the one with the shorter queue (the triage bot posts reviewers' active review counts). The bare ready command picked someone outside the client-go maintainer group on all 15 MRs where it was used; each had to forward the MR. (observed, 15 MRs; `gitlab-org/api/client-go:.gitlab/CODEOWNERS@1fd23e50`, [!3051](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3051), [!3090](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3090))
- The contributor platform's request-review link (in gitlab-bot's welcome note) asked Duo and picked a client-go maintainer on 10 of 12 MRs. (observed, 12 MRs; [!3093](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3093), [!3144](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3144))
- Get a Duo review through the platform's request-review link, which a maintainer pointed contributors to for permission problems, Duo included, or through `@gitlab-bot ready @GitLabDuo` (you can add a maintainer in the same note), which has given mixed results: type it once, and if no Duo review starts, do not repeat it (references/bots.md, section 3); assigning GitLabDuo yourself returned DCR4003 on 29 MRs, and a plain mention starts nothing. Answer every Duo thread before the human review. Duo reviews with `.gitlab/duo/mr-review-instructions.yaml`. (observed, 29 MRs; `gitlab-org/api/client-go:.gitlab/duo/mr-review-instructions.yaml@49d50c93`, [!3040](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3040), [!3092](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3092), [!3148](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3148#note_4060585061))
- If a non-maintainer approves first, the MR still needs a maintainer to start the merge train; ask the reviewer to hand it over, or name a maintainer yourself, stating that it is approved, green and conflict-free. (observed, 3 MRs; [!3048](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3048), [!3046](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3046))
- Batch review fixes into one push, then reply in each thread with what changed and the commit SHA; answer a reviewer's standalone comment, which is not a thread, in a new top-level note that mentions them, because a reply under it opens a thread that blocks the merge here (references/review.md, section 8; observed, 1 MR, [!3143](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3143#note_4065621189)). Every push that changes the diff removes every approval, GitLab Duo's included (observed, 1 MR; [!3082](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3082#note_4041150199)). Then wait for the "reset approvals" note or about a minute, since until GitLab's reset job runs an approval it will remove still reads `approved` (references/review.md, sections 8 and 9), and re-request each reviewer whose state in `GET .../reviewers` reads `reviewed`, `requested_changes` or `unapproved`, which after such a push includes every person who had approved; leave out GitLab Duo, which needs a new review only while it reads `requested_changes`, and `duo-security-review-gitlab-org`, which team members request (references/bots.md, section 3; references/review.md, section 8; the GraphQL mutation and the sidebar button have no hourly limit, `@gitlab-bot ready` has one). Say what changed, and for a test the reviewer asked for, how to run it and that it fails without the fix. A maintainer who only commented, without submitting a review, still reads `unreviewed`, or is not in `GET .../reviewers` at all ([!3143](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3143#note_4064201956), where the maintainer who asked for the failing test was not listed): mention them in your reply. That was enough on !3143, where the maintainer answered the reply that mentioned them while a code owner of the `*` rule was listed reading `unreviewed`. When no listed person will read `unreviewed` after your re-requests, also ask for them once with `@gitlab-bot ready @<maintainer>`, which requests only the people it names; the mutation answers `Reviewer not found` for one who is not listed (references/review.md, sections 7 and 8). (observed, 4 MRs; [!3065](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3065), [!3092](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3092))
- A collapsed "Personal pre-analysis note" is machine-generated and labelled "no action needed"; do not answer it or count it as the first review (references/bots.md, section 6). (observed, 2 MRs; [!3086](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3086#note_3986436354), [!3099](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3099#note_3996271615))
- When a maintainer raises a design question that affects a future major and agrees to defer part of it, ask whether to open a project issue that tracks it against the next major, and link it. (observed, 1 MR; [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063))

## Size and pace

- Do not open many tiny MRs (one field, one doc link, one anchor each), even in a hackathon. Combine related changes into one MR, and for a long list of missing fields open one issue listing them so a maintainer can pre-approve chunks, then send fewer, larger field-sync MRs. Maintainers closed separate doc-link MRs and warned that further ones would be closed. (observed, 9 MRs; [!3053](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3053), [!3099](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3099#note_3993627978), [!3118](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3118))
- If you use an AI assistant, say so, and keep each MR small enough for a maintainer to verify by hand: maintainers explained that generated MRs still have to be validated one by one. (observed, 1 MR; [!3053](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3053))
- Keep only a few MRs waiting for a first review at a time. The project has three maintainers, and a maintainer asked a contributor with many open MRs to stop opening new ones and to fold related ones together, and invited them to do a first-pass review of other pending MRs and then tell a maintainer an MR is ready for them. (observed, 1 MR; [!3128](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3128#note_3998579963))
- Maintainers review community MRs in batches. In the last 22 merged community MRs (merged 14 to 21 October 2026, just after a hackathon), the first human note or approval came a median of 2.2 days after opening and the merge 4.4 days after, and the merges came from only some of the people in `.gitlab/CODEOWNERS`: check each code owner's GitLab status, and who merged recent community MRs, before naming one. (observed, 22 MRs; checked 2026-10-21; `gitlab-org/api/client-go:.gitlab/CODEOWNERS@1fd23e50`, [!3093](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3093), [!3137](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3137), [!3086](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3086#note_4031535973))
- When an MR waits, post at most one short reminder after about a week, stating its state (approved or not, green, no conflicts, what is left). If the maintainer's queue is long, politely ask another code owner to take it over. (observed, 5 MRs; [!3066](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3066), [!3119](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3119))

## Troubleshooting

**Assigning GitLabDuo returns "you don't have permission to create a pipeline for Code Review Flow ... Error code: DCR4003"**
- Cause: the Duo review runs as the Code Review Flow's service account, but GitLab first checks your permission to create the review pipeline in `gitlab-org/api/client-go`, which takes the Developer role there.
- Fix: do not retry. Use the platform's request-review link (`https://contributors.gitlab.com/manage-merge-request?action=review&projectId=65271576&mergeRequestIid=<iid>`), or post `@gitlab-bot ready @GitLabDuo @<maintainer>` once; if no Duo review starts, do not repeat it (references/bots.md, section 3).
- Who can fix it: the platform or the bot command.
- Sources: `gitlab-org/gitlab:doc/user/duo_agent_platform/flows/foundational_flows/code_review/_index.md@80a8241c`, `gitlab-org/gitlab:ee/app/services/ai/duo_workflows/create_workflow_service.rb@5fbbff89`, `gitlab-org/gitlab:ee/app/services/ai/duo_workflows/start_workflow_service.rb@a7c66e0e`, [!3040](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3040), [!2993](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2993), [!3148](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3148#note_4060585061)

**danger-review and autolabels are red; no Danger comment appears**
- Cause: your branch predates the 2026-10-22 change to `.gitlab-ci.yml`, so its fork pipeline runs the jobs that need secrets only the canonical project has; both are `allow_failure`.
- Fix: nothing; do not retry or push to re-trigger. Check the four blocking jobs and set the type label yourself. After your next rebase on `main` the fork pipeline runs the danger-review component instead (CI on the fork).
- Who can fix it: nobody needs to.
- Sources: `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`, [!3060](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3060)

**After a bare `@gitlab-bot ready`, the picked reviewer says this is not their project and unassigns; the MR drops to `workflow::in dev`**
- Cause: roulette data resolves to people outside the client-go maintainer group.
- Fix: `@gitlab-bot ready @<maintainer>` with a name from CODEOWNERS, after the one-hour limit.
- Who can fix it: you.
- Sources: `gitlab-org/quality/triage-ops:policies/community/hygiene/ping-incorrect-review-label.yml@544fa8e3`, [!3090](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3090), [!3138](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3138)

**"removed this merge request from the merge train because the pipeline did not succeed" although the fork pipeline was green**
- Cause: the train pipeline adds `tests:integration` against a licensed EE container, which can fail for reasons outside your change (a license interruption caused a two-hour timeout once).
- Fix: open the train pipeline and check the failed job. If it is an environment problem, ask the maintainer once whether anything needs changing; if it is your code, reproduce it locally as [Local checks before pushing](#local-checks-before-pushing) describes (`make testacc-up`, then the tests with `GITLAB_TOKEN_TEST` exported) and push the fix.
- Who can fix it: a maintainer reruns and re-adds the MR.
- Sources: [!2996](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2996)

**golangci-lint and verify-generated-code fail right after you applied a UI suggestion**
- Cause: the suggestion's whitespace is not gofmt-clean.
- Fix: pull, `make fmt`, check `make lint`, push one formatting commit and say it only reformats.
- Who can fix it: you.
- Sources: [!3041](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3041)

**verify-generated-code: "Files should have been generated" with a diff under `testing/`**
- Cause: a service interface or signature changed without regenerating mocks.
- Fix: `mise exec -- make generate`, commit everything it changes, push.
- Who can fix it: you.
- Sources: `gitlab-org/api/client-go:.gitlab-ci.yml@8b8f0028`

**The security policy bot reports a scan mismatch: "The following scans are missing: Dependency scanning"**
- Cause: the MR comes from a personal fork, where dependency-scanning does not run.
- Fix: the policy is in warn mode and does not block. To avoid it, open from the community fork.
- Who can fix it: you.
- Sources: [!2978](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2978)

**Approved and green, but `discussions_not_resolved`**
- Cause: all threads must be resolved, and the bot's reply inside your ready note makes it a thread.
- Fix: resolve your ready thread once the bot has answered, and threads you started once answered.
- Who can fix it: you.
- Sources: [!3139](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3139), [!3147](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3147)

**All comments addressed and green, but the reviewer's "requested changes" still blocks**
- Cause: a Request changes review blocks the merge until the same reviewer approves or removes their request, or a maintainer bypasses it. Your push, a re-request, or a comment-only review from them does not lift it. (enforced; `gitlab-org/gitlab:app/services/merge_requests/update_reviewer_state_service.rb@fb5c7cb6`, `gitlab-org/gitlab:ee/app/services/merge_requests/mergeability/check_requested_changes_service.rb@86fa5a3b`, `gitlab-org/gitlab:ee/app/services/ee/merge_requests/refresh_service.rb@43d553b2`)
- Fix: reply in each thread with the commit, then re-request that reviewer (references/review.md, section 8: the `mergeRequestReviewerRereview` GraphQL mutation for an agent, the Re-request review button in the right sidebar for a person, or `@gitlab-bot ready @<that reviewer>`, which re-requests a listed reviewer for you) with one sentence on what changed, and wait for their approval. If they are away, ask a maintainer to bypass the request.
- Who can fix it: you, then the reviewer.
- Sources: [!3065](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3065), `gitlab-org/gitlab:app/services/merge_requests/request_review_service.rb@8c5023ca`, `gitlab-org/gitlab:app/graphql/mutations/merge_requests/reviewer_rereview.rb@00fb3e11`, `gitlab-org/gitlab:doc/user/project/merge_requests/reviews/_index.md@69117032`

**GitLab Duo's "requested changes" still blocks after you fixed what it flagged**
- Cause: Duo requested changes, and its request blocks the merge until Duo approves a later review or a maintainer bypasses it. Re-requesting Duo yourself goes through and then answers DCR4003 (references/review.md, section 8), so no later review comes from it. (documented; `gitlab-org/gitlab:doc/user/duo_agent_platform/flows/foundational_flows/code_review/_index.md@80a8241c`)
- Fix: reply in each Duo thread with the commit, then open the platform's request-review link (above), tick Duo, untick the maintainer unless you mean to re-request them (never one who approved), and submit once. gitlab-bot re-requests Duo; on [!3147](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3147#note_4061201228) Duo approved within six minutes ([note 4061242865](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3147#note_4061242865)) and its block was gone, leaving the MR `not_approved`, waiting on the maintainer's approval (Duo's does not count). Do this rather than asking a maintainer to re-request Duo; on [!3148](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3148#note_4060585061) a maintainer who did it for the author pointed to the platform instead. (observed, 1 MR, and a maintainer's recommendation on another)
- Who can fix it: you.
- Sources: `gitlab-org/developer-relations/contributor-success/contributors-gitlab-com:contributors/app/controllers/api/v1/manage_merge_request_controller.rb@a8b2e177`, `gitlab-org/quality/triage-ops:triage/processor/community/command_mr_request_review.rb@837f6867`, [!3147](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3147), [!3148](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3148)

**Merge conflicts while waiting for review**
- Cause: `main` gets many merges a day and field syncs touch the same structs.
- Fix: rebase onto the current target branch, rerun `make reviewable`, force-push, say what conflicted, and after the reset note, or about a minute, re-request each reviewer the note names except GitLab Duo and ask them to approve again ([Requesting review and choosing reviewers](#requesting-review-and-choosing-reviewers)).
- Who can fix it: you.
- Sources: [!2996](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/2996), [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063)

**A maintainer asks for integration tests or says they "kicked off ee tests", but your pipeline has no integration job**
- Cause: `tests:integration` needs `ENABLE_EE_ACCEPTANCE_TESTS` and a license file that only the canonical project has.
- Fix: write the tests in `gitlab_test/`, run them locally, report the command and result, and let the maintainer run the canonical pipeline.
- Who can fix it: you write them; a maintainer runs them in CI.
- Sources: [!3048](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3048), [!3063](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3063)

**A maintainer says your change is breaking and asks you to retarget**
- Cause: breaking changes ship only in majors, on `release-client-<major>.0`.
- Fix: change the target branch, rebase with `git rebase --onto`, mark the commit with `!` and `BREAKING CHANGE:`, add a migration guide entry, rerun `make reviewable`. If the branch does not exist yet, keep the MR open and say you will retarget.
- Who can fix it: you.
- Sources: [!3076](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3076), [!3014](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3014)

**A maintainer asks you to combine several small MRs, or closes new ones**
- Cause: every MR is validated by hand.
- Fix: move the commits into one MR, update its title and description, close the others pointing to it, request one review.
- Who can fix it: you.
- Sources: [!3099](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3099#note_3993627978), [!3122](https://gitlab.com/gitlab-org/api/client-go/-/merge_requests/3122)
