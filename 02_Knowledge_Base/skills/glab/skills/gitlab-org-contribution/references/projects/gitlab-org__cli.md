# gitlab-org/cli

glab, the GitLab command-line tool, written in Go with cobra. The squashed MR title becomes the commit on `main` and the release-note line, so titles are Conventional Commits. The command reference under `docs/source` is generated from the help text, and a lint gate fails comments that restate the code.

| Fact | Value |
| --- | --- |
| Default branch | `main` |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/cli` |
| Merge settings | Squash default on, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | Conventional Commits, checked by the `lint_commit` job (commitlint) |
| MR template | `.gitlab/merge_request_templates/Default.md`; `Documentation.md` for docs-only |
| Changelog | Built by GoReleaser from commit subjects on `main`, grouped by type; no file to edit |
| Issue auto-close on merge | On: an issue the description closes is closed when the MR merges into `main` (project setting `autoclose_referenced_issues`, checked 2026-10-22) |
| Contributor docs | `CONTRIBUTING.md`, `AGENTS.md`, `docs/development_process.md` |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Issues first

- Work from an open issue: the Default template states that the project only accepts MRs related to open issues. Replace the template's `Resolves #[issue_number]` with a line starting `Closes https://gitlab.com/gitlab-org/cli/-/issues/<iid>`: both close the issue on merge, but gitlab-bot's label copier ignores `Resolves` (references/commits-and-descriptions.md, Linking the issue). Skip issues labelled blocked, and ask in the issue before coding if the change needs a GitLab.com server change or touches a workstream the team owns. MRs without an issue, with an empty template, needing a server change first, or targeting a workstream not open to contributions were closed. (documented; enforced for the label copier; `gitlab-org/cli:.gitlab/merge_request_templates/Default.md@8003e52b`, `gitlab-org/cli:CONTRIBUTING.md@5686d748`, `gitlab-org/quality/triage-ops:triage/triage/related_issue_finder.rb@6ea4023d`, [!4023](https://gitlab.com/gitlab-org/cli/-/merge_requests/4023), [!3899](https://gitlab.com/gitlab-org/cli/-/merge_requests/3899), [!4067](https://gitlab.com/gitlab-org/cli/-/merge_requests/4067))
- `CONTRIBUTING.md` is softer than the template: it lets a trivial change (a typo, or a bug fix of about 20 lines) go straight to an MR and asks for an issue first only for a large one. Practice follows the template: 28 of the last 30 merged community MRs carried `linked-issue`, so open an issue even for a small bug fix. (documented, with a difference between the two; observed, 30 MRs; checked 2026-10-21; `gitlab-org/cli:CONTRIBUTING.md@5686d748`, [!4008](https://gitlab.com/gitlab-org/cli/-/merge_requests/4008), [!4038](https://gitlab.com/gitlab-org/cli/-/merge_requests/4038))
- `CONTRIBUTING.md` says to report an issue with the "Default" issue template, which does not exist: the templates are Bug, Feature Request, Maintainer Onboarding and Vulnerability Disclosure, and the default issue description in project settings only asks you to pick one. Use Bug for a defect, Feature Request for a feature, and `SECURITY.md` for a vulnerability. (documented, with a conflict; `gitlab-org/cli:CONTRIBUTING.md@5686d748`, `gitlab-org/cli:.gitlab/issue_templates/Bug.md@8003e52b`, https://gitlab.com/gitlab-org/cli/-/tree/1159804bffcc66fb3bde5727b74720b50d7956d4/.gitlab/issue_templates)
- gitlab-bot's ML classifier labels new issues (`automation:ml`, `type::bug`, `bug::functional`, a group and a section), and it has put glab bugs in groups that do not own the CLI. Do not rely on the issue's group reaching the MR: set `group::developer clients`, the group the MR template names, and the `type::` label on the MR yourself with `@gitlab-bot label`. (observed, 2 issues; [#8613](https://gitlab.com/gitlab-org/cli/-/issues/8613), [#8623](https://gitlab.com/gitlab-org/cli/-/issues/8623), `gitlab-org/cli:.gitlab/merge_request_templates/Default.md@8003e52b`)
- glab replaces the deprecated release-cli, whose maintainers decline contributions: fixes and features for creating releases and their asset links (`glab release create`, `--assets-links`) belong here. (documented; observed, 1 MR; `gitlab-org/release-cli:README.md@4a842a47`, [release-cli!201](https://gitlab.com/gitlab-org/release-cli/-/merge_requests/201), https://gitlab.com/groups/gitlab-org/-/epics/15437)
- The Default template's section headings are `## Description`, `## Related Issues`, `## How has this been tested?` and `## Screenshots (if appropriate):`. Fill these headings; never replace them with a structure of your own: an MR with an empty or missing template is closed. The Description section holds `%{all_commits}`, which GitLab expands only when it applies the template to a new MR from the web form; replace it with your own words when you paste the template or create the MR through the API (references/commits-and-descriptions.md, MR descriptions). (documented; `gitlab-org/cli:.gitlab/merge_request_templates/Default.md@8003e52b`)
- `AGENTS.md` suggests `/copy_metadata #<issue>` in the description to carry the issue's labels, and the template ends with `/label` and `/assign me` lines. All three quick actions need `admin_merge_request` in `gitlab-org/cli`, which the Developer role grants and Reporter does not, so they do nothing for a contributor without a role. The `Closes` line above makes gitlab-bot copy the issue's `type::` and group labels; add any other allow-listed label with `@gitlab-bot label`. (enforced; `gitlab-org/cli:AGENTS.md@392ad277`, `gitlab-org/cli:.gitlab/merge_request_templates/Default.md@8003e52b`, `gitlab-org/gitlab:lib/gitlab/quick_actions/issue_and_merge_request_actions.rb@b748b633`, `gitlab-org/gitlab:lib/gitlab/quick_actions/issuable_actions.rb@428a138f`, `gitlab-org/gitlab:app/policies/merge_request_policy.rb@b42110b5`, `gitlab-org/gitlab:config/authz/roles/developer.yml@19df6706`, `gitlab-org/gitlab:config/authz/roles/reporter.yml@6d12e303`, `gitlab-org/quality/triage-ops:triage/triage/related_issue_finder.rb@6ea4023d`)
- Avoid MRs that only edit generated `docs/source` pages. (documented; `gitlab-org/cli:CONTRIBUTING.md@5686d748`)

## Commits and title

- Use `type(scope): subject`, for example `fix(mr): keep the fill flag when push is false`. With squash on (the default), `lint_commit` checks the MR title with any `Draft:` prefix removed; with squash off, every commit. Keep the header within 72 characters as `CONTRIBUTING.md` asks, although commitlint allows 100. (enforced; `gitlab-org/cli:scripts/commit-lint/lint.js@ada4904f`, `gitlab-org/cli:scripts/commit-lint/.commitlintrc.js@f65bf77a`, `gitlab-org/cli:CONTRIBUTING.md@5686d748`)
- The title's type decides where it lands in the release notes (feat, fix, docs, chore(deps), others). (enforced; `gitlab-org/cli:.goreleaser.yml@d51c4cc5`)
- Danger does not run here: there is no Dangerfile on `main` and no Danger job in the CI configuration (checked 2026-10-22), so only commitlint checks messages, with its subject-case rule turned off. Danger's capital-letter rule therefore does not apply, and `CONTRIBUTING.md` asks for a lowercase first letter after `type(scope):`. (documented; `gitlab-org/cli:CONTRIBUTING.md@5686d748`, `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, `gitlab-org/cli:scripts/commit-lint/.commitlintrc.js@f65bf77a`, `gitlab-org/cli:scripts/commit-lint/lint.js@ada4904f`)
- `CONTRIBUTING.md` opens with a DCO notice, but no job checks a `Signed-off-by:` trailer or a signature: merged community MRs had unsigned commits, and the squash commit on `main` is the title alone, so a sign-off in your commits does not land (references/workflow.md, section 1). (observed, 3 MRs; `gitlab-org/cli:CONTRIBUTING.md@5686d748`, `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, [!4099](https://gitlab.com/gitlab-org/cli/-/merge_requests/4099), [!4093](https://gitlab.com/gitlab-org/cli/-/merge_requests/4093), [!4063](https://gitlab.com/gitlab-org/cli/-/merge_requests/4063))

## Local checks before pushing

Run `make generate`, `make gen-docs`, `make check-embed`, `make check-args`, `make lint` and `make test-race`. Then run `lefthook install` so the docs check runs on commit (`LEFTHOOK=0` skips it locally; CI does not). The jobs check_go_generated_code, check_docs_update, check_embed, check_args, lint and tests:unit fail on what these targets report. (enforced; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, `gitlab-org/cli:lefthook.yml@f679ecb2`, `gitlab-org/cli:AGENTS.md@392ad277`)

- Install the pinned tools with `make bootstrap`, which runs `mise install` for what `.tool-versions` lists (Go, golangci-lint, shellcheck, markdownlint-cli2, lychee, vale, node, lefthook). `make lint` runs the golangci-lint on `PATH` when there is one and otherwise downloads the version `.tool-versions` names into `bin/`, so put mise's first on `PATH`. `check_go_version` runs when `go.mod`, `.tool-versions` or `.gitlab-ci.yml` changes, so a Go bump touches all three. The lefthook pre-push hooks run markdownlint, Vale and lychee on the files you push, but each hook that needs a tool (golangci-lint, shellcheck, markdownlint-cli2, Vale, lychee, and Node.js for the commit message check) prints "not found ... Skipping" and succeeds when the tool is missing: a passing hook proves nothing until `make bootstrap` has installed them, so read its output. (enforced; `gitlab-org/cli:.tool-versions@b5b2e198`, `gitlab-org/cli:Makefile@b5b2e198`, `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, `gitlab-org/cli:lefthook.yml@f679ecb2`)
- CI's `lint` job does not run `make lint`: it runs `golangci-lint run` in the `golangci/golangci-lint:v2.14.0-alpine` image, whose version `.tool-versions` keeps in step. When your local result differs from the job's, run the same command in that image. (enforced; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, `gitlab-org/cli:.tool-versions@b5b2e198`)
- `make test` and `make test-race` clear `VISUAL`, `EDITOR`, `PAGER` and `GITLAB_TOKEN` and export `CI_PROJECT_PATH` from `git remote get-url origin`, and some tests depend on that: narrow them with `TEST_PKGS`, or unset those variables before a bare `go test` of one package. Run them in a git clone with an `origin` remote: `internal/testing/cmdtest` runs `git rev-parse --show-toplevel` when it loads, and outside a checkout every test package that imports it stops with "Failed to get root directory". Integration tests (`_integration_test.go`, tag `integration`) run only through `make integration-test-race` with `GITLAB_TEST_HOST` and `GITLAB_TOKEN_TEST` set (a token with `api` scope; the `glab duo` tests need a Duo-enabled user) and skip otherwise; `CONTRIBUTING.md` names `GITLAB_TOKEN` in one of its sentences, but the helper reads `GITLAB_TOKEN_TEST`. `vendor/` is git-ignored: on an inconsistent-vendoring error run `go mod vendor`, never `-mod=mod`. (documented, with a conflict; enforced; `gitlab-org/cli:AGENTS.md@392ad277`, `gitlab-org/cli:Makefile@b5b2e198`, `gitlab-org/cli:internal/testing/cmdtest/helper.go@fa616eff`, `gitlab-org/cli:test/helpers.go@f679ecb2`, `gitlab-org/cli:CONTRIBUTING.md@5686d748`)
- To try a change by hand, build it (`go build -o <dir>/glab ./cmd/glab`) and run it with `GLAB_CONFIG_DIR` pointing at an empty directory that holds a `config.yml` for a test host (top-level `host`, `check_update: false` and `telemetry: false`, and under `hosts.<host>` the `token`, `api_host` and, for a local stub server, `api_protocol: http`), with `GITLAB_TOKEN` unset, since it overrides the file. Run it outside a git repository unless the command needs one: glab detects the host from the remotes of the repository it runs in. Your own configuration and tokens then stay out of the run. To try CI auto-login, set `GLAB_ENABLE_CI_AUTOLOGIN=true` and `GITLAB_CI=true` and the predefined variables it reads (`CI_SERVER_FQDN`, `CI_SERVER_PROTOCOL`, `CI_JOB_TOKEN` and the others in `config_mapping.go`): they replace the usual variables for those keys, such as `GLAB_API_PROTOCOL`, and win over the config file. (documented; enforced; `gitlab-org/cli:AGENTS.md@392ad277`, `gitlab-org/cli:internal/config/schema.go@eab64cb2`, `gitlab-org/cli:README.md@437a1b96`, `gitlab-org/cli:internal/config/config_mapping.go@3204dd39`, `gitlab-org/cli:internal/config/config.go@cadbd956`)
- Run the comment gate locally: `go run ./scripts/comment-overlap -threshold 1.0 -max-findings 0 ./cmd/... ./internal/...`. Of the two scripts in `lint:comments`, only comment-overlap fails the job; comment-ratio against the MR's diff base prints a number for you to weigh and never fails. (enforced; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`)

## Code and docs rules

- Never edit `docs/source` by hand. Change the command's `Short`, `Long`, `Example` or flag help in Go, run `make gen-docs`, and commit the regenerated pages with the code. Keep each `Long` paragraph on one source line. (enforced; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, `gitlab-org/cli:.gitlab/duo/mr-review-instructions.yaml@80cc6798`)
- Write comments that explain why, not what the next line does; the `lint:comments` gate allows zero comment-overlap findings. Do not cite issue or MR numbers in code comments; maintainers asked contributors to remove "(see #NNNN)" and one MR was closed partly over it. (enforced and observed, 2 MRs; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, [!1765](https://gitlab.com/gitlab-org/cli/-/merge_requests/1765), [!4036](https://gitlab.com/gitlab-org/cli/-/merge_requests/4036))
- Test commands with `cmdtest.SetupCmdForTest` and the `gitlabtesting` mocks from `make generate`. Do not add new httpmock-based tests; reuse existing helpers. (documented; `gitlab-org/cli:AGENTS.md@392ad277`)
- Maintainers ask GitLab Duo first, so meet `.gitlab/duo/mr-review-instructions.yaml` before pushing: pass `gitlab.WithContext(ctx)` to every client-go call; add a cmdtest `FactoryOption` rather than a package-level function variable that tests override; no `t.Setenv("NO_COLOR", ...)` or other TTY environment hacks; assert JSON output through a typed struct; a test for each flag path, keeping the baseline test; a shared helper rather than a duplicated function; `resp.HasStatusCode(http.StatusXxx)` rather than magic numbers; when you change one of a set of sibling commands (such as `token list` for project, group and personal tokens), the equivalent test in each sibling package; and no import of one command package from another, so code two commands share goes in `internal/cmdutils/` or another shared package. (documented; `gitlab-org/cli:.gitlab/duo/mr-review-instructions.yaml@80cc6798`)
- Ask before adding a dependency; a dependency choice maintainers did not want contributed to a closure. (observed, 1 MR; [!4036](https://gitlab.com/gitlab-org/cli/-/merge_requests/4036))
- Target `main`, and do not pin a client-go pseudo-version. (observed, 1 MR; [!4067](https://gitlab.com/gitlab-org/cli/-/merge_requests/4067))

## CI on the fork

- Prefer the community fork over a personal one: a community-fork pipeline runs account-verified, while a personal fork fails on account verification. Neither gets the canonical project's test credentials: `CONTRIBUTING.md` says the integration tests "will be skipped locally or in forks" without them, and in community-fork MR pipelines `tests:integration` passed with 17 of its 27 tests skipped, while the merge train ran all 33. So the integration paths of your change first run in the merge train a maintainer starts. (documented; observed, 3 pipelines; checked 2026-10-21; `gitlab-org/cli:CONTRIBUTING.md@5686d748`, https://gitlab.com/gitlab-community/gitlab-org/cli/-/jobs/17359782000, https://gitlab.com/gitlab-community/gitlab-org/cli/-/jobs/17241714186, https://gitlab.com/gitlab-org/cli/-/jobs/17304125919)
- The merge train pipeline runs jobs a fork MR pipeline does not: `build_test`, `build_windows` (amd64 and arm64), `windows_installer`, `snapcraft_build_edge`, advanced SAST, dependency scanning and secret detection (22 jobs against 13); the build and Windows jobs also run in an MR pipeline that changes `.gitlab-ci.yml` or `.goreleaser.yml` (the Windows ones also `scripts/setup_windows.iss`), and the snap job in one that changes `.gitlab-ci.yml` or `snap/snapcraft.yaml`. Otherwise a Windows, snap or security-scan failure shows up only once a maintainer starts the train. When a train dropped an MR on a job `main` had since been changed to tolerate, the maintainer asked the author to rebase onto `main`: an exception to not pushing after approval, made only when a maintainer asks. (enforced; observed, 1 MR; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, https://gitlab.com/gitlab-org/cli/-/pipelines/2973420728, https://gitlab.com/gitlab-community/gitlab-org/cli/-/pipelines/2973391357, [!4081](https://gitlab.com/gitlab-org/cli/-/merge_requests/4081))
- `lint_commit` runs in every merge request pipeline of a public project, the community fork's included, so the fork pipeline already checks your title (or your commits, with squash off); it does not run in a private fork or in a branch pipeline (checked 2026-10-19 on [!4036](https://gitlab.com/gitlab-org/cli/-/merge_requests/4036)'s community fork pipeline and 2026-10-22 on [!4081](https://gitlab.com/gitlab-org/cli/-/merge_requests/4081)'s). `tests:integration` uses `GITLAB_TOKEN_TEST` and `GITLAB_TEST_HOST` from the canonical project's variables. `govulncheck` is manual on MRs. Review-app docs jobs use project secrets. Personal-fork pipelines failed on account verification; one MR was reopened from the community fork to get a pipeline. (enforced; `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`, `gitlab-org/cli:.gitlab/ci/review-docs.gitlab-ci.yml@70adb737`, [!3940](https://gitlab.com/gitlab-org/cli/-/merge_requests/3940))

## Review

- An MR from a non-maintainer needs a reviewer and a maintainer. In practice a maintainer asks GitLabDuo first, then reviews and starts the merge train. (documented; `gitlab-org/cli:docs/development_process.md@8003e52b`)
- The development process describes a Recommend Reviewers flow, but it answers "insufficient permissions" when a community member triggers it; use `@gitlab-bot ready @<maintainer>`, naming a maintainer chosen as below. (observed, 3 MRs; [!3878](https://gitlab.com/gitlab-org/cli/-/merge_requests/3878), [!4070](https://gitlab.com/gitlab-org/cli/-/merge_requests/4070))
- `.gitlab/CODEOWNERS` is one section where the last matching pattern decides, and for most paths it names only the CLI maintainers group, so it gives no person: take the reviewer from the history of the touched files or from who merged recent community MRs (a few people merged all of the last 30). `README.md`, `CONTRIBUTING.md` and `docs/` add one more owner, and the dependency firewall, govern and orbit paths add their domain team. (enforced; observed, 30 MRs; checked 2026-10-21; `gitlab-org/cli:.gitlab/CODEOWNERS@18dc6be3`)
- Name that maintainer on the ready line. A bare `@gitlab-bot ready` went to the bot's pick, who forwarded the MR to another developer; it then waited 12 days with two bot nudges and no review, and naming a maintainer who had merged recent MRs brought, within hours, a GitLab Duo review that maintainer requested, which approved; the human review was still pending more than a day later (checked 2026-10-22). (observed, 1 MR; [!4044](https://gitlab.com/gitlab-org/cli/-/merge_requests/4044))
- In the last 30 merged community MRs (merged 15 to 21 October 2026), the first human note or approval came a median of about 2 days after opening and the merge about 6.6 days after. (observed, 30 MRs; checked 2026-10-21; [!4081](https://gitlab.com/gitlab-org/cli/-/merge_requests/4081), [!4040](https://gitlab.com/gitlab-org/cli/-/merge_requests/4040), [!4093](https://gitlab.com/gitlab-org/cli/-/merge_requests/4093), [!4101](https://gitlab.com/gitlab-org/cli/-/merge_requests/4101), [!4071](https://gitlab.com/gitlab-org/cli/-/merge_requests/4071))
- A Duo review is not a human review. Several MRs whose only review request was GitLabDuo (which failed with DCR4003) were auto-closed after weekly nudges. (observed, 4 MRs; [!3658](https://gitlab.com/gitlab-org/cli/-/merge_requests/3658), [!3878](https://gitlab.com/gitlab-org/cli/-/merge_requests/3878))
- GitLab Duo can approve or request changes on MRs here; its change request blocks the merge until Duo approves a later review or a member bypasses it. (observed, 1 MR here; [!4031](https://gitlab.com/gitlab-org/cli/-/merge_requests/4031))
- A push that changes the diff removes only the approvals of code owners whose rules match the files it changed ("Remove approvals by Code Owners if their files changed"). Every pattern in `.gitlab/CODEOWNERS` names the CLI maintainers group, so a maintainer's approval goes, while GitLab Duo's approval and those of approvers who meet no code owner rule stay; Duo's approval does not meet the code owner rule either, so the MR still needs a maintainer's. Ask for the maintainer's approval once the branch is final. (documented; enforced; observed, 3 MRs, from which the setting is inferred; `gitlab-org/gitlab:doc/user/project/merge_requests/approvals/settings.md@2ac227a8`, `gitlab-org/gitlab:ee/app/services/merge_requests/reset_approvals_service.rb@bbef49e2`, `gitlab-org/cli:.gitlab/CODEOWNERS@18dc6be3`, [!4062](https://gitlab.com/gitlab-org/cli/-/merge_requests/4062), [!4061](https://gitlab.com/gitlab-org/cli/-/merge_requests/4061), [!3891](https://gitlab.com/gitlab-org/cli/-/merge_requests/3891))
- Every thread must be resolved before merge, an approving reviewer's optional, non-blocking suggestion included. Either reply why you leave it as it is and resolve the thread, which keeps the approval, or apply it in one push, locally in one commit (formatters and linters run, a `Co-authored-by:` trailer for the reviewer) or in GitLab where the suggested lines already pass the formatters and linters (references/review.md, section 7), wait for the "reset approvals from" note or about a minute (references/review.md, section 9; on !4134 it came 16 seconds after the push), and say in the reply what changed. Re-request every approver the note names, the reviewer included when it names them (for example a maintainer who approved beside a reviewer outside the CLI maintainers group, whose files the push changed): each reads `unapproved`, which allows it, and the re-request gives them a to-do item; say that their approval went and ask them to approve again. An approver the note does not name, one outside the CLI maintainers group or GitLab Duo (previous rule), keeps the approval and still reads `approved`: do not re-request them, which would remove it (references/review.md, section 8), and resolve their thread yourself once your reply names the commit. If a maintainer had already started the merge train, the push took the MR off it: ask them to start it again. (enforced; documented; observed, 1 MR; `gitlab-org/gitlab:ee/app/services/merge_requests/reset_approvals_service.rb@bbef49e2`, `gitlab-org/gitlab:doc/ci/pipelines/merge_trains.md@43ecb41e`, [!4134](https://gitlab.com/gitlab-org/cli/-/merge_requests/4134#note_4065200311))
- Reviewers here usually resolve their own diff threads once your reply names the commit that addresses them, and authors resolving them was accepted too. Reply with the commit and leave the thread to the reviewer unless they ask you to resolve it. That is for a thread you answered with a change: the thread of an approving reviewer's optional suggestion you decline without a change (previous rule) is yours to resolve, and so are GitLab Duo's threads once you have replied in them, since Duo never resolves its own (references/bots.md, section 3; on [!4148](https://gitlab.com/gitlab-org/cli/-/merge_requests/4148) the author resolved it), and the thread of an approver whose approval your push kept, whom you do not re-request (previous rule). (observed, 8 MRs and 4 reviewers; checked 2026-10-22; [!3992](https://gitlab.com/gitlab-org/cli/-/merge_requests/3992), [!3995](https://gitlab.com/gitlab-org/cli/-/merge_requests/3995), [!4040](https://gitlab.com/gitlab-org/cli/-/merge_requests/4040), [!4062](https://gitlab.com/gitlab-org/cli/-/merge_requests/4062), [!4105](https://gitlab.com/gitlab-org/cli/-/merge_requests/4105), [!4148](https://gitlab.com/gitlab-org/cli/-/merge_requests/4148))
- This project pilots gitlab-bot giving the binding approval on Duo's behalf when Duo is the only reviewer. The pilot skips community MRs and, while its switch is off, only posts internal "would have" notes, so it changes nothing for you: you still need a human reviewer and maintainer. (documented; `gitlab-org/quality/triage-ops:REACTIVE.md@f98daef9`)

## Troubleshooting

**check_docs_update: "Documentation changes detected! ... Run make gen-docs", or check_go_generated_code: "Files should have been generated"**
- Cause: help text or interfaces changed without regenerating.
- Fix: `make gen-docs` and `make generate`, commit, push.
- Who can fix it: you.
- Sources: `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`

**lint_commit fails on type-enum or header-max-length**
- Cause: with squash on it checks the MR title; with squash off, every commit.
- Fix: retitle the MR to `type(scope): subject` and get a new pipeline (push or ask the reviewer); with squash off, reword commits and force-push.
- Who can fix it: you.
- Sources: `gitlab-org/cli:scripts/commit-lint/lint.js@ada4904f`

**lint:comments fails with comment-overlap findings**
- Cause: a new comment restates the code; zero findings are allowed.
- Fix: delete comments that repeat the code, keep only the why, rerun the command above.
- Who can fix it: you.
- Sources: `gitlab-org/cli:.gitlab-ci.yml@b5b2e198`

**Your personal fork pipeline does not run (account verification)**
- Cause: the personal fork's CI requires a verified account.
- Fix: push the branch to the community fork and open the MR from there.
