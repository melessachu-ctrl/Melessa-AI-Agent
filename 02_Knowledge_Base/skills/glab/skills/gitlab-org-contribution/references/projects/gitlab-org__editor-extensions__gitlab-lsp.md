# gitlab-org/editor-extensions/gitlab-lsp

The GitLab Language Server and the Duo CLI (`packages/cli`): a TypeScript monorepo built with bun and turbo under mise. Reviews are deep and often take several rounds, and maintainers frequently prefer a server-side fix or a simpler approach of their own.

| Fact | Value |
| --- | --- |
| Default branch | `main` |
| Language | TypeScript |
| Fork to use | Community fork `gitlab-community/gitlab-org/editor-extensions/gitlab-lsp` |
| Merge settings | Squash default on, merge trains on, pipeline must succeed; threads do not have to be resolved |
| Commit convention | Conventional Commits with a scope |
| MR template | `.gitlab/merge_request_templates/Default.md` |
| Changelog | semantic-release from Conventional Commits; nothing to edit |
| Contributor docs | `CONTRIBUTING.md`, `AGENTS.md`, `docs/developer/` (including `maintainership.md`) |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Before you start

- Confirm the bug is the client's to fix before writing a client-side workaround. If the server or the workflow service is the real cause, comment on the issue with your analysis and ask whether a client change is wanted. Several MRs were closed because maintainers preferred a backend fix, found the issue no longer reproducible after a service change, or showed the fallback could never run. (observed, 6 MRs; [!4088](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4088), [!3650](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3650), [!3493](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3493), [!3646](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3646))
- The template says the project accepts MRs related to open issues and asks you to discuss first. For a new keyboard shortcut, UI behavior or CLI default on an issue the team did not create, ask the product and UX owners named on the group's handbook page (linked from the issue's group label) to confirm it is wanted; a shortcut MR was closed after implementation. `CONTRIBUTING.md` asks for a new issue, or a comment of interest on an existing one, before you start, but lets trivial changes go straight to an MR. In practice 21 of the last 22 merged community MRs carried `linked-issue`, and a contributor filed a bug issue with reproduction steps the day before opening the MR, and the MR was accepted. (documented and observed, 22 MRs; checked 2026-10-21; `gitlab-org/editor-extensions/gitlab-lsp:.gitlab/merge_request_templates/Default.md@138ff6c6`, `gitlab-org/editor-extensions/gitlab-lsp:CONTRIBUTING.md@059a90db`, [!3369](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3369), [!4409](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4409))
- Ask whether a behavior is intentional before changing it; one MR was closed as wontfix (headless runs must auto-approve MCP tools). (observed, 1 MR; [!3683](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3683))

## Commits and description

- Use Conventional Commits with a scope (`feat(cli):`, `fix(tui):`, `refactor(ls):`); the squashed title feeds semantic-release. When the branch conflicts, rebase onto `origin/main`, never merge `main` into it, and push with `--force-with-lease`. (documented; `gitlab-org/editor-extensions/gitlab-lsp:AGENTS.md@f54a6f14`, [!4408](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4408))
- `lint_commit` runs commitlint's `config-conventional` with the header capped at 100 characters (error), body lines at 100 (warning) and a blank line before body and footer, while `docs/developer/commits.md` asks for lines of 72 or less. With squash on (the default) and outside a merge train it lints only the MR title, any `Draft:` prefix removed; on the merge train, and with squash off, it lints the commits that land. It does not run while the title starts with `Draft:`, so a bad title shows up only once you mark the MR ready; reverts, `fixup!` and `squash!` commits and "Merge branch" commits are ignored. (enforced; `gitlab-org/editor-extensions/gitlab-lsp:scripts/commit-lint/lint.js@e376d90b`, `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, `gitlab-org/editor-extensions/gitlab-lsp:docs/developer/commits.md@736d6e6c`)
- For a user-facing Duo CLI change, use a scope from `CLI_CHANGELOG_SCOPES` (`cli`, `duo-cli`, `tui`, `plugin-marketplace`, `plugins`, `marketplace`, `sandbox`, `mcp`, `hooks`, `skills`): the CLI's `/whatsnew` lists only `feat` and `fix` entries with one of them. Mark updates of non-dev dependencies `fix:` and of dev dependencies `chore:`, and start the body with `BREAKING CHANGE:` for a breaking change. (documented; `gitlab-org/editor-extensions/gitlab-lsp:docs/developer/commits.md@736d6e6c`)
- Almost every merge cuts a release: semantic-release makes `feat` a minor and `fix`, `refactor`, `test`, `style`, `perf`, `ci`, `build`, `chore` and `docs(README)` a patch; other `docs` and the type `no-release` make none. The changelog line reads `**<scope>:** <subject> (<hash>) by <commit author name>`, so your type, scope and subject are published as written. (enforced; `gitlab-org/editor-extensions/gitlab-lsp:release.config.js@736d6e6c`)
- Fill the template: related issues, how it was tested with a focus on end-to-end testing and smoke-testing webviews downstream (exact settings, scenarios, edge cases), and the "What CHANGELOG entry will this MR create?" checklist. Do not repeat what CI verifies. (documented; `gitlab-org/editor-extensions/gitlab-lsp:.gitlab/merge_request_templates/Default.md@138ff6c6`)
- If your MR builds on another unmerged MR, keep it in draft, name the dependency and the commit it is based on, and rebase onto `main` once the dependency merges. A stacked draft that did not was closed. (observed, 2 MRs; [!4400](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4400), [!4018](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4018))

## Local checks before pushing

- Run tools through mise from inside the repository, because outside it you silently get a different bun: `mise exec -- bun install`, the package's own typecheck (`packages/cli` uses `bun run build`) or `mise exec -- bun run compile` for cross-package changes, `bun scripts/dev/fix-changed.ts` (eslint and prettier on changed files; the lint job fails on prettier), and `bun run test:unit`. Most packages have a `typecheck` script (`mise exec -- bun run --filter <pkg> typecheck`); `packages/cli/*` and `packages/ls/legacy/*` have none, so run `bun run build` in the package directory, which also checks their tests. When `bun run compile` fails, turbo interleaves every task's output, so rerun the failed package's script in its directory to read the errors; on a cold cache it can take more than 10 minutes. (documented; `gitlab-org/editor-extensions/gitlab-lsp:AGENTS.md@f54a6f14`, `gitlab-org/editor-extensions/gitlab-lsp:lefthook.yml@2b83946a`, [!4404](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4404))
- `bun install` also runs the root `prepare` script, which, unless `CI` is set, sets the local git config `blame.ignoreRevsFile` to `.git-blame-ignore-revs` and installs the lefthook hooks. In a container or sandbox where you want neither, set `CI=1`, as CI does. (enforced; `gitlab-org/editor-extensions/gitlab-lsp:package.json@4da0fc8f`, `gitlab-org/editor-extensions/gitlab-lsp:scripts/git_blame_ignore.mjs@e8ad4251`)
- Every CI job runs by default in `registry.gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/ci-node:<CI_NODE_TAG>` (the tag is in `.gitlab-ci.yml`), Debian bookworm with mise and the tools of `mise/config.toml` (Node 22.22.1, Bun 1.4.2), pulled from the canonical project's public registry so that fork pipelines work. When your host's mise, Bun or system libraries differ, run a job's script in that image with `CI=1` and the job's `NODE_OPTIONS` and `BUN_INSTALL_CACHE_DIR`. (documented in the CI file; enforced; observed, anonymous pull of tag `abe5d1895293f153`, checked 2026-10-22; `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, `gitlab-org/editor-extensions/gitlab-lsp:docker/ci-node/Dockerfile@af3d4f07`, `gitlab-org/editor-extensions/gitlab-lsp:mise/config.toml@4cd9c0be`)
- A change to `mise/config.toml` or `docker/ci-node/Dockerfile` also changes `CI_NODE_TAG`: `verify-ci-node-tag` fails unless it equals the first 16 hex characters of the SHA-256 of the Dockerfile followed by `mise/config.toml`. The lefthook pre-commit command `update-ci-node-hash` rewrites the tag in `.gitlab-ci.yml` and `.gitlab/duo/agent-config.yml` and stages both, so commit them with your change. (enforced; `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, `gitlab-org/editor-extensions/gitlab-lsp:lefthook.yml@2b83946a`, `gitlab-org/editor-extensions/gitlab-lsp:scripts/dev/update-ci-node-hash.ts@11f6055e`)
- Do not edit `packages/cli/app/docs/cli-reference.md` by hand. Put user-facing text (exit-code tables included) in the command's synopsis or option definitions, regenerate with `bun run --filter @gitlab/duo-cli docs` (or `lefthook run pre-commit --force`), as `verify-cli-docs` prints when it fails, and commit the result. The lefthook `gen-cli-docs` hook regenerates the file when `packages/cli/app/src/*_option_defs.ts` or the generator scripts change. (enforced; `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, `gitlab-org/editor-extensions/gitlab-lsp:lefthook.yml@2b83946a`, [!3650](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3650))
- `lint_documentation` runs `scripts/lint-docs.sh` in the docs-gitlab-com lint image: Vale at error level, markdownlint-cli2 and lychee (offline, fragments included) over `docs/`, `packages/cli/app/docs/`, every `packages/**/ARCHITECTURE.md` and `README.md` (markdownlint also `CONTRIBUTING.md`, lychee every root Markdown file). lefthook runs the same script on commit when Markdown changes, with the tools from mise, so run it from inside the repository. (enforced; `gitlab-org/editor-extensions/gitlab-lsp:scripts/lint-docs.sh@059a90db`, `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, `gitlab-org/editor-extensions/gitlab-lsp:lefthook.yml@2b83946a`)

## Code and tests

- `ARCHITECTURE.md` files next to the code under `packages/` are the design contract for their directory. Load their chain with `scripts/arch-context.ts <path>...` before changing files, and run the repository's architecture review skill (`.agents/skills/architecture-review/SKILL.md`) before handing work back. The architecture review account checks MRs against the same chain, and answers "You have insufficient permissions" when a contributor triggers it, so running the skill yourself is how to get ahead of it. (documented; observed, 2 MRs; `gitlab-org/editor-extensions/gitlab-lsp:AGENTS.md@f54a6f14`, [!4400](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4400#note_4004416450), [!4331](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4331#note_3965306441))
- `AGENTS.md` code standards reviewers can hold you to: mark private members with `#` and never write `public`; no `any` in final code (leave a `// FIXME` if one is unavoidable); re-exports only in index files, importing from the original module elsewhere; log through the injected `Logger` or `packages/ls/legacy/common/log.ts`, whose second argument to `info`, `warn`, `err` and `debug` is for an error object only, so objects go into the first argument as `${JSON.stringify(...)}`. (documented; `gitlab-org/editor-extensions/gitlab-lsp:AGENTS.md@f54a6f14`)
- Fix types and tests honestly: do not add optional chaining, defaults or hedges to production code just so test fakes (`createFakePartial`) compile, and do not keep tests that pass whether or not the code exists. (observed, 3 MRs; [!4404](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4404), [!4088](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4088), [!3580](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3580))
- Keep trust boundaries narrow: when adding a path, directory or permission, expose only what the feature needs and say in the description what else becomes reachable. A finding that a whole directory exposed credentials and transcripts went unanswered and the MR was closed. (observed, 1 MR; [!3785](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3785))
- Verify every claim in generated documentation against the code before publishing; unreviewed generated docs and pages were closed. (observed, 2 MRs; [!4355](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4355), [!3733](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3733))

## Review

- Danger runs only the simple roulette here, and `.gitlab/CODEOWNERS` names only technical writers, for root Markdown files and `docs/`: no code path has an owner. Take the code reviewer from the roulette or from recent merged changes to the touched files. The maintainers list is pruned about quarterly (anyone with fewer than 10 reviews in the last six months is flagged), so the roulette's picks usually review here. The Duo flows maintainers use (recommend reviewers, architecture review) answer "insufficient permissions" when a community member triggers them. (enforced; documented; `gitlab-org/editor-extensions/gitlab-lsp:Dangerfile@fc470d95`, `gitlab-org/editor-extensions/gitlab-lsp:.gitlab/CODEOWNERS@a059312b`, `gitlab-org/editor-extensions/gitlab-lsp:docs/developer/maintainership.md@1b3df931`)
- On an MR from the community fork, Danger's "Reviewer roulette" comment comes first from a gitlab-community group service account (the fork pipeline) and again, with the same picks, from this project's bot when a maintainer starts the merge train. Danger does not notify the picks, so neither comment is a review request, and the second needs nothing. (observed, 1 MR; [!4437](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4437#note_4011640145), [!4437](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4437#note_4088401628))
- A reviewer named in the ready may answer gitlab-bot's business-day nudge with an away notice and an offer to pick someone else: ask the next candidate then, as the handbook expects (references/review.md, section 4). On !4437 the roulette's reviewer, asked next with `@gitlab-bot ready`, reviewed on the next working day and approved after the fixes, noting that a maintainer review was still needed, and the first reviewer approved later and started the merge train. (observed, 1 MR; [!4437](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4437#note_4019992480), [!4437](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4437#note_4033415834), [!4437](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4437#note_4088393515), `gitlab-com/content-sites/handbook:content/handbook/engineering/workflow/code-review.md@5f92de45`)
- A first reviewer who is not a maintainer may approve and hand over ("This still need a maintainer review"), so expect a wait for a maintainer after the first approval. In the last 22 merged community MRs (merged 5 to 21 October 2026) the first human note or approval came a median of 0.7 days after opening and the merge 9.3 days after. (observed, 22 MRs; checked 2026-10-21; [!4437](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4437#note_4059045103), [!4402](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4402), [!4377](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4377))
- GitLab Duo can approve and request changes here: its change request blocks the merge until Duo approves a later review or a member bypasses it; on !4409 a maintainer bypassed it, then re-requested Duo, which approved (references/bots.md, section 3). (observed, 2 MRs; [!4409](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4409#note_4048733290), [!4451](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4451#note_4027283122))
- The MR template and the `duo-cli-bug` issue template apply `group::developer clients`, the Bug issue template `group::duo client sdk`, and template quick actions do nothing for a contributor anyway; 18 of the last 22 merged community MRs carried `group::developer clients`. Take the group from the linked issue, otherwise use developer clients, and set it with `@gitlab-bot label`. (documented; observed, 22 MRs; `gitlab-org/editor-extensions/gitlab-lsp:.gitlab/merge_request_templates/Default.md@138ff6c6`, `gitlab-org/editor-extensions/gitlab-lsp:.gitlab/issue_templates/Bug.md@aac351a1`, `gitlab-org/editor-extensions/gitlab-lsp:.gitlab/issue_templates/duo-cli-bug.md@aac351a1`)
- Expect several rounds and design input from UX or another group for TUI and workflow changes. Address blocking threads first, then non-blocking ones, then the description, answering each with the commit that fixes it; offer follow-up issues for non-blocking suggestions you defer. Reviewers mark AI-generated review comments as such. (observed, 3 MRs; [!4400](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4400), [!4408](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4408), [!3650](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3650))
- A Duo error (for example no credits) is not a reason to close an MR; request a human review instead. (observed, 1 MR; [!4234](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4234))

## Troubleshooting

**The fork pipeline is green, but the merge train fails in `integration-test-binaries-linux`, `cli-e2e-test`, `cli-headless-e2e-*` or `integration-test-sandbox-macos`**
- Cause: since an MR merged on 2026-09-23, these jobs are not created in fork MR pipelines. `integration-test-binaries-linux`, `integration-test-vs-code-node-bundle`, `integration-test-browser` and `cli-e2e-test` run only in the canonical project, on the merge train, or in a fork that set its own `GITLAB_TEST_TOKEN`; `cli-headless-e2e-*` runs only in the canonical project, and `integration-test-sandbox-macos` only there or in its security mirror. The cited fork pipeline (33 jobs) was green without them, and they first ran in the merge train (44 jobs). Before that change they failed at once in forks ("GITLAB_TEST_TOKEN not set to a Gitlab PAT").
- Fix: read the failed job in the train pipeline; if your change caused it, fix it, otherwise post the job link and ask the maintainer to re-run it and add the MR to the train again.
- Who can fix it: you for your code; a maintainer for the re-run.
- Sources: `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, [!4115](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4115), https://gitlab.com/gitlab-community/gitlab-org/editor-extensions/gitlab-lsp/-/pipelines/2970673326, https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/pipelines/2966168586, [!3580](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3580)

**lint fails on prettier, or typescript-compiles fails with a type error such as TS2345 in a test**
- Cause: formatting or types differ from CI; a common case is a readonly tuple passed to `it.each`.
- Fix: `bun scripts/dev/fix-changed.ts`, then the package typecheck or `mise exec -- bun run compile`, then commit.
- Who can fix it: you.
- Sources: [!4408](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4408), [!4404](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4404)

**verify-cli-docs fails after you edited `cli-reference.md`**
- Cause: the file is generated from command synopses.
- Fix: move the text into the synopsis, run `bun run --filter @gitlab/duo-cli docs`, commit.
- Who can fix it: you.
- Sources: [!3650](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3650)

**`verify-ci-node-tag` fails with "CI_NODE_TAG mismatch: expected '...', got '...'"**
- Cause: `mise/config.toml` or `docker/ci-node/Dockerfile` changed without a new `CI_NODE_TAG`, either in your commits or in the target branch the merged result includes.
- Fix: run `lefthook run pre-commit --force`, as the job says, and commit `.gitlab-ci.yml` and `.gitlab/duo/agent-config.yml`; if you already did, rebase on `main` and run it again.
- Who can fix it: you.
- Sources: `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`, `gitlab-org/editor-extensions/gitlab-lsp:lefthook.yml@2b83946a`

**`unit-tests` fails with "Open handles detected - failing build" although every test passed**
- Cause: the job runs `scripts/run_test_and_detect_open_handles.sh`, which fails whenever Jest's output suggests `--detectOpenHandles`.
- Fix: run `bun run test:unit -- --detectOpenHandles` on your tests and close the timer, server or stream they leave open.
- Who can fix it: you.
- Sources: `gitlab-org/editor-extensions/gitlab-lsp:scripts/run_test_and_detect_open_handles.sh@f97a0ef9`, `gitlab-org/editor-extensions/gitlab-lsp:.gitlab-ci.yml@4cd9c0be`

## Why MRs here were closed

- Design or product decisions: client-side workarounds for server-side problems, no-ops, intended behavior ([!3369](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3369), [!3493](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3493), [!3646](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3646), [!3650](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3650), [!3683](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3683), [!4088](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4088)).
- Superseded by a maintainer's simpler fix that built on the contribution ([!3580](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3580)).
- Stale: open review feedback, a stacked draft, a failing pipeline ([!3785](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3785), [!4018](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4018), [!1341](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/1341)).
- Duplicates: the issue was assigned to another contributor through the platform minutes earlier ([!4350](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4350), [!4403](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4403)).
- Unreviewed generated content ([!3733](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/3733), [!4355](https://gitlab.com/gitlab-org/editor-extensions/gitlab-lsp/-/merge_requests/4355)).
