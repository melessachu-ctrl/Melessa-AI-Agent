# gitlab-org/gitlab-services/design.gitlab.com

The monorepo for the Pajamas design system site and the `@gitlab/ui` and `@gitlab/svgs` packages. Commits use plain capitalized subjects (no Conventional Commits prefixes), publishable package changes need a changeset, and visual regression screenshots come from CI: the job that commits them works only in the canonical project, so from a fork you apply a pipeline's screenshots locally with a script. Code Owner approval is layered: a file outside the packages needs the design system team even after a GitLab UI maintainer approved.

| Fact | Value |
| --- | --- |
| Default branch | `main` |
| Language | JavaScript and Vue |
| Fork to use | Community fork `gitlab-community/gitlab-org/gitlab-services/design.gitlab.com` |
| Merge settings | Squash default off, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | Capital first letter, no `fix(scope):` prefixes, no trailing period, full URLs for references; checked by lefthook (capital letter only) and, in canonical MR pipelines, Danger |
| MR template | `Default.md` (what the MR does, screenshots, integrations for consumers, checklist with changeset, component labels, UX and accessibility review) and `Documentation.md` |
| Changelog | Changesets (`yarn changeset`, a file in `.changeset/`) per publishable package |
| Contributor docs | `AGENTS.md`, `CONTRIBUTING.md` (links to design.gitlab.com/contribute), `doc/changesets.md`, `packages/gitlab-ui/CONTRIBUTING.md` |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Commits and changelog

- Start commit subjects with a capital letter, do not use prefixes like `fix(scope):`, and do not end with a period. The lefthook commit-msg hook checks only the capital letter; length, the trailing period, the 72-column body and short references are checked by Danger's commit linter, which runs only in canonical MR pipelines (see Visual snapshots and forks), where danger-review failed on a lowercase subject. Check those rules yourself before pushing from a fork. Some merged titles still carry `docs:`; follow the tooling, not those. (enforced; `gitlab-org/gitlab-services/design.gitlab.com:AGENTS.md@6fd1d5a3`, `gitlab-org/gitlab-services/design.gitlab.com:lefthook.yml@786f06f6`, `gitlab-org/gitlab-services/design.gitlab.com:scripts/simple_commit_message_linter.mjs@d858e3ac`, [!6134](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6134), [!6358](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6358))
- Add a changeset (`yarn changeset`) with patch, minor or major for every publishable package (`@gitlab/ui`, `@gitlab/svgs`) whose published output your MR changes; without one the fix gets no release. On a canonical MR pipeline Danger opens a blocking question thread when it is missing (from a fork you check this yourself); resolve it yourself only when nothing observable changes (docs, stories, specs, CI). (enforced; `gitlab-org/gitlab-services/design.gitlab.com:danger/changeset/Dangerfile@6b82ad81`, [!6417](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6417))
- Packages are not published when your MR merges: a scheduled "Publish packages" pipeline releases the pending changesets once a day, in the early afternoon UTC, while `doc/publishing-packages.md` still describes the older publish-on-merge job. The release adds a CHANGELOG line that links the MR and credits its author automatically, so the changeset summary must not link its own MR: write `<Component or function>: <full sentence>`, with full URLs only, never `!123` or `#123`. (enforced; documented; observed, schedule checked 2026-10-21; `gitlab-org/gitlab-services/design.gitlab.com:.gitlab-ci.yml@e513be11`, `gitlab-org/gitlab-services/design.gitlab.com:doc/publishing-packages.md@84541d63`, `gitlab-org/gitlab-services/design.gitlab.com:doc/changesets.md@6a41b172`, `gitlab-org/gitlab-services/design.gitlab.com:scripts/lib/changelog.mjs@3114f65c`, [!5838](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5838))

## Local checks and tests

- Node 22.23.3 and Yarn 1.22.22 are pinned in `mise.toml` (there is no `.nvmrc`), while CI's `NODE_IMAGE` is `node:22.23.4-trixie`; use the CI version (references/local-environment.md, section 1). Install once at the repository root with `yarn install --frozen-lockfile`, even for work in `packages/gitlab-ui`: the root `postinstall` runs patch-package, and the root `prepare` script (`scripts/prepare.sh`) installs the lefthook hooks (unless `CI=true`), builds `@gitlab/svgs` and generates the component API the site reads. Jobs that do not run Cypress set `CYPRESS_INSTALL_BINARY=0` to skip its download; do the same unless you run the integration tests. (enforced; documented; `gitlab-org/gitlab-services/design.gitlab.com:mise.toml@3934b68b`, `gitlab-org/gitlab-services/design.gitlab.com:package.json@d582f45c`, `gitlab-org/gitlab-services/design.gitlab.com:scripts/prepare.sh@5178892f`, `gitlab-org/gitlab-services/design.gitlab.com:.gitlab-ci.yml@e513be11`, `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/.gitlab-ci.yml@8f5d0b49`)
- Before pushing, run `yarn lint` at the root: it runs lefthook's `lint-in-ci` group, the set the CI `lint` job runs, in parallel: ESLint, markdownlint, Prettier, Stylelint and `yarn-deduplicate`. The single tools are `yarn lint:eslint`, `yarn lint:prettier`, `yarn lint:stylelint` and `yarn lint:markdownlint`. A lint failure dropped an approved MR from the merge train. (enforced; documented; `gitlab-org/gitlab-services/design.gitlab.com:package.json@d582f45c`, `gitlab-org/gitlab-services/design.gitlab.com:lefthook.yml@786f06f6`, `gitlab-org/gitlab-services/design.gitlab.com:.gitlab-ci.yml@e513be11`, `gitlab-org/gitlab-services/design.gitlab.com:AGENTS.md@6fd1d5a3`, [!6358](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6358))
- Change or add the component's `*.spec.js` when you change a component or directive; Danger lists the spec files it expected to change. CI runs the `@gitlab/ui` unit suite twice, `ui:unit_tests_vue2` and `ui:unit_tests_vue3` (`VUE_VERSION=3`): in `packages/gitlab-ui` run `yarn test:unit` and `yarn test:unit-vue3`, or for the specs you touched `NODE_ENV=test npx jest <spec>` and the same with `VUE_VERSION=3`. (enforced; `gitlab-org/gitlab-services/design.gitlab.com:danger/gitlab_ui_specs/Dangerfile@e898a86c`, `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/.gitlab-ci.yml@8f5d0b49`, `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/package.json@6d2dcf7d`, [!5562](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5562))

## Visual snapshots and forks

- danger-review runs only in merge request pipelines of the canonical project, not in fork pipelines or merge trains (rule `is-design-gitlab-com-mr`, since March 2026). An MR from the community fork therefore gets no Danger note at all (no blocking changeset thread, no commit message checks, no reviewer roulette) unless a team member starts a pipeline in the canonical project. Check your commit messages and changeset yourself, and pick reviewers from `.gitlab/CODEOWNERS`. (enforced; observed, 3 MRs; `gitlab-org/gitlab-services/design.gitlab.com:.gitlab-ci.yml@e513be11`, [!5801](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5801), [!6446](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6446), [!6417](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6417), [!6372](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6372))
- A community-fork pipeline runs the lint, unit (Vue 2 and Vue 3), integration and visual test jobs, and they can pass. `publish_npm_packages_dry_run`, the Storybook and site review apps, `ui:create_integration_merge_request`, `ui:duo_job` and `ui:update_tokens` work only in canonical MR pipelines, and `ui:update_screenshots`, which fork pipelines do create, cannot push from them (next bullet). From a fork, run `npx changeset status --since=origin/main` locally instead of reading the dry run, and ask a maintainer for a canonical pipeline when the review needs a review app or an integration MR. Fork MRs merge without that: the merge train runs the canonical pipeline once a maintainer sets auto-merge. (enforced; observed, 3 MRs; `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/.gitlab-ci.yml@8f5d0b49`, `gitlab-org/gitlab-services/design.gitlab.com:site/.gitlab-ci.yml@34a1f05a`, `gitlab-org/gitlab-services/design.gitlab.com:.gitlab-ci.yml@e513be11`, [!6446](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6446), [!6450](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6450), [!6452](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6452))
- Visual regression tests fail on any intended visual change. Do not produce the screenshots by hand: they come from CI. `ui:update_screenshots` (manual, or run automatically by the `pipeline:ui-update-screenshots` label) commits them to your branch only in pipelines of the canonical project. In a fork pipeline, since [!6536](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6536) (merged 2026-10-22), it prints the command that applies that pipeline's screenshots and fails when they differ: once `ui:screenshot_collector` has succeeded, run `packages/gitlab-ui/bin/update_screenshots.mjs --pipeline <pipeline url>` from the repository root on your branch (it needs `unzip`, and `GITLAB_TOKEN` set to a `read_api` token when the artifacts are not public), review the changes and commit `packages/gitlab-ui/tests/__image_snapshots__/`. The label runs the job without `allow_failure`, so on a fork MR whose screenshots differ it fails the pipeline; leave it off. Before that MR, maintainers updated the screenshots for fork MRs or recreated two contributions in the canonical project with the contributor credited. (documented; enforced; observed, 5 MRs; `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/doc/contributing/visual_testing.md@8f5d0b49`, `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/bin/update-screenshots.sh@ce9be567`, `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/.gitlab-ci.yml@8f5d0b49`, [!6120](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6120), [!6216](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6216), [!6358](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6358), [!4764](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/4764))

## Design and docs

- No issue is required before an MR: there is no bug issue template, no issue field in the MR template and no Danger rule about issues, and maintenance and docs MRs merged without one. Most community feature and bug MRs pick up an existing `quick win` issue the team filed; linking one adds `linked-issue` (14 of the last 20 merged community MRs carried it). (documented; observed, 20 MRs; checked 2026-10-21; `gitlab-org/gitlab-services/design.gitlab.com:.gitlab/merge_request_templates/Default.md@49df0b00`, [!6450](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6450), [!6452](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6452), [!6417](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6417))
- `@gitlab/ui` serves many products besides GitLab. Do not compute behavior that assumes GitLab's backend (for example query parameters on asset URLs), keep props generic rather than tied to one app's logic, prefer string props over slots where arbitrary markup is risky, and list integration MRs for consumers when the API changes (`ui:create_integration_merge_request` job). A core component change was declined for assuming GitLab hosting. (observed, 3 MRs; [!5091](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5091), [!6120](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6120), `gitlab-org/gitlab-services/design.gitlab.com:.gitlab/merge_request_templates/Default.md@49df0b00`)
- Agree on scope and naming in the issue before restructuring documentation or changing component semantics; design system owners decide information architecture and may ask you to start over. (observed, 2 MRs; [!5998](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5998), [!5802](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5802))
- In site content, use the `<note>` component (not `NOTE:`), keep `<!-- live-example -->` blocks, update the hand-maintained `nav.json` when you move or rename a page, add a 301 to `static/_redirects` with a comment linking the MR, and cross-link component mentions. The `check_links` job may fail without stopping the pipeline, so check links yourself. (observed, 3 MRs; [!5998](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/5998), [!6267](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6267), `gitlab-org/gitlab-services/design.gitlab.com:.gitlab/duo/mr-review-instructions.yaml@de2c0ea4`)

## Review

- Check how `.gitlab/CODEOWNERS` matches your files: it has no named sections, so each changed file is owned by the last pattern that matches it, and the MR needs an approval for each matched pattern. Anything matching only `*` (root scripts, docs outside the packages) needs the Design System maintainers even if a GitLab UI maintainer approved. Under `packages/gitlab-ui/` either the GitLab UI or the Design System maintainers can approve, except that the core components, utilities, directives and tokens listed for it (`src/components/base/<name>/`, `src/components/regions/empty_state/`, `src/components/utilities/<name>/`, `src/directives/`, `src/tokens/`) need a Design System maintainer and `tests/__image_snapshots__/` needs a product designer from the UX designers group, so a visual change always needs a designer's approval besides the engineering one; `/.changeset/*.md`, `package.json` and `yarn.lock` accept either maintainer group, and charts have their own owners. Component changes also need a UX review from a product designer, and accessibility changes an accessibility review. In a canonical MR pipeline Danger's roulette suggests reviewers. (enforced; `gitlab-org/gitlab-services/design.gitlab.com:.gitlab/CODEOWNERS@5531afa3`, [!6452](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6452), [!6389](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6389), [!6358](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6358), [!6390](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6390))
- In the last 20 merged community MRs (June to October 2026), the first human note or approval came a median of about 2 days after the ready request and the merge about 8 days after opening. The first reviewer often approves and asks a second maintainer to review and merge through a merge train, so expect two approvals in sequence. (observed, 20 MRs; checked 2026-10-21; [!6446](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6446), [!6451](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6451))

## Troubleshooting

**Visual snapshot tests fail after an intended visual change, and `ui:update_screenshots` fails in your fork pipeline with "This job cannot push to your branch from a pipeline in a fork."**
- Cause: the job pushes only from pipelines of the canonical project; in a fork it prints the command to apply that pipeline's screenshots instead, and exits with an error.
- Fix: once `ui:screenshot_collector` has succeeded, run the printed `packages/gitlab-ui/bin/update_screenshots.mjs --pipeline <pipeline url>` on your branch, review the changes and commit `packages/gitlab-ui/tests/__image_snapshots__/`. The `--pipeline` option arrived with !6536 (merged 2026-10-22), so rebase a branch that predates it; ask a maintainer if the pipeline's screenshots cannot be applied.
- Who can fix it: you.
- Sources: `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/bin/update-screenshots.sh@ce9be567`, `gitlab-org/gitlab-services/design.gitlab.com:packages/gitlab-ui/doc/contributing/visual_testing.md@8f5d0b49`, [!6536](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6536), [!6120](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6120), [!6216](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6216)

**Danger opens "question (blocking): Does this merge request need any changesets?"**
- Cause: files of a publishable package changed without a changeset (seen only on a canonical MR pipeline).
- Fix: add one with `yarn changeset`; only changesets added or changed in the MR count, and when a later canonical pipeline sees every touched publishable package covered, Danger resolves the thread itself (and reopens it if coverage is lost). Resolve it by hand only when no changeset is needed.
- Who can fix it: you.
- Sources: `gitlab-org/gitlab-services/design.gitlab.com:danger/changeset/Dangerfile@6b82ad81`

**gitlab-bot asks for a `type::bug`, `type::feature` or `type::maintenance` label**
- Fix: comment `@gitlab-bot label ~"type::..."` or use the contributor platform link in the note.
- Who can fix it: you, through the bot.
- Sources: [!6248](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6248)

**An approved MR still cannot merge for a missing Code Owner approval**
- Cause: a changed file's last matching pattern (the `*` fallback or a more specific one) names owners who have not approved.
- Fix: find the last pattern in `.gitlab/CODEOWNERS` that matches each changed file and ask a member of the group it names.
- Who can fix it: you.
- Sources: [!6452](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6452), [!6389](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/merge_requests/6389)
