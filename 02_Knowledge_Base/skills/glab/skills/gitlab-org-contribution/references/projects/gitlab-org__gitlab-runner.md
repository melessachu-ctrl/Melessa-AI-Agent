# gitlab-org/gitlab-runner

GitLab Runner, the Go agent that runs CI/CD jobs: executors (Docker, Kubernetes, shell, SSH, instance, custom), the helper binary and cache code. The MR title becomes the `CHANGELOG.md` entry, features that need a new `.gitlab-ci.yml` keyword must be accepted in `gitlab-org/gitlab` first, and new executors are refused.

| Fact | Value |
| --- | --- |
| Default branch | `main` |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/gitlab-runner` |
| Merge settings | Squash default on with no squash template (the squash commit is the MR title alone), merge commits, merge trains on (the train needs a green pipeline), merged results pipelines on, threads need not be resolved to merge, one approval rule, or two when the MR touches `docs/`, which one writer's approval met on each docs-only MR read (see [Review, labels and release](#review-labels-and-release)) |
| Commit convention | gitlab-dangerfiles commit message rules; no Conventional Commits requirement |
| MR template | `.gitlab/merge_request_templates/Default.md`; `Documentation.md` for docs-only |
| Changelog | Generated from MR titles at release; no file to edit |
| Contributor docs | `CONTRIBUTING.md`, `AGENTS.md`, `PROCESS.md`, `docs/development/_index.md` |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Before you start

- An issue is not required before an MR: 10 of the last 30 merged community MRs had no `linked-issue`, features among them, and the Default template only asks for "relevant issue numbers". The rules below still apply: get assigned to an issue if one exists, and get `gitlab-org/gitlab` to accept a new `.gitlab-ci.yml` keyword first. (documented; observed, 30 MRs; checked 2026-10-21; `gitlab-org/gitlab-runner:.gitlab/merge_request_templates/Default.md@6f507c0d`, [!7432](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7432), [!7273](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7273), [!7495](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7495))
- For a feature that needs a new or changed `.gitlab-ci.yml` keyword or job payload field, get it accepted in `gitlab-org/gitlab` first and link that MR or issue from the runner MR. Do not propose new executors (use the custom executor), or new architectures GitLab cannot build and test on its shared runners. (documented; `gitlab-org/gitlab-runner:CONTRIBUTING.md@ed851f8f`, [!6962](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/6962), [!7432](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7432))
- Do not invest in fixes for the deprecated `gitlab-runner exec`. The docker+machine executor is formally deprecated but still maintained (it runs GitLab.com's hosted Linux runners), so fixes for it are welcome. (documented; `gitlab-org/gitlab-runner:AGENTS.md@aa75f751`)
- Get assigned to the issue before opening an MR: three hackathon MRs were closed because the issue was assigned to someone else. (observed, 3 MRs; [!7611](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7611), [!7612](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7612), [!7617](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7617))
- Trace the code path from production before fixing: a fix to a function with no production caller was closed as a no-op and replaced by removing the dead code. (observed, 1 MR; [!7555](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7555))
- For a CI problem that affects many projects, comment on the issue before opening an MR; a maintainer replaced one with a fix applied the same way everywhere. (observed, 1 MR; [!7610](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7610))

## Title, commits and description

- Write the MR title as the changelog line an administrator reads before upgrading: a clear, specific sentence such as "Fix timestamp in docker executor job output", never "Fixes bug". A plain imperative sentence is the norm; a prefix is optional. (documented; `gitlab-org/gitlab-runner:CONTRIBUTING.md@ed851f8f`)
- Every commit must pass Danger's commit linter: subject of 3 or more words and at most 72 characters, capital first word (after a `fix:` prefix the next word is capitalized), no trailing period, blank line, body wrapped at 72 (URLs excepted), no emoji, full URLs instead of short references, and a body for commits touching 3 or more files and 30 or more lines. (enforced; `gitlab-org/gitlab-runner:Dangerfile@a89440e4`, `gitlab-org/gitlab-runner:AGENTS.md@aa75f751`, [!7432](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7432), [!7268](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7268))
- You do not need to squash yourself: the merge train squashes, keeping you as the author and making reviewers whose commits you take co-authors. If a maintainer offers fixes for their own review comments, take their commits into your MR rather than letting them open one under their name, so you keep the credit. The project sets no squash template, so the squash commit's message is the MR title alone and commit bodies never reach `main`; the merge commit adds the description's closing reference (`%{issues}`), the MR URL and Merged-by, Approved-by, Reviewed-by and Co-authored-by trailers. Its Co-authored-by trailers name the authors of the MR's commits (`%{co_authored_by}`), so a `Co-authored-by:` trailer you write in a commit body for a reviewer whose suggestion you applied locally stays on your branch; the reviewer is credited in Reviewed-by, and in Approved-by once they approve. Put the reasoning and the closing issue reference in the MR description, not only in a commit. (observed, 3 MRs; documented; enforced, project settings checked 2026-10-21; `gitlab-org/gitlab:doc/user/project/merge_requests/commit_templates.md@ae75c0d9`, [!7417](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7417), [!6962](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/6962), https://gitlab.com/gitlab-org/gitlab-runner/-/commit/ee01258a3ad37aabadbe65d704fc41b3fa20ae49, https://gitlab.com/gitlab-org/gitlab-runner/-/commit/b7759a45b904cf12f83b832624d145fdbd700537, and on [!7661](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7661) the commits 1060edae and 32891ef7, each with a reviewer's trailer, the squash commit https://gitlab.com/gitlab-org/gitlab-runner/-/commit/4e0e4c49f27d7c07f8cecb8b6069c7b69e826052 and the merge commit https://gitlab.com/gitlab-org/gitlab-runner/-/commit/f72252efa51b489abe8cefc091a632334b995c77)
- Fill the Default template: What does this MR do, Why was this MR needed, What's the best way to test this MR (commands a reviewer can run; for executor bugs a minimal `.gitlab-ci.yml` or `config.toml`), relevant issue numbers. Use `Documentation.md` only when every changed file is under `docs/`. Templates are not applied to MRs created through the API, so copy the text yourself. Its "What does this MR do?" section is `%{first_multiline_commit}`; replace it with your own words when you paste the template (references/commits-and-descriptions.md, MR descriptions). (documented; `gitlab-org/gitlab-runner:.gitlab/merge_request_templates/Default.md@6f507c0d`, `gitlab-org/gitlab-runner:AGENTS.md@aa75f751`, [!7417](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7417))
- Do not edit `CHANGELOG.md`; it is generated from MR titles. (documented; `gitlab-org/gitlab-runner:CONTRIBUTING.md@ed851f8f`, [!7571](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7571))

## Local checks before pushing

- Run, in this order: `make tools`, `make development_setup` (integration fixtures), `go build ./...`, `go vet ./...`, `go test -race` on the touched packages (the whole tree needs `-count=1 -timeout 30m`), and `make lint` (with the golangci-lint from `mise.toml`, see the next rule). Tests needing Docker, Kubernetes or a real GitLab may fail locally; say which you could not run. (documented; `gitlab-org/gitlab-runner:AGENTS.md@aa75f751`, `gitlab-org/gitlab-runner:docs/development/_index.md@ba94fe20`)
- golangci-lint is not pinned in the Makefile, although `AGENTS.md` says it is: `make lint` runs whatever `golangci-lint` is on `PATH` (`GOLANGLINT ?= golangci-lint`), and `make tools` does not install it. The versions CI uses are in `mise.toml` (Go, golangci-lint, mockery, markdownlint-cli2, Vale, shellcheck, hadolint and others) and in `GOLANGLINT_VERSION` and `GO_VERSION` in `.gitlab/ci/_common.gitlab-ci.yml`, which runs lint in the `runner-linters:<lint>-go<go>` image. Run `mise install` before `make lint`, and lint again a branch prepared before a toolchain bump, the way the merge train will: the train's merged results pipeline lints the branch merged into `main`, with `main`'s `.golangci.yml` and lint image, while the fork's MR pipeline still runs the branch's own CI files and the old image (references/local-environment.md, section 1). Linting the branch itself with the new version reports what the bump fixed or turned off on `main`: after [!7675](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7675), golangci-lint 2.14.0's new `errorsastype` analyzer, which `main` disables, and the deprecated `Transport.Dial`, which that MR replaced with `DialContext`. Without rebasing, `git merge-tree --write-tree upstream/main HEAD` (Git 2.38 or later) prints that merged tree without touching your worktree, and `git archive <tree>` exports it for the lint image. (enforced; documented, with a conflict; `gitlab-org/gitlab-runner:Makefile@6f382196`, `gitlab-org/gitlab-runner:mise.toml@146fb0fe`, `gitlab-org/gitlab-runner:.gitlab/ci/_common.gitlab-ci.yml@cf36569c`, `gitlab-org/gitlab-runner:.golangci.yml@ba94fe20`, `gitlab-org/gitlab-runner:AGENTS.md@aa75f751`, [!7675](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7675), https://git-scm.com/docs/git-merge-tree)
- A local `make lint` that ends with `Timeout exceeded: try increasing it by passing --timeout option` (exit code 4) was cut short: golangci-lint prints its report first and the timeout after it, so the issues it listed, or a `0 issues.`, are not the result to quote. The `go:lint` job runs `make --silent lint` in `$RUNNER_LINTERS_IMAGE` with `LINT_FLAGS: "--color=never --timeout=15m"`, a 20-minute job timeout and the `.go-cache` template, which keeps `GOCACHE` in `$CI_PROJECT_DIR/.gocache` between pipelines. Locally in that image, mount a persistent `GOCACHE` and, on a slower machine, raise the timeout through the Makefile's own variable (`make lint LINT_FLAGS=--timeout=60m`); neither changes what is linted. (enforced; `gitlab-org/gitlab-runner:Makefile@6f382196`, `gitlab-org/gitlab-runner:.gitlab/ci/qa.gitlab-ci.yml@324d49e7`, `gitlab-org/gitlab-runner:.gitlab/ci/_common.gitlab-ci.yml@cf36569c`, https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/commands/run.go#L227-L262, https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/exitcodes/exitcodes.go)
- Until [!7665](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7665) (open, checked 2026-10-24) merges, three unit tests fail on hosts unlike CI's, which runs them on linux/amd64 in UTC: `TestGenerateMetadataToFile` in `commands/helpers` outside UTC, a `TestPrepare` case in `executors/kubernetes` on arm64, and `TestRunnerWrapperCommand_createListener` in `commands` on macOS, whose too long socket path ends in a panic that stops the rest of that package's tests. Run the tests with `TZ=UTC`, and say in the MR which of these failed on your host and why, rather than reading them as your regression. (observed, 1 MR; [!7665](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7665))
- On a heavily loaded machine, `TestServerCertificateChange` in `network` can fail: it makes 10 requests to a TLS server that generates a new 2048-bit RSA key on every handshake, under the client's 10-second `TLSHandshakeTimeout`, and reads `resp.TLS` without checking that the request succeeded, so a slow handshake ends in a panic on the nil response, which stops the rest of the package's tests. Rerun it alone (`go test -run TestServerCertificateChange ./network/`) before you read it as your regression. (enforced; `gitlab-org/gitlab-runner:network/client_test.go@97e99274`, `gitlab-org/gitlab-runner:helpers/certificate/x509.go@572f59d3`, `gitlab-org/gitlab-runner:network/client.go@ba94fe20`)
- `TestCacheArchiverAddingUntrackedFiles` and `TestCacheArchiverAddingUntrackedUnicodeFiles` in `commands/helpers` write files and expect exactly those back from `git ls-files -o -z`, which the archiver runs in the package directory; outside a git repository the command fails, the archiver only logs a warning, and both tests fail. In a tree without `.git` (an export, a copy for a container), run `git init -q && git add -A` there first, so that only the files the tests write are untracked, as in CI's checkout. (enforced; `gitlab-org/gitlab-runner:commands/helpers/file_archiver.go@3b953f25`, `gitlab-org/gitlab-runner:commands/helpers/file_archiver_test.go@a416a8fa`)
- Keep build directives right: unit tests `_test.go` with `//go:build !integration`, integration tests `_integration_test.go` with `//go:build integration` (`make check_test_directives`). When you touch integration tests, compile them with their tags, for example `go vet -tags 'integration kubernetes' ./executors/kubernetes/`: the MR pipeline does not build every combination, and a broken integration test once passed CI. (documented; `gitlab-org/gitlab-runner:docs/development/_index.md@ba94fe20`, [!6557](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/6557))
- No CI job lints the files behind the `integration` or `kubernetes` tags: `make lint`, and the `go:lint` job that runs it in the runner-linters image, lint with the build tag `network_faults` only (`run.build-tags` in `.golangci.yml`). Lint the tagged files you touch yourself, for example `golangci-lint run --build-tags=integration,network_faults ./shells/...`, with the golangci-lint version `GOLANGLINT_VERSION` names. Since nothing lints them, the tagged files on `main` are not kept clean, so such a run over a whole package also reports on files you did not touch: report the result for the files you changed, as [!7677](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7677) and [!7679](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7679) do ("no issues in the new files"). (enforced; observed, 2 MRs; `gitlab-org/gitlab-runner:.golangci.yml@ba94fe20`, `gitlab-org/gitlab-runner:Makefile@6f382196`, `gitlab-org/gitlab-runner:.gitlab/ci/qa.gitlab-ci.yml@324d49e7`, `gitlab-org/gitlab-runner:.gitlab/ci/_common.gitlab-ci.yml@cf36569c`)
- Test a change to generated shell scripts in `shells/shell_writer_integration_test.go` (build tag `integration`) with `shellstest.OnEachShellWithWriter`, which runs the script in bash, Windows PowerShell and pwsh and skips a shell that is not installed. Windows PowerShell exists only on Windows, so its subtest first runs in the Windows integration jobs on the merge train; install pwsh to cover PowerShell syntax locally, and say in the MR which shells you could not run. (enforced; `gitlab-org/gitlab-runner:shells/shell_writer_integration_test.go@2f596852`, `gitlab-org/gitlab-runner:.gitlab/ci/_project_fork.gitlab-ci.yml@c9ac85c6`)
- For `docs/` changes, run `make lint-docs` (Vale, markdownlint-cli2, rumdl with `docs/.rumdl.toml`, and lychee offline), or say you could not run it. The script prints a message and goes on, still passing, for each of those tools it does not find, so run `mise install` first and read its output. The `docs:lint markdown` job runs `apk add --quiet go` and `make lint-docs VALE_MIN_ALERT_LEVEL=error` in `$DOCS_LINT_IMAGE`, the docs-gitlab-com `lint-markdown` image (`alpine-3.24-vale-3.21.0-markdownlint2-0.23.2-lychee-0.24.2-rumdl-0.2.69`), which carries all four tools, so none is skipped there: run those two lines in that image. (enforced; `gitlab-org/gitlab-runner:.gitlab/ci/qa.gitlab-ci.yml@324d49e7`, `gitlab-org/gitlab-runner:.gitlab/ci/_common.gitlab-ci.yml@cf36569c`, `gitlab-org/gitlab-runner:scripts/lint-docs@146fb0fe`, `gitlab-org/gitlab-runner:mise.toml@146fb0fe`, `gitlab-org/gitlab-runner:.markdownlint-cli2.yaml@146fb0fe`, `gitlab-org/gitlab-runner:.vale.ini@801c1388`)

## Code rules

- Follow `AGENTS.md`: wrap errors with `fmt.Errorf` and `%w`, use the logrus logger already imported, table-driven tests with testify, mocks generated with mockery, no `go.mod` changes unless needed, no unrelated refactors, fix the root cause for the whole input class, and keep the old behavior as the default for any new config field (changing a default is breaking). (documented; `gitlab-org/gitlab-runner:AGENTS.md@aa75f751`)
- When a fix would change behavior that existing configurations depend on, the documented path is an `FF_*` feature flag that switches from the old behavior to the new one on demand. A maintainer described the usual shape, a flag that defaults to the current behavior, tests for both modes and a deprecation note before the default flips, and asked for it in a follow-up issue rather than in a documentation MR. (documented; observed, 1 MR; `gitlab-org/gitlab-runner:docs/configuration/feature-flags.md@833d0151`, [!7661](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7661#note_4060211451), [#40168](https://gitlab.com/gitlab-org/gitlab-runner/-/work_items/40168))
- When you add a feature flag, choose where it is read: `Build.IsFeatureFlagOn` reads the build's settings, which take each flag from `[runners.feature_flags]` when the runner configuration defines it and otherwise from the job's variables, so a job can switch such a flag for itself, while `RunnerConfig.IsFeatureFlagOn` reads the configuration only. A flag that limits what a job may do belongs to the second kind, and its description says where it can be changed, as `FF_RESOLVE_FULL_TLS_CHAIN`'s does ("This feature flag can only be disabled in the [`[runners.feature_flags]` configuration]"; `network/gitlab.go` reads it with `config.IsFeatureFlagOn`; the flag is deprecated, to be removed in GitLab Runner 20.0, so the example goes with it). (enforced; documented; `gitlab-org/gitlab-runner:common/build_settings.go@f3e9b4e2`, `gitlab-org/gitlab-runner:common/build.go@f3e9b4e2`, `gitlab-org/gitlab-runner:common/config.go@4e0e4c49`, `gitlab-org/gitlab-runner:network/gitlab.go@a3cdf731`, `gitlab-org/gitlab-runner:helpers/featureflags/flags.go@833d0151`)
- The flags table in `docs/configuration/feature-flags.md` is generated from `helpers/featureflags/flags.go` by `make update_feature_flags_docs`, and the `docs:check feature flags` job fails when the committed table differs: regenerate it, never edit it. Open MRs that add their flag at the same place of `flags.go` ([!7435](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7435) and [!7706](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7706) both append after the last entries) will conflict there and in the table, so whichever merges second is rebased and regenerated. (enforced; `gitlab-org/gitlab-runner:.gitlab/ci/qa.gitlab-ci.yml@324d49e7`, `gitlab-org/gitlab-runner:Makefile@6f382196`, `gitlab-org/gitlab-runner:helpers/featureflags/flags.go@833d0151`, `gitlab-org/gitlab-runner:docs/configuration/feature-flags.md@833d0151`)
- `.golangci.yml` enables `bodyclose` for every non-test Go file, and it can report an `*http.Response` whose body another function closes: `network/gitlab.go` marks such calls `//nolint:bodyclose` with the reason ("body is closed with closeResponseBody function call", "Linting violation here is a false-positive"). When a helper only needs a response's status and headers, pass those values, as the shared check a reviewer sketched on [!7679](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7679#note_4077384400) does (`checkChunkRange(code, status, contentRange, offset, length)`, kept as sketched, with `go:lint` green), and run `make lint` before you reshape a reviewer's signature into one that hands an `*http.Response` around. (enforced; observed, 1 MR; `gitlab-org/gitlab-runner:.golangci.yml@ba94fe20`, `gitlab-org/gitlab-runner:network/gitlab.go@a3cdf731`, https://github.com/timakin/bodyclose/blob/98ded9ab4ef2741bca30b6d18b73bd9b53181cd4/README.md, https://gitlab.com/gitlab-community/gitlab-org/gitlab-runner/-/pipelines/2984163005)
- `.editorconfig` sets `max_line_length = 120` for `*.go` and `*.mod` (140 for YAML), but no linter checks it (`.golangci.yml` enables no `lll`), and `main` already has longer lines (22 in `commands/helpers/cache_extractor.go`, the longest 229 characters). So a reviewer's suggestion that makes a longer line can be applied as written, as on [!7678](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7678#note_4081670421) (a 213-character line, `go:lint` green), or wrapped, as on [!7677](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7677#note_4081717323); say which in the reply. (documented; enforced; observed, 2 MRs; `gitlab-org/gitlab-runner:.editorconfig@c9ac85c6`, `gitlab-org/gitlab-runner:.golangci.yml@ba94fe20`, `gitlab-org/gitlab-runner:commands/helpers/cache_extractor.go@ee01258a`)
- In a test, report from code that a library runs on its own goroutine (an `http.RoundTripper` or `httptest` handler, a callback from a worker pool such as the parallel range download) with `assert` or `t.Errorf`, never `require`: `require` calls `t.FailNow`, which must be called from the test's goroutine and elsewhere only ends the goroutine it runs on, so the code under test loses that work without an error and the test fails later at a misleading place. A reviewer asked for this. (documented, https://pkg.go.dev/testing#T.FailNow; observed, 1 MR; [!7677](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7677#note_4077383119))
- Log fields that are not runner-specific belong in the LabKit fields package; never build field names dynamically. Duo applies this to non-test Go files. (documented; `gitlab-org/gitlab-runner:.gitlab/duo/mr-review-instructions.yaml@9e124c6b`)
- Treat job-controlled input in the runner manager (URLs, paths, variables) as untrusted: no switches that disable TLS verification, limit response sizes, no redirects to arbitrary hosts, https only, no user info in URLs, keep remote response bodies out of job logs or truncate them. (observed, 1 MR with several blocking rounds; [!7432](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7432))

## Docs

- Put the docs change in the same MR as the code. Touching `docs/` makes the bot request a technical writer automatically. (enforced; `gitlab-org/gitlab-runner:PROCESS.md@bc11fbbb`, [!7493](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7493))
- For a docs-only MR, use `Documentation.md` and ask with a bare `@gitlab-bot ready`. With no name given and no reviewer on the MR yet, the command skips its own pick when every changed file is under `docs/` and CODEOWNERS names a writer, and the documentation bot, reacting to the `workflow::ready for review` label the command adds, requests a member of the runner docs maintainers group (`[Documentation]` in `.gitlab/CODEOWNERS`, which owns `/docs/`). The ready then gets no reply from gitlab-bot: the documentation bot's own note and the "requested review from" note for the writer show that it worked (observed, 1: on [!7493](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7493) they came 9 and 10 seconds after the ready). Do not name a reviewer on that first ready, not even a `[Documentation]` member: the command adds the label before it requests reviewers, so the label event the documentation bot reacts to lists no reviewer yet; the bot then requests its own pick and sets the reviewers to that event's list plus the writer, which removes the person you named a second later unless its pick is that same person. If no writer is requested within a few minutes, post `@gitlab-bot ready @<member of [Documentation]>` once the hour limit allows: while the label is set, a second bare ready requests nobody. The documentation bot acts only on an MR that already carries `Community contribution`, so a bare ready processed before gitlab-bot adds that label requests nobody and gets no reply; if you request review under the 70-minute rule of references/review.md, section 1, while the label is still missing, name the writer, `@gitlab-bot ready @<member of [Documentation]>`, whom the documentation bot then leaves in place, since it does not react (observed, 1: on [gitlab-org/gitlab!260638](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/260638) `workflow::ready for review` came a second before `Community contribution`, and no writer was requested until the label was added back). While the MR still has `workflow::ready for review`, `@gitlab-bot ready @<member of [Documentation]>` keeps that reviewer, because the documentation bot reacts only when the label is added. A scheduled gitlab-bot job moves an MR that has the label and no reviewer back to `workflow::in dev` (references/troubleshooting.md); once it has, post a bare `@gitlab-bot ready` again, which adds the label so that the documentation bot requests a writer. (enforced; `gitlab-org/quality/triage-ops:triage/processor/community/command_mr_request_review.rb@837f6867`, `gitlab-org/quality/triage-ops:triage/processor/community/automated_review_request_doc.rb@57fab1af`, `gitlab-org/quality/triage-ops:triage/triage/reaction.rb@839eee7f`, `gitlab-org/quality/triage-ops:triage/processor/community/community_processor.rb@8765efcd`, `gitlab-org/quality/triage-ops:triage/triage/event.rb@6bd2523b`, `gitlab-org/quality/triage-ops:policies/community/hygiene/ping-incorrect-review-label.yml@544fa8e3`, `gitlab-org/gitlab-runner:.gitlab/CODEOWNERS@146fb0fe`)

(enforced; observed, 3 MRs; `gitlab-org/gitlab-runner:.gitlab/CODEOWNERS@146fb0fe`, `gitlab-org/gitlab:doc/api/merge_request_approvals.md@bd47f4ae`, [!7493](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7493), [!7597](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7597), [!7649](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7649))

## Review, labels and release

- Request review with `@gitlab-bot ready @<reviewer>`, choosing from Danger's Reviewer roulette table and from who recently merged changes to the same files; on an MR that touches `docs/` the documentation bot replaces that reviewer a second later, so follow [Docs](#docs) there. `.gitlab/CODEOWNERS` gives `*` to the runner maintainers group, `docs/` to the runner docs maintainers group, and secrets helpers to the pipeline security group. Danger runs in community-fork pipelines here; its roulette table has one Reviewer and one Maintainer slot and links the GitLab Review Workload Dashboard for finding another available reviewer, and before you name its pick, check how many open review requests that person holds (references/review.md, section 4). (documented; enforced; observed, 2 MRs; `gitlab-org/gitlab-runner:.gitlab/CODEOWNERS@146fb0fe`, `gitlab-org/gitlab-runner:Dangerfile@a89440e4`, `gitlab-org/quality/triage-ops:triage/processor/community/automated_review_request_doc.rb@57fab1af`, https://gitlab.com/gitlab-community/gitlab-org/gitlab-runner/-/pipelines/2965270512, [!7662](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7662), [!7679](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7679))
- The approvals come from the CODEOWNERS rules the diff matches, and every section is required (none starts with `^`): the default section's `*` (the runner maintainers group) matches every file, `docs/` included, and `[Documentation]` (the runner docs maintainers group) matches `/docs/`. So an MR that touches `docs/`, a docs-only one included, needs one approval from each group (`approvals_required` 2), which one person in both groups meets with a single approval, and an MR that touches no `docs/` file needs one. Read which rules are still open from `GET /projects/:id/merge_requests/:iid/approvals` (`approval_rules_left`). On an MR that also changes code, a writer in both groups can bring `approvals_left` to 0 before any person has reviewed the code, as on !7630, where the code reviewer the author had asked was still `unreviewed`: rules met is not code reviewed, so keep waiting for that reviewer and remind them, rather than asking anyone to merge. (enforced; documented; observed, 7 MRs; `gitlab-org/gitlab-runner:.gitlab/CODEOWNERS@146fb0fe`, `gitlab-org/gitlab:doc/user/project/codeowners/reference.md@dee712e7`, `gitlab-org/gitlab:doc/api/merge_request_approvals.md@bd47f4ae`, [!7661](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7661), [!7493](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7493), [!7597](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7597), [!7649](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7649), [!7630](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7630))
- Expect the first review a few days after you ask and a merge in about two weeks: in the last 30 merged community MRs (merged 16 September to 21 October 2026) the first human note or approval came a median of 2.1 days after the review request and 3.7 days after opening, and the merge 13.7 days after opening. When the requested reviewer is away or lacks context, team members pass the MR to another reviewer, so one polite follow-up is enough. (observed, 30 MRs; checked 2026-10-21; [!7417](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7417), [!7493](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7493), [!7501](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7501), [!7511](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7511), [!7428](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7428))
- Reviewers use conventional comments (issue, suggestion, nitpick, thought, chore, each blocking or non-blocking); treat the blocking ones as required. (observed; [!7432](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7432))
- Some reviews here come as a batch of comments headed `**Severity:**` (High, Medium, Low or Nit) and `**Lens:**`, some with a `suggestion` block or marked optional, then a short overview note and a "requested changes" review, also when every point is Low or Nit. The MR then reads `requested_changes` until that reviewer approves (references/review.md, section 8), so answer every point, giving the reason for an optional one you leave, push the fixes in one push and re-request the reviewer: on !7661 the reviewer approved and started the merge train after that. (observed, 8 MRs in 2 projects, from more than one reviewer, listed in references/review.md, section 7; [!7661](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7661), High on [!7280](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7280#note_3804788187))
- Threads need not be resolved to merge (`only_allow_merge_if_all_discussions_are_resolved` is false, checked 2026-10-24): [!7635](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7635) merged with the reviewer's threads answered but open. Who resolves a reviewer's threads varies by MR: on !7280 the author resolved all of them after replying or applying the change, before it merged, and on !7661 most of them, and !7661 merged with one thread still open, while on !7635 the author resolved none. Resolve a thread once you have applied the change or answered it so that it needs nothing more from the reviewer, and leave open one that waits on the reviewer's decision (references/review.md, section 8). (enforced; observed, 3 MRs; [!7280](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7280), [!7661](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7661), [!7635](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7635))
- Set type and group labels with `@gitlab-bot label ~"type::bug" ~"group::runner core"`; leave `Review::P1` to `P3`, `priority::`, `severity::` and the milestone to the team. Danger's milestone warning is not yours to fix. (documented; `gitlab-org/gitlab-runner:CONTRIBUTING.md@ed851f8f`, [!7268](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7268))
- Consider splitting when Danger says the MR is "quite big" (it warned at about 600 changed lines). (enforced; `gitlab-org/gitlab-runner:Dangerfile@a89440e4`)
- Rebase when a reviewer asks; a branch far behind `main` also triggers the security policy bot's "mismatch between the scans" warning. ## Troubleshooting

**The community fork pipeline fails at once with "yaml invalid" and 0 jobs; CI lint reports "gitlab_secrets_manager source group with path gitlab-org not found"**
- Cause: from 2026-10-09 the docs review app jobs read `gitlab-org` group secrets, which a fork pipeline cannot resolve, so the whole configuration was rejected ([issue 40099](https://gitlab.com/gitlab-org/gitlab-runner/-/issues/40099)). [!7633](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7633), merged on 2026-10-19, includes those jobs only in canonical pipelines.
- Fix: rebase onto `main` and push. If a branch you cannot rebase still hits it, ask your reviewer once to run a pipeline in `gitlab-org/gitlab-runner`. Do not push empty commits.
- Who can fix it: you (rebase), or a maintainer.
- Sources: [!7628](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7628), [!7630](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7630), [!7597](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7597)

**A docs-only MR's fork pipeline shows "yaml invalid" with 0 jobs while the Pipeline Editor validates the branch**
- Cause: something in the canonical CI files could not be evaluated outside `gitlab-org`.
- Fix: say the docs change is unrelated and ask the writer or maintainer to check or run the pipeline upstream. Do not edit CI files in a docs MR to work around it.
- Who can fix it: a maintainer or member.
- Sources: [!7493](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7493), [!7609](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7609)

**The fork pipeline has no integration, Kubernetes or Windows jobs**
- Cause: community-fork MR pipelines run only the unit tests, lints, check jobs and danger-review (17 jobs, against 86 on the merge train). Linux integration tests, Kubernetes integration, the Windows suites, helper images, binaries, dependency scanning and advanced SAST are left out outside the `gitlab-org` namespace, and fork pipelines have no Windows runners.
- Fix: say in the MR which integration or Windows paths you could not run. For risky shell or Windows changes, ask the reviewer to run a canonical pipeline before merging, because a failure on the train drops the MR from it.
- Who can fix it: a maintainer.
- Sources: `gitlab-org/gitlab-runner:.gitlab/ci/_rules.gitlab-ci.yml@f42ecc6b`, `gitlab-org/gitlab-runner:.gitlab/ci/test.gitlab-ci.yml@95674f10`, `gitlab-org/gitlab-runner:.gitlab/ci/_project_fork.gitlab-ci.yml@c9ac85c6`, https://gitlab.com/gitlab-community/gitlab-org/gitlab-runner/-/pipelines/2965270512, https://gitlab.com/gitlab-org/gitlab-runner/-/pipelines/2949205992

**The fork pipeline is green, but `unit test` shows a warning**
- Cause: in community-fork MR pipelines `unit test` is `allow_failure: true`, so a failure shows as a warning, not as a failed pipeline.
- Fix: open the `unit test` job and check its own status before asking for review; fix what failed.
- Who can fix it: you.
- Sources: `gitlab-org/gitlab-runner:.gitlab/ci/_rules.gitlab-ci.yml@f42ecc6b`, `gitlab-org/gitlab-runner:.gitlab/ci/test.gitlab-ci.yml@95674f10`

**`coverage_fuzzing_unlicensed` fails in a personal fork pipeline**
- Cause: coverage fuzzing needs an Ultimate license; the job is `allow_failure`.
- Fix: ignore it and say so; the community fork avoids it.
- Who can fix it: nobody needs to.
- Sources: [!7428](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7428)

**The security policy bot reports "a mismatch between the scans of the source and target pipelines"**
- Cause: the branch is far behind `main`.
- Fix: rebase and push for a fresh pipeline.
- Who can fix it: you.
- Sources: [!6962](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/6962)

**Green pipeline, but a reviewer says a package does not build with `-tags 'integration kubernetes'`**
- Cause: the MR pipeline does not compile every integration tag combination.
- Fix: run `go vet` with the tags of every integration test file you touched, and fix references to removed helpers.
- Who can fix it: you.
- Sources: [!6557](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/6557)

**After `@gitlab-bot ready @<reviewer>`, a system note shows your reviewer removed and a technical writer requested (or the reverse)**
- Cause: the documentation bot and the ready command both edit the reviewer list on MRs that touch docs.
- Fix: ask for the reviewer again through the contributor platform's Request review with only them ticked or typed, which no hourly limit counts, or run `@gitlab-bot ready @<reviewer>` again after the hour limit; either way, add one line explaining the earlier request was replaced (references/review.md, section 4).
- Who can fix it: you.
- Sources: [!7630](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7630), [!7501](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7501), [!7661](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/7661)
