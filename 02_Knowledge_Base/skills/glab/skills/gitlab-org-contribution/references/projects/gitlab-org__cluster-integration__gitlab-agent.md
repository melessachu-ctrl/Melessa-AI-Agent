# gitlab-org/cluster-integration/gitlab-agent

GitLab Relay, formerly the Kubernetes Agent Server (kas, a name still in wide use), and the GitLab agent for Kubernetes (agentk), built with Bazel; its CI config lives in `.gitlab/.gitlab-ci.yml` (`gitlab-org/cluster-integration/gitlab-agent:README.md@e280a48b`, `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`). `CONTRIBUTING.md` sends contributors to the community fork, which has working CI, and forbids Conventional Commits prefixes. User docs live in `gitlab-org/gitlab`.

| Fact | Value |
| --- | --- |
| Default branch | `master` |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/cluster-integration/gitlab-agent`. `CONTRIBUTING.md` links the older path `gitlab-community/cluster-integration/gitlab-agent`, which redirects there (checked 2026-10-22) |
| Merge settings | Squash default off, merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | Imperative subjects of at most 72 characters, no Conventional Commits prefixes |
| MR template | Default description in project settings (`%{all_commits}` plus `/label ~"group::workflow engine" ~"section::primitives"`), which takes priority over `.gitlab/merge_request_templates/default.md` (`%{all_commits}`, a scalability and availability checklist and older labels) |
| Changelog | Optional `Changelog: <category>` trailer; the release changelog lists only commits that carry one |
| Contributor docs | `CONTRIBUTING.md`, `AGENTS.md`; design docs in `doc/`; user docs in `gitlab-org/gitlab` (`doc/user/clusters/agent`) |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Rules

- Open MRs from the community fork; personal-fork pipelines lacked arm64 runners and some jobs never started. (documented; `gitlab-org/cluster-integration/gitlab-agent:CONTRIBUTING.md@5f1e827d`, [!1388](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1388), [!2157](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2157))
- In the community fork's MR pipeline, unit-test, integration-test, the golangci-lint jobs, shellcheck, verify, logging-field-validator and `agentk:image:ci` run on their own; the relay images, the theseus chart, the AutoFlow load tests and `build-package-and-qa` (a trigger into the omnibus mirror) are manual and you need not start them. A `go.sum` change makes `build-package-and-qa` start on its own and block, one more reason to leave dependency bumps to the dependency bot. The merge train then runs a pipeline in the canonical project. (enforced; observed, 1 MR; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/.gitlab-ci.yml@b2a96e3a`, https://gitlab.com/gitlab-community/gitlab-org/cluster-integration/gitlab-agent/-/pipelines/2933406923)
- A clear fix needs no issue first: nothing in `CONTRIBUTING.md`, the MR template or Danger asks for one, and 4 of the 7 community MRs merged in 2026 had no `linked-issue` (documented; observed, 7 MRs; read 2026-10-26). When you link one, use the general full-URL form (references/commits-and-descriptions.md, Linking the issue), which works here too; other forms are also seen: in the last 100 merged MRs (12 to 26 October 2026) 18 description lines start `Closes #<iid>` or `Close #<iid>` and 12 `Relates to <URL>`, and the community MRs that wrote `Closes #<iid>` got `linked-issue` (observed, 100 MRs; read 2026-10-26). Open an issue first only when maintainers have to choose the approach, and expect that to be slower: the last 22 merged community MRs (February 2024 to October 2026) got a first human review in a median of under a day, while community feature issues have sat for years and some were labelled `backlog::to-be-closed`. (observed, 22 MRs; checked 2026-10-21; [!4665](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4665), [!4656](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4656), [!4598](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4598), [!4431](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4431), [#566](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/issues/566))
- The README sends bug reports and feature requests to this project's tracker and security issues to GitLab's responsible disclosure process. The only issue templates are "Feature Proposal - lean" and "Security developer workflow", so write a bug with the usual summary, steps to reproduce, current and expected behaviour. (documented; `gitlab-org/cluster-integration/gitlab-agent:README.md@e280a48b`, https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/tree/a562427158cad0cd564bc4467092f75c1ca51c9c/.gitlab/issue_templates)
- Write imperative commit subjects of at most 72 characters, wrap bodies at 72, and do not use Conventional Commits prefixes (`feat:`, `fix:`), WIP commits or AI disclaimers. Older merged MRs used `feat:` titles; follow the current files, not the history. `CONTRIBUTING.md`'s Writing quality section governs code comments too, for human and automated contributors alike: say why, never restate the code, and keep explanations and history in the commit and MR; reviewers asked to shorten comments that described the old behaviour or repeated a test. No `Signed-off-by:` or signing is checked, although `CONTRIBUTING.md` places contributions under the DCO and license terms. (documented; observed, 1 MR; `gitlab-org/cluster-integration/gitlab-agent:CONTRIBUTING.md@5f1e827d`, `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`, [!4601](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4601))
- Add a `Changelog: <category>` trailer (added, fixed, changed, deprecated, removed, security, performance, other, as in `.gitlab/changelog_config.yml`) to a user-visible fix that should be listed: each release's `CHANGELOG.md` section is generated from the commits that carry one. Few commits carry one: 2 of the last 300 non-merge commits on `master` (29 September to 26 October 2026), both `fixed`, one a team fix and one from a community MR merged on 2026-10-25 ([!4756](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4756), https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/commit/0ad4b22c6ed89c7e6cd3107b2227edfb447b12e4). (documented; observed, 300 commits; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/changelog_config.yml@1dbadb90`, `gitlab-org/cluster-integration/gitlab-agent:CHANGELOG.md@0581a155`, https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/commit/09df1a7ee820016b5572668efe5d623f42c00f19, [!4654](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4654))
- Run `make test` (or `make quick-test`, and `make test-it`) and `make lint` (`make lint-shell`, `make fmt`). After changing protos, mocks or Go dependencies, run `make regenerate-proto`, `make regenerate-mocks`, `make update-repos` and `make fmt-bazel`, and commit only the generated changes your change needs; reviewers asked contributors to revert unrelated lock and BUILD changes. The `verify` job runs `make verify-ci`, which deletes and regenerates the generated files (protos, vendored types, mocks, flowtest docs, the autocore metrics doc), runs fmt, gazelle and update-repos, checks that the proto breaking change tests list every proto, and fails on any uncommitted diff; run it before pushing. Install the pinned toolchain with `mise install` (`mise.toml`); Bazel is the primary build, and every Bazel Go test target runs under the race detector. (documented; enforced; `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`, `gitlab-org/cluster-integration/gitlab-agent:Makefile@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:.gitlab/.gitlab-ci.yml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:doc/developing.md@af7d7930`, [!1395](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1395))
- **Without Bazel**, `make buildifier` formats the BUILD and Starlark files through `go run` of the latest buildifier, over the Makefile's own file list, which leaves out the flow corpus's `.star` files that buildifier cannot parse. It rewrites in place, so read `git diff` afterwards, or add `--mode=check` to its two lines to only report. Gazelle cannot run at the pinned version without Bazel: `MODULE.bazel` pins `bazel_dep(name = "gazelle", version = "2.0.0-beta.2")`, and `go run github.com/bazel-contrib/bazel-gazelle/v2/cmd/gazelle@v2.0.0-beta.2` stops with "does not contain package github.com/bazelbuild/bazel-gazelle/language/defaults", because that tag's `v2/go.mod` requires nothing and only the repository's `go.work` brings that package in. A copy built from a checkout of that tag would take `-mode=diff` and read the root `BUILD.bazel`'s directives, but that was not tried. Leave gazelle to `verify`, which runs it: on [!4756](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4756) an older standalone gazelle reported no change, and `verify` passed in the fork and train pipelines. (enforced; documented; observed, 1 MR; `gitlab-org/cluster-integration/gitlab-agent:Makefile@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:MODULE.bazel@dce567c2`, `gitlab-org/cluster-integration/gitlab-agent:BUILD.bazel@bc1b8144`, https://github.com/bazelbuild/buildtools/blob/42840eee04cbd3da882aa00134d03d78d824d649/buildifier/README.md, https://github.com/bazel-contrib/bazel-gazelle/blob/v2.0.0-beta.2/v2/go.mod, https://github.com/bazel-contrib/bazel-gazelle/blob/v2.0.0-beta.2/v2/cmd/gazelle/langs.go#L18-L23, https://github.com/bazel-contrib/bazel-gazelle/blob/v2.0.0-beta.2/go.work, https://github.com/bazel-contrib/bazel-gazelle/blob/v2.0.0-beta.2/v2/cmd/gazelle/update/update.go#L163, https://gitlab.com/gitlab-community/gitlab-org/cluster-integration/gitlab-agent/-/pipelines/2984752336, https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/pipelines/2986506903)
- For a quick loop, plain `go test -race ./internal/module/<module>/...` works from the root module without Bazel: CI's FIPS unit test job runs plain `go test` over `./cmd/...`, `./pkg/...` and every `./internal/...` package but `internal/it`, and `pkg/autoflow` separately as its own module. A plain `go build` leaves out the policy engine that Bazel builds in, so flows that load a policy behave differently there. CI's main test jobs run Bazel, so run the Bazel target before pushing (`make test` for all, `bazel test //internal/module/<module>/server:server_test` for one, as `AGENTS.md` shows). `make test-it` and `make test-migrations` need a working Docker setup. Go is pinned in `mise.toml` (1.27.3), above the `go 1.27.0` line of `go.mod`. (enforced; documented; `gitlab-org/cluster-integration/gitlab-agent:Makefile@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:.gitlab/.gitlab-ci.yml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`, `gitlab-org/cluster-integration/gitlab-agent:mise.toml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:go.mod@01d7e093`)
- `logging-field-validator` runs `make validate-log-fields` (LabKit's validator) on Go changes. Log with `log/slog` without the `*Context` variants, use the fields defined in `internal/tool/logz/logz.go`, and do not change the type of an established field. (enforced; documented; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/.gitlab-ci.yml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:Makefile@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`)
- `proto-breaking` checks the protos against the baselines the target branch carries under `build/protobreaking/` (buf's `WIRE` rules for the protos whose encoded rows outlive the process that wrote them or that are spoken across versions; `WIRE_JSON`, which adds the JSON names, for the four configuration files' protos, which are parsed with protojson, so a renamed JSON field breaks them too; between them the two sets cover every proto in the tree but the vendored copies, which neither checks), through Bazel, in MR pipelines that change a `.proto` file, `MODULE.bazel`, `build/protobreaking/`, the Makefile or the CI file, and is allowed to fail by design: a red job asks you to check that what a released version encoded still decodes. The baselines in the tree are kept in step with the protos by `make regenerate-proto`, as the Makefile says, and `verify-ci` checks that the breaking change tests list every proto in their directories. Say in the description why a reported break is safe. (enforced; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/.gitlab-ci.yml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:Makefile@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:build/protobreaking/wire.buf.yaml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:build/protobreaking/config_files.buf.yaml@b2a96e3a`, `gitlab-org/cluster-integration/gitlab-agent:build/protobreaking/BUILD.bazel@092aeb60`)
- Define a feature flag in the `featureflag` package with `NewFeatureFlag(name, defaultEnabled)`, define it in Rails too with the `gitlab_kas_` prefix (a `gitlab-org/gitlab` MR), give it a rollout issue, and test both states; the suite runs with every flag enabled. (documented; `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`)
- There is no `.gitlab/duo/mr-review-instructions.yaml`, so Duo reviews with its defaults; `.gitlab/duo/agent-config.yml` only sets up Duo agent flows. (documented; checked 2026-10-21; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/duo/agent-config.yml@4efd426d`)
- Do not edit generated files such as the agent config JSON schema by hand; change the proto and regenerate. (observed, 1 MR; [!2157](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2157))
- Put new agent settings in the agent configuration file rather than command-line flags (config settings are versioned and reload without a restart), and do not add dependencies to packages kas also imports. (observed, 2 MRs; [!2350](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2350), [!1138](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1138))
- From `AGENTS.md`: keep a module's server and agent code in separate packages so dependencies do not leak; `pkg/tunnel` is a separate in-tree Go module that cannot import the root module; tests use testify `require` and `assert` and `go.uber.org/mock/gomock`; protos use edition 2023 with `buf.validate` rules; code, comments and docs use US English, which misspell enforces. (documented; `gitlab-org/cluster-integration/gitlab-agent:AGENTS.md@0cfa9dec`)
- To call a server-streaming RPC handler in a test, wrap the existing gomock `ServerStream` in grpc's generic type, `&grpc.GenericServerStream[Req, Res]{ServerStream: mock_rpc.NewMockServerStream(ctrl)}`, whose `Send` goes to `SendMsg`, rather than generating a new mock; the Flux server test does this, and passes `cache.NewWithError(0, 0, ...)` so that the zero TTL calls the loader directly instead of needing Redis. (enforced; `gitlab-org/cluster-integration/gitlab-agent:internal/module/flux/server/server_test.go@0ad4b22c`, `gitlab-org/cluster-integration/gitlab-agent:internal/tool/cache/cache_with_err.go@a5769aaa`, `gitlab-org/cluster-integration/gitlab-agent:go.mod@01d7e093`, https://github.com/grpc/grpc-go/blob/v1.84.0/stream_interfaces.go#L207-L220)
- Put user documentation changes in a separate MR in `gitlab-org/gitlab` (`doc/user/clusters/agent`) and link it. When your change depends on `gitlab-org/gitlab` MRs, list them as MR dependencies and say how to test end to end. (observed, 2 MRs; [!2157](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2157), [!2351](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2351))
- Expect a domain reviewer first and then a maintainer from the group `.gitlab/CODEOWNERS` names, who merges through a merge train; when an MR changes behaviour another group owns (for example a Rails internal API a module calls), that group's feature owner reviews first and the code owner second. Danger runs only in merge request pipelines of the canonical project (`# Don't run Danger on MRs from forks.`), so before the merge train there is no Danger comment and no reviewer roulette: choose the reviewer from the CODEOWNERS group. In the canonical pipeline it posts the roulette and the type and subtype checks, and may fail. (enforced; observed, 5 MRs; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/CODEOWNERS@2b455750`, `gitlab-org/cluster-integration/gitlab-agent:Dangerfile@666ad185`, `gitlab-org/cluster-integration/gitlab-agent:.gitlab/.gitlab-ci.yml@b2a96e3a`, [!2177](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2177), [!2193](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/2193), [!4601](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4601))
- The project's owning labels are `group::workflow engine` and `section::primitives`. The default description in project settings, which a new MR gets first, carries them, while `.gitlab/merge_request_templates/default.md` still names `devops::verify` and `section::ci`. None of these quick actions works for a contributor: set `group::workflow engine` and the type with `@gitlab-bot label`. (documented; observed, 2 MRs; `gitlab-org/cluster-integration/gitlab-agent:.gitlab/merge_request_templates/default.md@a40ec50d`, project setting `merge_requests_template` checked 2026-10-21, [!4654](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4654), [!4665](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4665))
- If a maintainer pushes a fix to your branch, another approver is needed; do not ask that maintainer to approve again. (observed, 1 MR; [!4598](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4598))
- Before refactoring a package, look for open MRs that change it and coordinate; a rename was closed because a maintainer was refactoring the same package. (observed, 1 MR; [!1205](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1205))

## Troubleshooting

**GitLabDuo replies "Something went wrong and the review request was stopped. Please request a new review."**
- Cause: the Duo review run failed on a fork MR; the cause is not shown to contributors.
- Fix: do not keep re-requesting; wait for the human reviewer. Maintainers merged all three affected MRs without a Duo review.
- Who can fix it: a maintainer or member.
- Sources: [!4598](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4598), [!4656](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4656), [!4665](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/4665)

**Personal-fork jobs stay pending ("GitLab runner is not active") or arm64 jobs have no runner**
- Cause: personal forks use your own runners and minutes.
- Fix: reopen the MR from the community fork, linking and closing the old one.
- Who can fix it: you.
- Sources: [!1388](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1388), [!1138](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1138)

- A draft overtaken by code changes and split into issues ([!1511](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1511)); accidental MRs ([!1400](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1400), [!1407](https://gitlab.com/gitlab-org/cluster-integration/gitlab-agent/-/merge_requests/1407)).
