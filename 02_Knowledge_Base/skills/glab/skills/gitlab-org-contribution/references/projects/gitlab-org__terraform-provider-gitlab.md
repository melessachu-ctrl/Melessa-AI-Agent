# gitlab-org/terraform-provider-gitlab

The Terraform and OpenTofu provider for GitLab, written in Go on top of client-go. Acceptance tests run against real GitLab containers in child pipelines, a `type::` label is mandatory, and commits follow the plain-sentence style Danger checks, not Conventional Commits.

| Fact | Value |
| --- | --- |
| Default branch | `main` |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/terraform-provider-gitlab` |
| Merge settings | Squash default off (maintainers squashed every merged community MR in the sample), merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | gitlab-dangerfiles commit message rules (warnings) |
| MR template | None; `CONTRIBUTING.md` carries the checklist |
| Changelog | Generated at release from merged MR titles and type labels; never edit `CHANGELOG.md` |
| Contributor docs | `CONTRIBUTING.md`, `AGENTS.md`, `docs/development/CreatingANewResource.md`, and the testing and schema skills under `.agents/skills/` (`AGENTS.md` links the testing one) |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Labels and title

- Make sure the MR carries exactly one of `type::feature`, `type::bug` or `type::maintenance` before the pipeline runs: `validate:mr-labels` fails without one, and because it runs in the lint stage the test stages never start. Set it with `@gitlab-bot label ~"type::bug"`, then push or ask the reviewer to retry the pipeline. (enforced; `gitlab-org/terraform-provider-gitlab:scripts/validate-mr-labels.sh@6c879f50`, `gitlab-org/terraform-provider-gitlab:.gitlab-ci.yml@8c0ffa78`, [!3297](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3297), [!3288](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3288))
- Make the MR title a user-facing sentence naming the resource or attribute. At release a maintainer runs `scripts/generate-changelog.sh`, which copies merged MR titles into `CHANGELOG.md`, files them under FEATURES or BUG FIXES by type label, and prefixes the resources touched. Do not edit `CHANGELOG.md`. (enforced; `gitlab-org/terraform-provider-gitlab:scripts/changelog/main.go@bab674db`, `gitlab-org/terraform-provider-gitlab:.gitlab/changelog_config.yml@2b2a1ebf`)

## Commits

- Write subjects as plain sentences: capital first letter, at least three words, at most 72 characters, a blank line before the body, body lines within 72 characters, a body for commits changing 30 or more lines across 3 or more files, full URLs instead of `!123` or `#123`. Do not use prefixes such as `fix:`, which trip the capital-letter rule. Danger warned 20 times in the sample, 8 of them for a `fix:` prefix. danger-review is `allow_failure`, but reviewers expect the warnings fixed. (enforced; `gitlab-org/terraform-provider-gitlab:Dangerfile@2b2a1ebf`, [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321), [!3296](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3296))
- Nothing checks a DCO sign-off or a commit signature, and the Dangerfile leaves out the changelog rule; community commits merge unsigned. (enforced; observed, 1 MR; `gitlab-org/terraform-provider-gitlab:Dangerfile@2b2a1ebf`, [!3340](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3340))

## Local checks before pushing

- `make reviewable` (build, fmt, generate, unit tests) before every push. It needs network access and changes files: `build` runs `go mod tidy`; `fmt` installs into `./bin` golangci-lint (`@latest`, not the v2.15.0 in `tools/go.mod`, so a new golangci-lint release reaches you and CI the day it ships), shfmt and tfproviderlintx (from `tools/go.mod`), clones and builds Terraform v1.1.4 from GitHub on first use, and runs `golangci-lint run --build-tags acceptance --fix`. Check `git diff` for `go.mod`, `go.sum` and fixed files before you commit. Use the Go in `.tool-versions` (1.26.10, the same as `go.mod` and CI's `GOLANG_IMAGE_VERSION`); the "version 1.20+" in `CONTRIBUTING.md` is out of date. (documented, with a conflict; enforced; `gitlab-org/terraform-provider-gitlab:CONTRIBUTING.md@5230a845`, `gitlab-org/terraform-provider-gitlab:GNUmakefile@0de86535`, `gitlab-org/terraform-provider-gitlab:tools/go.mod@afa6bca9`, `gitlab-org/terraform-provider-gitlab:.tool-versions@8c0ffa78`, `gitlab-org/terraform-provider-gitlab:go.mod@8c0ffa78`, `gitlab-org/terraform-provider-gitlab:.gitlab-ci.yml@8c0ffa78`)
- Acceptance tests sit behind the `acceptance` build tag, so `make test` does not run them. Run them against a local GitLab: `make testacc-up`, `make testacc RUN=TestAccGitlabYourResource_`, `make testacc-down`. `TESTACCTAG=flakey` or `settings` select the other tagged suites. (documented; `gitlab-org/terraform-provider-gitlab:GNUmakefile@0de86535`, `gitlab-org/terraform-provider-gitlab:CONTRIBUTING.md@5230a845`)
- For EE-only resources, run `make testacc-up SERVICE=gitlab-ee` with the license in `Gitlab-license.txt` at the repository root (the Makefile mounts it) or in `GITLAB_ACTIVATION_CODE`, which the container's setup script activates; `CONTRIBUTING.md` links the handbook process through which a community contributor requests one. Without either, the EE container runs unlicensed and still counts as EE: `SkipIfCE` reads the metadata API's `enterprise` flag, which reflects the edition, not the license, so EE-only tests run there and fail where they need licensed features. Without a license, run only the tests that need none, and say in the MR which ran. (enforced; documented; observed, 1 MR; `gitlab-org/terraform-provider-gitlab:GNUmakefile@0de86535`, `gitlab-org/terraform-provider-gitlab:docker-compose.yml@5573b6e9`, `gitlab-org/terraform-provider-gitlab:CONTRIBUTING.md@5230a845`, `gitlab-org/terraform-provider-gitlab:internal/provider/testutil/helpers.go@a496ae5d`, `gitlab-org/terraform-provider-gitlab:internal/provider/utils/license_utils.go@bab674db`, `gitlab-org/gitlab:app/models/app_config/instance_metadata.rb@7a12d2ec`, [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344))
- Without a GitLab instance, compile-check the acceptance-tagged files with `go vet -tags acceptance ./internal/provider/...` and run `make test` for the untagged tests. Even listing the tagged tests (`go test -tags acceptance -list '<pattern>' ./internal/provider/sdk/`) panics without `GITLAB_TOKEN` and `GITLAB_BASE_URL`, because `internal/provider/testutil` creates its test client when it loads; placeholder values are enough for a list, which sends no request (enforced; `gitlab-org/terraform-provider-gitlab:internal/provider/testutil/helpers.go@a496ae5d`). Do not run `go test -tags acceptance` on the package: some of its tests create objects through the API before `resource.ParallelTest` checks `TF_ACC`, so against no instance the first such test fails and its cleanup panics on a nil pointer, which ends the whole package. (enforced; observed, 1 MR; `gitlab-org/terraform-provider-gitlab:internal/provider/datasource_gitlab_application_test.go@bab674db`, [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344))
- There is no `make lint` target. CI runs `make lint-golangci` and a matrix of `make lint-examples-tf`, `lint-examples-sh`, `lint-generated`, `lint-custom` and `lint-tfprovider`; run those before pushing. `lint-generated` runs `make generate` and fails on any change `git status` shows, so run it on a clean tree. `lint-custom` runs `scripts/lint-custom.sh`, which fails a resource or data source whose description lacks an `**Upstream API**: [...](...)` link to the GitLab API page it wraps. (enforced; `gitlab-org/terraform-provider-gitlab:GNUmakefile@0de86535`, `gitlab-org/terraform-provider-gitlab:.gitlab-ci.yml@8c0ffa78`, `gitlab-org/terraform-provider-gitlab:scripts/lint-custom.sh@706f7194`, [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344))

## Code, tests and docs

- Do not hand-edit `docs/`. Change the schema `MarkdownDescription` and the examples (`examples/.../resource.tf` and `import.sh`), run `make generate` (tfplugindocs), and commit the regenerated docs. Duo flagged MRs whose docs were not regenerated. (enforced; `gitlab-org/terraform-provider-gitlab:GNUmakefile@0de86535`, [!3326](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3326))
- Build new resources with the Terraform Plugin Framework, name attributes exactly as the GitLab API does, build the ID from the URL path variables joined with `:`, add no new `//lintignore`, and mark attributes that depend on experimental GitLab features as experimental in their description. (documented; `gitlab-org/terraform-provider-gitlab:CONTRIBUTING.md@5230a845`, `gitlab-org/terraform-provider-gitlab:docs/development/CreatingANewResource.md@bab674db`, [!3286](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3286))
- Before changing or working around an `Optional` + `Computed` attribute, read `.agents/skills/create-update-schema/SKILL.md`, which schema fixes are judged by: plain `Optional` for a value the API never sets on its own; `Optional` + `Computed` (the default for most API-backed optional attributes) with `UseNonNullStateForUnknown()`, or a `Default` when the fallback is a constant; `UseStateForUnknown()` on `Computed`-only attributes. (documented; `gitlab-org/terraform-provider-gitlab:.agents/skills/create-update-schema/SKILL.md@08fb984a`)
- For an `Optional` + `Computed` attribute GitLab never returns, such as a secret, a maintainer asked for `data.Secret = types.StringValue(data.Secret.ValueString())` wherever the state is built from the API response, rather than code that checks for an unknown value: an unconfigured or unknown value is then stored as `""`, not null, and the tests check it with `resource.TestCheckResourceAttr(<resource>, "secret", "")`. Read must do the same, or an imported resource keeps a null that the next update reports as "Provider produced inconsistent result after apply". (observed, 1 MR, approved; [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4082987058), [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4085335959), [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4086412522))
- Read `.agents/skills/test-terraform-resource/SKILL.md`, which `AGENTS.md` marks critical, before writing tests. Every resource change and bug fix gets a Terraform acceptance test in the resource's `//go:build acceptance` test file; a bug fix's test fails without the fix and replays the user-visible scenario as steps ("If the bug was an API rejection, the apply step failing is the test. Do not mock it away."), and a new resource needs create, update and import steps with `ImportStateVerify`. Helpers that the resource's acceptance test reaches get no unit test of their own (state mapping, option builders, plan modifiers, private helpers, anything needing a mock client or a hand-built `tfsdk.State`); plain unit tests are for pure functions in shared packages such as `internal/provider/utils`, `internal/provider/api` and `./scripts`. That skill was merged to `main` on 2026-10-21 (UTC) in [!3355](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3355), so a branch based earlier has no copy: read it, and `AGENTS.md`, from the canonical default branch, not from your branch, after `git fetch upstream` (`git show upstream/main:<path>`, with the remotes of references/workflow.md, section 6), or on gitlab.com; your fork's `origin/main` can be older. (documented; checked 2026-10-26; `gitlab-org/terraform-provider-gitlab:.agents/skills/test-terraform-resource/SKILL.md@63652bc3`, `gitlab-org/terraform-provider-gitlab:AGENTS.md@63652bc3`, `gitlab-org/terraform-provider-gitlab:CONTRIBUTING.md@5230a845`, [!3274](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3274), [!3254](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3254))
- Reviewers ask to remove mock and unit tests from bug fixes or to turn them into acceptance tests; for a very small fix a maintainer preferred no test over a unit test. (observed, 2 MRs; [!3335](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3335#note_4038510426), [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344#note_4036164119))
- For a resource deleted outside Terraform (a 404 on Read), add an acceptance step whose `PreConfig` deletes the object through the API (for example `testutil.DeleteProjectAndWait`) and that checks with `plancheck.ExpectResourceAction(<resource>, plancheck.ResourceActionCreate)` in `PostApplyPostRefresh` that Terraform plans to create it again, as the existing `_deletedOutsideTerraform` tests do. (observed, 1 MR; [!3334](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3334))
- Read must set every attribute the API returns, not only some of them depending on another field (a maintainer: "It should be setting those fields regardless of the value of `Enabled`"). Prove it with a step whose `PreConfig` changes the object through the API and that applies the same configuration with `plancheck.ExpectResourceAction(<resource>, plancheck.ResourceActionUpdate)` in `PreApply`, which fails with "expected Update, got action(s): [no-op]" while Read misses the change, and with an import step whose `ImportStateVerify` covers the field instead of ignoring it. (observed, 1 MR, approved; [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4082987058), [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4083388406))
- For a list data source fixed to read every page, create only as many objects as it takes to pass one page in total, counting what the instance already has, not a full page of new ones; maintainers ask for the fewest API calls. (observed, 1 MR; [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321#note_4000919053))
- An acceptance test that uses `ExternalProviders` (state migration and upgrade tests) must pin a provider version listed in `.gitlab/ci/external-providers.txt`, which is baked into the CI image as a filesystem mirror and checked by `TestExternalProvidersAreMirrored`. Maintainers removed the tests that needed provider 16.x or older because pulling old releases caused 502 errors and rate limiting, then moved the remaining ones to the mirror. Reuse a listed version, and ask before adding one: that also rebuilds the CI image, which the fork cannot do (CI on the fork below). (enforced; observed, 2 MRs and 1 issue; `gitlab-org/terraform-provider-gitlab:internal/provider/external_providers_mirror_test.go@93d18ab2`, `gitlab-org/terraform-provider-gitlab:.gitlab/ci/external-providers.txt@93d18ab2`, [!3292](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3292), [!2949](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/2949), [#6750](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/issues/6750))
- GitLab Duo reviews against `.gitlab/duo/mr-review-instructions.yaml`, which asks for `new(value)` instead of `gitlab.Ptr(value)` in non-test Go files. (documented; `gitlab-org/terraform-provider-gitlab:.gitlab/duo/mr-review-instructions.yaml@ad0c9fe4`)
- `CONTRIBUTING.md` says "It is always best to open an issue before starting on a change", but nothing enforces it: 12 of the last 20 merged community MRs had no `linked-issue`, small bug fixes among them. An issue matters most for a new attribute and for a change that needs a maintainer's decision (next rule). (documented; observed, 20 MRs; checked 2026-10-21; `gitlab-org/terraform-provider-gitlab:CONTRIBUTING.md@5230a845`, [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321), [!3317](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3317))
- If the API field you need is missing from client-go, get it into client-go first and wait for Renovate to bump client-go here. Do not ship a `go.mod` replace pointing at a fork, extra API calls to work around the gap, or version checks for GitLab versions older than the three CI tests. (observed, 5 MRs; [!3254](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3254), [!3236](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3236), [!3282](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3282))
- Before proposing a new attribute, check whether maintainers left it out on purpose or want user demand first; ask in the issue. Two MRs were closed for this. (observed, 2 MRs; [!3276](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3276), [!3252](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3252))

## CI on the fork

- Acceptance jobs (`testacc:acceptance`, `testacc:flakey`, `testacc:settings`) start GitLab CE containers for three versions in child pipelines. `testacc:ee` runs only when `ENABLE_EE_ACCEPTANCE_TESTS` is true, which only the parent project sets. When CE is green, say so, name the resources you changed, and ask the reviewer to run the EE acceptance tests. (enforced; `gitlab-org/terraform-provider-gitlab:.gitlab/ci/test-set.gitlab-ci.yml@51d8e768`, [!3337](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3337), [!3282](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3282))
- A personal fork ran out of compute credits on these pipelines and the MR had to be reopened from the community fork. (observed, 1 MR; [!3311](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3311))
- The community fork has no container registry, so it cannot rebuild the acceptance CI image. An MR that changes `.gitlab/ci/Dockerfile`, `.gitlab/ci/external-providers.txt`, `.gitlab/ci/terraformrc` or `.tool-versions` triggers `acctest:image`, which fails there with "error checking push permissions ... a repository name must be specified", and `testacc:acceptance`, `testacc:flakey` and `testacc:settings` are then skipped. Say so in the MR and ask a maintainer to run the pipeline in the parent project. (enforced; observed, 1 MR; `gitlab-org/terraform-provider-gitlab:.gitlab-ci.yml@8c0ffa78`, [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344))
- Ignore gitlab-bot's note asking the approver to start a new pipeline after the first approval; it is addressed to maintainers. Ignore Danger's milestone and "quite big" warnings, which maintainers handle. (observed, 24 MRs; `gitlab-org/terraform-provider-gitlab:.gitlab-ci.yml@8c0ffa78`, [!3297](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3297))

## Review

- Only a few maintainers can approve. Pick from `.gitlab/CODEOWNERS`; when you need the one already reviewing, @-mention them (that creates a to-do) rather than assigning more people. Expect the maintainer to rebase or rerun jobs near merge. (observed, 3 MRs; `gitlab-org/terraform-provider-gitlab:.gitlab/CODEOWNERS@0f68e7c9`, [!3286](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3286), [!3292](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3292))
- A push that changes the diff removes every approval here, GitLab Duo's included ("reset approvals from @GitLabDuo by pushing to the branch"), so batch review fixes into one push and, once the branch is final, re-request each person the reset note names and ask them to approve again, except GitLab Duo, which needs a new review only while it reads `requested_changes` (references/review.md, sections 8 and 9). (observed, 1 MR; [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344#note_4055962561))
- A maintainer has requested GitLab Duo's review here: after the ready, and again hours after a push that removed Duo's approval. A "requested review from @GitLabDuo" note by a maintainer needs nothing from you. (observed, 2 MRs; [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321#note_4000782373), [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4036144044), and on !3348 [note 4060553248](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4060553248) after the reset note [4055962671](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4055962671))
- All threads must be resolved here, and a maintainer here resolved their own diff threads once the reply named the commit: for a diff thread you answered with a change, reply with the commit and leave the thread to them. The rest are yours to resolve: your own ready threads, the thread of an approving reviewer's optional suggestion you decline without a change (references/review.md, section 9), and GitLab Duo's threads once you have replied in them, since Duo never resolves its own (references/bots.md, section 3). (observed, 2 MRs; [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321#note_4008120369), [!3348](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3348#note_4086508336))
- A collapsed "Personal pre-analysis note" is machine-generated and not a review; do not answer it (references/bots.md, section 6). (observed, 4 MRs; [!3333](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3333#note_3997858178), [!3316](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3316), [!3337](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3337), [!3312](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3312))
- Maintainers hold merges on release day (the provider releases with GitLab's monthly cadence) because the acceptance suite is flaky, and near merge the train has dropped MRs on EE acceptance tests the change does not touch. Comment with the failed job and the same failure on `main`, and ask for the MR to be added to the train again; push nothing. (observed, 3 MRs; [!3313](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3313#note_4023848007), [!3334](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3334#note_4004397748), [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321#note_4033474380))

## Troubleshooting

**validate:mr-labels: "MR is missing a required type label"; test stages never start**
- Cause: no `type::feature`, `type::bug` or `type::maintenance` label.
- Fix: `@gitlab-bot label ~"type::bug"` (or the right type), then push or ask the reviewer to retry.
- Who can fix it: you with the bot command.
- Sources: `gitlab-org/terraform-provider-gitlab:scripts/validate-mr-labels.sh@6c879f50`

**The fork pipeline is green but has no EE acceptance jobs**
- Cause: `ENABLE_EE_ACCEPTANCE_TESTS` is set only in the parent project.
- Fix: comment that CE passes and which resources changed, and ask the reviewer to run EE.
- Who can fix it: a maintainer.
- Sources: [!3337](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3337)

**Danger warns about the commit subject (capital letter, three words, 72 characters, missing body)**
- Cause: the commit message rules check each commit; `fix:` starts lowercase.
- Fix: reword with an interactive rebase and force-push.
- Who can fix it: you.
- Sources: `gitlab-org/terraform-provider-gitlab:Dangerfile@2b2a1ebf`

**`acctest:image` fails with "a repository name must be specified", and every acceptance child pipeline is skipped**
- Cause: the MR changes a file the acceptance CI image is built from, and the community fork has no container registry to push it to.
- Fix: say so in the MR and ask a maintainer to run the pipeline in the parent project; do not change CI to work around it.
- Who can fix it: a maintainer.
- Sources: `gitlab-org/terraform-provider-gitlab:.gitlab-ci.yml@8c0ffa78`, [!3344](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3344)

**The merge train drops the MR on an EE acceptance test your change does not touch**
- Cause: a flaky EE acceptance test.
- Fix: post the failed job and the same failure on `main`, and ask the maintainer to add the MR to the train again; push nothing.
- Who can fix it: a maintainer.
- Sources: [!3334](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3334#note_4004397748), [!3321](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3321#note_4033474380)

**A maintainer or a Duo flow cannot push a fix to your branch (403), and the fix appears on a branch in the parent project**
- Cause: your branch is in a personal fork that members and bots cannot write to.
- Fix: cherry-pick the offered commit and push; next time use the community fork or keep "Allow commits from members who can merge" on.
- Who can fix it: you.
- Sources: [!3286](https://gitlab.com/gitlab-org/terraform-provider-gitlab/-/merge_requests/3286)
