# gitlab-org/container-registry

The GitLab container registry: a Go service with a PostgreSQL metadata database, released by semantic-release from Conventional Commits. A commitlint job checks every commit, and maintainers keep the MR title conventional because the squash commit carries it.

| Fact | Value |
| --- | --- |
| Default branch | `master` |
| Languages | Go, PL/pgSQL |
| Fork to use | Community fork `gitlab-community/gitlab-org/container-registry` (created on a contributor's request after their CI minutes ran out) |
| Merge settings | Squash default on with no squash template (the squash commit is the MR title alone), merge commits, no merge train (auto-merge when checks pass), pipeline must succeed, all threads must be resolved |
| Commit convention | Conventional Commits 1.0, checked by a commitlint job |
| MR template | `.gitlab/merge_request_templates/Default.md` (release-effect checklist, CODEOWNERS approval per category, database checklist) |
| Changelog | Generated by semantic-release; do not edit `CHANGELOG.md` |
| Contributor docs | `CONTRIBUTING.md`, `docs/style-guide.md`; no `AGENTS.md` and no `.gitlab/duo/mr-review-instructions.yaml`, so Duo reviews with its defaults (checked 2026-10-21) |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Commits and title

- Write every commit as a Conventional Commit in lower case (except acronyms and identifiers), with the package (without `registry/`) as scope, `build(deps)` for dependency updates, an optional `(#issue)` suffix and a subject of at most 72 characters. Rebase instead of merging the target branch, and make every commit build and pass tests: commits are reviewed one by one and semantic-release reads them, although with squash on (the default) only the MR title reaches `master` as a commit. (documented; `gitlab-org/container-registry:CONTRIBUTING.md@67a07eb1`) The commitlint job only extends `@commitlint/config-conventional`, which allows headers up to 100 characters and checks no scope, and the Dangerfile leaves out the gitlab-dangerfiles `commit_messages` and `changelog` rules: the 72-character limit and the package scope are left to reviewers, so keep to them yourself. (enforced; `gitlab-org/container-registry:.commitlintrc.yml@3220d96b`, `gitlab-org/container-registry:Dangerfile@20573808`)
- Keep the MR title in the same form, with the prefix your change deserves (`fix`, `feat`, `perf`, `build(deps)`); squash makes the MR title the whole squash commit, and a maintainer had to restore a prefix before merging. Pick the type from the template's checklist, which says which types trigger which release. (observed, 1 MR; `gitlab-org/container-registry:.gitlab/merge_request_templates/Default.md@3a956b60`, [!2947](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2947))

## Checks and docs

- Run `go test` on the touched packages for every commit, commitlint with the repository's `.commitlintrc.yml`, and `make lint-docs` on docs you touch: it runs `script/lint-docs.sh` (Vale, markdownlint-cli2 and an offline lychee check of local links and anchors, over `docs/`, `script/ci_tool/` and `devvm/`) inside the docs-gitlab-com lint image the Makefile names, and the `docslint` job runs it on every MR, so a broken relative link or anchor fails the MR, not only style. (documented; enforced; `gitlab-org/container-registry:CONTRIBUTING.md@67a07eb1`, `gitlab-org/container-registry:.vale.ini@e4ddaac2`, `gitlab-org/container-registry:Makefile@9f52c33a`, `gitlab-org/container-registry:script/lint-docs.sh@9cbdf0ec`, `gitlab-org/container-registry:.gitlab/ci/validate.yml@cee65bb3`)
- Use the LabKit v2 constants from `gitlab.com/gitlab-org/labkit/v2/fields` for log field names: `logging-field-validator` runs `make validate-log-fields` on every change to Go files, `go.mod` or `go.sum` and fails on a deprecated field name. `.labkit_logging_todo.yml` is generated (with the validator's `-update-todo`), not edited by hand, and only for offenses that cannot be fixed right away. (enforced; `gitlab-org/container-registry:.gitlab/ci/validate.yml@cee65bb3`, `gitlab-org/container-registry:.labkit_logging_todo.yml@cee65bb3`, `gitlab-org/container-registry:Makefile@9f52c33a`)
- Tests that touch the metadata database need PostgreSQL, the `integration` build tag and the `REGISTRY_DATABASE_*` variables (`REGISTRY_DATABASE_ENABLED=true`, the host, port, user and password, and `REGISTRY_DATABASE_SSLMODE=disable`). They always connect to a database named `registry_test`, which they may wipe: the test helper sets that name itself, so `REGISTRY_DATABASE_DBNAME` does not change it. The `database:*` jobs start the project's `postgresql-ci:<PG_VERSION>` image with `POSTGRES_ROLE=primary` and set those variables; running that image with the `database:datastore` job's variables and `go test -tags integration ./registry/datastore` reproduces the job. `docs/database-local-setup.md` (Integration tests) does the same against a local server where you create `registry_test` yourself, and `make psql-stack-up` starts the compose stack in `containers/compose-postgres.yml`. Other suites add tags, for example `integration,api_conformance_test` for `./registry/handlers`: take them from the job's `TAGS`. `make test` runs with `-test.short` and leaves these out. CI runs the Go versions in `.go-versions` (1.26 and 1.27) against PostgreSQL 16, 17 and 18. The community fork's MR pipeline runs these jobs too (Troubleshooting below), so this is for a fast local loop and for reproducing a failure. (documented; enforced; observed, 1 MR; `gitlab-org/container-registry:docs/database-local-setup.md@9f52c33a`, `gitlab-org/container-registry:.gitlab/ci/integration.yml@82537bb0`, `gitlab-org/container-registry:registry/datastore/testutil/testutil.go@2ce54bcd`, `gitlab-org/container-registry:.gitlab-ci.yml@b31cd4ab`, `gitlab-org/container-registry:Makefile@9f52c33a`, [!2971](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2971))
- Lint with a golangci-lint built with a Go at least as new as the CI's: `.gitlab-ci.yml` pins `GOLANGCI_LINT_VERSION` (2.15.0) with the note that it "must be built with a Go toolchain >= GO_VERSION, otherwise golangci-lint's type checker panics when loading the newer standard library". (documented; `gitlab-org/container-registry:.gitlab-ci.yml@b31cd4ab`)
- When you change the HTTP API or configuration, update `docs/spec` or `docs/configuration.md` in the same MR, following `docs/style-guide.md`. (documented; `gitlab-org/container-registry:CONTRIBUTING.md@67a07eb1`)
- In tests, do not panic; pass `t` to helpers or return errors. When a migration adds media types, update the golden files in the same MR. (observed, 2 MRs; [!2828](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2828), [!2731](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2731))

## Code rules

- If your change touches the metadata database, fill the template's database checklist. You cannot run postgres.ai: tick the box saying you have no access and ask in a comment for the query plans to be run for you; a maintainer did so for a contributor. (documented; `gitlab-org/container-registry:.gitlab/merge_request_templates/Default.md@3a956b60`, [!2787](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2787))
- Do not change a default value in a bug fix: a default change is breaking and waits for a major release with a deprecation. Reviewers split one out of a TLS fix into a follow-up. When a bug kept a default from ever applying, the baseline is what deployments have been running, not the documented value: making the documented default effective counts as breaking, while honouring an explicitly configured value is the fix. (observed, 2 MRs; [!2958](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2958), [!2960](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2960))
- For a fix that changes how a configuration behaves, say in the description whether the GitLab Helm chart (the `charts/registry` templates) and Omnibus (`gitlab.rb`) can produce the affected configuration: the maintainer checks both before deciding whether the MR needs the `breaking change` label, and asked for one more line on what an ordinary setup would now see. (observed, 2 MRs; [!2960](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2960), [!2971](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2971))
- For a bug on a non-official S3-compatible backend, propose a fix that holds for every backend, not a guard for that one. (observed, 1 MR; [!2885](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2885))
- Do not bump the minimum Go version yourself; it follows the distribution team's schedule. A contributor's bump was finished in a maintainer's MR that kept the commit. (documented; `gitlab-org/container-registry:CONTRIBUTING.md@67a07eb1`, [!2556](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2556))

## Review

- An issue is not required before a bug-fix MR: 15 of the last 24 merged community MRs (April 2024 to October 2026) carried `linked-issue`, the rest merged without one, and no reviewer asked. When one exists, link it on the template's "Related to" line (or `Closes`) and add `CONTRIBUTING.md`'s ` (#issue)` suffix to the commit subject. There is no bug or feature issue template (only Release Plan and a trainee maintainer template), so write an issue with summary, steps, and current and expected behaviour. (observed, 24 MRs; checked 2026-10-21; documented; `gitlab-org/container-registry:.gitlab/merge_request_templates/Default.md@3a956b60`, [!2957](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2957), [!2954](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2954), https://gitlab.com/gitlab-org/container-registry/-/tree/24a4ef3a5fb284816f69c5c974e8df639c07528f/.gitlab/issue_templates)
- Request review with `@gitlab-bot ready @<reviewer>` and add the labels in the same comment: `@gitlab-bot label ~"type::bug" ~"bug::functional" ~backend ~"group::container registry" ~"Category:Container Registry"` (adjust type and subtype). This meets Danger's type and subtype warnings, which come from gitlab-dangerfiles 3.13.0, the release the `Gemfile`'s `~> 3.0` resolves to, but they stay on Danger's comment until the next pipeline, since a label change starts none: leave them, and do not retry the job for them (references/bots.md, section 2). (observed, 4 MRs; [!2958](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2958), [!2962](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2962); the warnings: enforced, `gitlab-org/container-registry:Gemfile@20573808`, `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/rules/subtype_label/Dangerfile@e8c76530`; staying after the labels: observed, 1, [!2978](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2978#note_4081891799))
- Expect two approvals, one from a maintainer, plus a Code Owner approval for the category you touch (storage drivers, database, notifications and so on) as listed in `.gitlab/CODEOWNERS`. A coach assigned by the bot usually forwards the MR to a domain expert. Check each section's paths against the tree before naming a code owner: paths outside the named sections, such as `configuration/`, fall only to the default registry maintainers group, and the `[Rate limiters]` section still names `/registry/ratelimiter/` although the code moved to `registry/middleware/ratelimiter/`, so a change there needs no section owner. In the last 24 merged community MRs (April 2024 to October 2026) the first human note or approval came a median of 0.8 days after opening (0.4 after the review request) and the merge 2.3 days after. (documented; observed, 24 MRs; checked 2026-10-21; `gitlab-org/container-registry:CONTRIBUTING.md@67a07eb1`, `gitlab-org/container-registry:.gitlab/CODEOWNERS@12a619ac`, https://gitlab.com/gitlab-org/container-registry/-/commit/34f0e272848c0810467b8c9775988c97e2bc0d9d, [!2959](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2959), [!2947](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2947), [!2954](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2954))
- Ignore Danger's milestone warning; it appeared on 13 community MRs and none was held for it. (observed, 13 MRs; `gitlab-org/container-registry:Dangerfile@20573808`)
- If a maintainer says the team is not accepting changes for a while (a freeze, as during the artifact registry rollout in September 2026), keep the MR open, rebase it now and then and post a short status note. A blocked MR still counts as in your court for the stale bot; ask for `automation:prevent-auto-close` or agree to reopen after the freeze. One MR in that state was auto-closed while another stayed active and merged. (observed, 2 MRs; [!2932](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2932), [!2947](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2947))
- A release is cut when a maintainer runs the `release:prepare` job, which opens a release MR updating `CHANGELOG.md`; the tag follows its merge. In 2026 tags came 6 to 59 days apart, so a merged fix has no fixed ship date. A `release:backport` job lets maintainers cut a patch release on a maintenance line from cherry-picked commits; do not ask for one in your MR. (documented; observed from tags; checked 2026-10-21; `gitlab-org/container-registry:CONTRIBUTING.md@67a07eb1`, https://gitlab.com/gitlab-org/container-registry/-/tags, [!2821](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2821), [!2885](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2885))

## Troubleshooting

**In a personal fork, SeaweedFS or S3 storage jobs do not run or fail for lack of runners**
- Cause: those jobs need runners a personal fork cannot use; the community fork has them.
- Fix: ask a maintainer to run them; they did so in their own branch or MR while keeping your authorship.
- Who can fix it: a maintainer or member.
- Sources: [!2880](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2880), [!2885](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2885)

**A flaky job such as `api:online-gc` fails in the community fork pipeline**
- Cause: a timing flake.
- Fix: retry it yourself in the community fork and say so in the MR. MR pipelines from the community fork run the whole pipeline (about 320 jobs, the Redis, PostgreSQL and `s3:seaweedfs` integration jobs included), so you see and can retry every job there; an `s3:seaweedfs` failure there is a known flake a maintainer called unrelated.
- Who can fix it: you.
- Sources: [!2947](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2947), [!2971](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2971), https://gitlab.com/gitlab-community/gitlab-org/container-registry/-/pipelines/2972750264, https://gitlab.com/gitlab-community/gitlab-org/container-registry/-/jobs/17334167737

**The commitlint job fails**
- Cause: a commit message is not a Conventional Commit.
- Fix: reword with `git rebase -i`, force-push.
- Who can fix it: you.
- Sources: `gitlab-org/container-registry:.commitlintrc.yml@3220d96b`

**A personal-fork pipeline cannot run because you are out of CI minutes**
- Cause: personal forks consume your own minutes.
- Fix: open the MR from the community fork.
- Who can fix it: you.
- Sources: [!2274](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2274)

- Accidental or test MRs, mostly "Add new file" from the web editor ([!1571](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1571), [!1723](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1723), [!1737](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1737), [!2837](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2837) to [!2839](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2839)). Check the target project and the diff before you click create.
- Stale for months or years ([!1015](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1015), [!1210](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1210), [!1736](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1736), [!2078](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2078)), and one auto-closed during a change freeze ([!2932](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2932)).
- Decided against in the issue ([!2727](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/2727)); a docs deletion with no explanation ([!1995](https://gitlab.com/gitlab-org/container-registry/-/merge_requests/1995)).
