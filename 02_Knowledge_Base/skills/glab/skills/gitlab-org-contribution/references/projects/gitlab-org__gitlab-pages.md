# gitlab-org/gitlab-pages

The Go daemon that serves GitLab Pages sites. Its Danger runs the commit message rule and the danger-review job may not fail, but it runs only in pipelines of the canonical project, so a long commit subject blocks the MR only once a member runs one. Releases follow `GITLAB_PAGES_VERSION` in `gitlab-org/gitlab`.

| Fact | Value |
| --- | --- |
| Default branch | `master` |
| Language | Go |
| Fork to use | Community fork `gitlab-community/gitlab-org/gitlab-pages` |
| Merge settings | Squash default on with no squash template (the squash commit is the MR title alone), merge trains on, pipeline must succeed, all threads must be resolved |
| Commit convention | gitlab-dangerfiles `commit_messages` rule (blocking here, in canonical pipelines only) |
| MR template | `.gitlab/merge_request_templates/Default.md` with a TODO list |
| Changelog | `Changelog:` trailer, read at release; it survives only an MR merged with squash off |
| Contributor docs | `CONTRIBUTING.md`, `PROCESS.md`; user docs live in `gitlab-org/gitlab` |

Each rule ends with its kind and its sources (see the legend in `INDEX.md`).

## Rules

- Open MRs from the community fork; a maintainer asked a contributor to reopen a personal-fork MR there. (observed, 1 MR; [!1324](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1324), [!1346](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1346))
- Prefer issues labelled Seeking community contributions; for a feature without that label, ask in the issue first. Documentation and test fixes merged without an issue: 5 of the last 10 merged community MRs carried no `linked-issue` (four docs changes and one acceptance-test fix). `CONTRIBUTING.md` also warns that if the issue you work on is marked for the current milestone, a team member may take over the MR to finish it before the release. (documented; observed, 10 MRs; checked 2026-10-21; `gitlab-org/gitlab-pages:CONTRIBUTING.md@86bd0df3`, [!1347](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1347), [!1350](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1350), [!1351](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1351))
- Keep every commit subject at most 72 characters and in the gitlab-dangerfiles format. danger-review is not allowed to fail here, but `.gitlab-ci.yml` includes the danger-review component only when `CI_PROJECT_PATH` is `gitlab-org/gitlab-pages` (or its security mirror), so the fork MR pipeline has no danger-review job: the blocking commit check, the reviewer roulette and Danger's warnings appear only once a member runs a pipeline in the canonical project, usually when the maintainer picks the MR up. Check commit subjects yourself before the first push. (enforced; `gitlab-org/gitlab-pages:Dangerfile@1861157b`, `gitlab-org/gitlab-pages:.gitlab-ci.yml@80b941cc`, [!1351](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1351), [!1368](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1368))
- Start the MR with one commit (or a few logical ones) and add review changes as new commits rather than squashing. Add a `Changelog:` trailer, as the template's TODO list asks, but know that a squash at merge keeps only the MR title: squash is on by default and no squash template is set, so GitLab writes a title-only commit and drops every commit body with its trailer, even for a single commit with a body. A commit survives only when its whole message equals the MR title, and an MR merged with squash off keeps its commits and trailer. For a change that needs a changelog entry, untick "Squash commits when merge request is accepted" before the MR joins a merge train, or ask the maintainer to keep the trailer in the squash message. With squash off, fold review commits into the trailer commit and force-push before approval, since the canonical Danger fails `fixup!` and "Apply N suggestion(s)" commits. (enforced; observed, 4 MRs; `gitlab-org/gitlab-pages:CONTRIBUTING.md@86bd0df3`, `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/plugins/commit_messages.rb@7dccad2f`, `gitlab-org/gitlab-pages:.gitlab/merge_request_templates/Default.md@f0a44240`, https://gitlab.com/gitlab-org/gitlab-pages/-/commit/e8425efe1e3ead198f26045099c579bd3a2fad0f, https://gitlab.com/gitlab-org/gitlab-pages/-/commit/98c754bde30b43deee85ba362b3c2e26b6c81fc8, [!1358](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1358), [!1352](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1352), [!1213](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1213))
- Untick squash only when the branch is already final (one commit, or every commit passes the commit linter): with squash off every commit lands on `master` and the canonical Danger checks each one, so review, `fixup!` or suggestion commits must first be folded and force-pushed before approval (previous rule). Unticking squash is not a push, so it keeps the approvals even after the MR is approved: of the changes to the MR itself, only a push to the source branch that changes the diff, or a change of target branch, removes them (references/review.md, section 9), and re-requesting an approver removes theirs (references/review.md, section 8). As the author you can do it yourself, with the checkbox or `PUT /projects/:id/merge_requests/:iid` with `squash=false`; do it before the MR joins a merge train. (enforced; observed, 1 MR; `gitlab-org/ruby/gems/gitlab-dangerfiles:lib/danger/plugins/commit_messages.rb@7dccad2f`, `gitlab-org/gitlab:ee/app/services/merge_requests/refresh/approval_service.rb@31e0b32d`, `gitlab-org/gitlab:ee/app/services/ee/merge_requests/update_service.rb@d57af028`, [!1368](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1368))
- Nothing checks the `Changelog:` trailer: the Dangerfile imports the gitlab-dangerfiles rules except changelog, and at release `CHANGELOG.md` is generated from the trailers on `master` through the repository changelog API. A missing or misspelled trailer is never reported; the change just has no entry. (enforced; `gitlab-org/gitlab-pages:Dangerfile@1861157b`, `gitlab-org/gitlab-pages:.gitlab/scripts/changelog.sh@b3104e69`)
- Besides unit and acceptance tests, CI runs `check deps` (`make deps-check`), `check mocks` (`make mocks-check`; regenerate the mocks when an interface changes), `logging-field-validator` (`make validate-log-fields`), code_quality (golangci-lint; locally `make lint`, or `make format`, which runs it with `--fix`), race, cover and a FIPS build, the tests and FIPS build on every Go version the `.go-versions` list in `.gitlab/ci/test.yml` names (1.26 and 1.27, checked 2026-10-22). Run the matching targets before pushing; code_quality has failed on import formatting. (enforced; observed, 2 MRs; `gitlab-org/gitlab-pages:.gitlab/ci/test.yml@80b941cc`, `gitlab-org/gitlab-pages:Makefile.util.mk@6af0d530`, [!1139](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1139), [!776](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/776))
- Lint with Go 1.26. `make lint` and `make format` run golangci-lint v2.12.2 through `go run` with the Go on `PATH`, and code_quality runs the `golangci/golangci-lint:v2.12.2` image, which is built on Go 1.26. golangci-lint added Go 1.27 support only in v2.13.0, so with the Go 1.27 that `.tool-versions` names (`go.mod` says `go 1.26.0`, with no `toolchain` line) v2.12.2 can fail on the standard library itself. `make lint` also pipes golangci-lint through `tee` without `pipefail`, so it exits 0 even when lint fails: read its output. Lint in the code_quality image, or with `GOTOOLCHAIN=go1.26.<patch>`, and say in the MR which one you used. (enforced; documented; `gitlab-org/gitlab-pages:Makefile.util.mk@6af0d530`, `gitlab-org/gitlab-pages:Makefile@6e308278`, `gitlab-org/gitlab-pages:.gitlab/ci/test.yml@80b941cc`, `gitlab-org/gitlab-pages:.tool-versions@7a7d740a`, `gitlab-org/gitlab-pages:go.mod@9f8ddcf7`, https://github.com/golangci/golangci-lint/blob/v2.12.2/build/buildx.Dockerfile, https://github.com/golangci/golangci-lint/blob/v2.14.0/CHANGELOG.md, [!1367](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1367), [!1368](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1368))
- Log fields follow the LabKit field standard: `logging-field-validator` rejects deprecated field names, and Duo's review instructions ask that a field that is not service-specific come from the LabKit fields package and not be built dynamically. `.labkit_logging_todo.yml` is generated and lists existing offenses; never edit it by hand. (enforced; documented; `gitlab-org/gitlab-pages:.gitlab/duo/mr-review-instructions.yaml@dd36597b`, `gitlab-org/gitlab-pages:.labkit_logging_todo.yml@3f432dc4`, `gitlab-org/gitlab-pages:.gitlab/ci/test.yml@80b941cc`)
- `build-package-and-qa` triggers an omnibus package build and QA downstream. On most MRs it is a manual job that may fail; for an MR that changes `go.mod` or `go.sum` it starts on its own and may not fail, so a dependency change needs that downstream build to pass. (enforced; `gitlab-org/gitlab-pages:.gitlab/ci/test.yml@80b941cc`)
- Add acceptance tests for behavior changes, and keep tests and comments to what the change needs; reviewers asked contributors to remove redundant generated tests and comments. (observed, 4 MRs; [!1140](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1140), [!1179](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1179), [!1347](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1347))
- The acceptance tests run the `gitlab-pages` binary at the repository root (flag `-gitlab-pages-binary`, default `../../gitlab-pages`), not the code in your tree: rebuild it with `make gitlab-pages` before `go test ./test/acceptance/...`, or use `make acceptance`, which builds it first. Without the binary they stop with "Couldn't find gitlab-pages binary"; with a stale one they test the old code. `go test -short ./...` (`make unit-test`) skips them. (enforced; `gitlab-org/gitlab-pages:test/acceptance/acceptance_test.go@6c158e6c`, `gitlab-org/gitlab-pages:Makefile.util.mk@6af0d530`, `gitlab-org/gitlab-pages:Makefile.build.mk@dc7095a1`)
- Rebase on the canonical `master`, not on your fork's possibly stale `master`, and check that no editor files (such as `.idea`) are committed. (observed, 3 MRs; [!1139](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1139), [!1141](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1141))
- Do not add configuration options or flags unless the issue asks for them; `CONTRIBUTING.md` lists "doesn't add configuration options" among the acceptance criteria. Security-sensitive changes go to an AppSec review that may reject them: an MR adding a TLS key log flag was closed because it would expose every tenant's traffic. Discuss the threat model in the issue first. For code that runs shell commands, reads or opens files or handles paths on disk (most of the serving code), `CONTRIBUTING.md` requires GitLab's shell command guidelines, and for code that creates files, the shared files guidelines. (documented; `gitlab-org/gitlab-pages:CONTRIBUTING.md@86bd0df3`, [!1346](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1346))
- Show the behavior: attach a before and after recording for user-visible changes, and run the example when you change docs. (observed, 2 MRs; [!1256](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1256), [!1348](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1348))
- Review is an initial reviewer plus a maintainer; trivial fixes may go straight to a maintainer. To find a reviewer for an area, `CONTRIBUTING.md` suggests the commit history of the affected files; `.gitlab/CODEOWNERS` names the Pages maintainers group. `@gitlab-bot ready @<maintainer>` works here: the maintainer requested GitLab Duo and an initial reviewer from the team and stepped back, then approved and merged once the initial reviewer approved and handed back. In the last 20 merged community MRs (July 2023 to October 2026) the first human note or approval came a median of 1.8 days after opening and the merge 4.8 days after. (documented; observed, 20 MRs; checked 2026-10-21; `gitlab-org/gitlab-pages:PROCESS.md@2dcda77d`, `gitlab-org/gitlab-pages:CONTRIBUTING.md@86bd0df3`, [!1358](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1358), [!1350](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1350), [!1347](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1347))
- The MR template ends with a `/label` line naming a group that no longer owns Pages, which does nothing for a contributor anyway. gitlab-bot's ML triage labels a community MR within about two days (`type::bug`, `backend`, `Category:Pages`, `bug::functional`), and once `Category:Pages` is set it adds `devops::plan`, `section::dev` and the group that owns Pages, so `@gitlab-bot label ~"type::bug" ~"Category:Pages"` is enough. (observed, 3 MRs; `gitlab-org/gitlab-pages:.gitlab/merge_request_templates/Default.md@f0a44240`, [!1349](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1349), [!1325](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1325), [!1367](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1367))
- After merge, a maintainer bumps `GITLAB_PAGES_VERSION` in `gitlab-org/gitlab`; your change ships with that bump. (documented; `gitlab-org/gitlab-pages:PROCESS.md@2dcda77d`, [!1213](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1213))

## Troubleshooting

**danger-review fails on a commit message (for example a subject over 72 characters)**
- Cause: the commit message rule is active, the job may not fail, and it runs only in a canonical pipeline a member started.
- Fix: reword with an interactive rebase, force-push, and ask for a new canonical pipeline.
- Who can fix it: you, then a member for the pipeline.
- Sources: `gitlab-org/gitlab-pages:Dangerfile@1861157b`, `gitlab-org/gitlab-pages:.gitlab-ci.yml@80b941cc`, [!1351](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1351)

**"removed this merge request from the merge train because the pipeline did not succeed"**
- Cause: usually a flaky acceptance test (for example `TestVFSFindOrOpenArchiveConcurrentAccess` or an "address already in use" port clash), sometimes a real failure.
- Fix: read the failed job; if it is flaky and unrelated, post the job link and ask the maintainer to retry and re-add the MR; if it is yours, fix it.
- Who can fix it: a maintainer or member.
- Sources: [!1350](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1350), [!1143](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1143), [!1353](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1353)

**code_quality fails on imports**
- Cause: imports not formatted with goimports and gci.
- Fix: run both (or `make format`), amend, push.
- Who can fix it: you.
- Sources: [!1139](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1139)

**A failing job looks unrelated**
- Fix: retry it if you can (in your fork pipeline) or ask a developer with the job link. Members can also run a pipeline for a personal-fork MR in the parent project once they have read the code.
- Who can fix it: you, or a member.
- Sources: `gitlab-org/gitlab-pages:CONTRIBUTING.md@86bd0df3`, [!774](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/774)

## Why MRs here were closed

- Stale drafts and refactors with unanswered review questions, some for years ([!418](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/418), [!524](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/524), [!774](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/774), [!776](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/776), [!793](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/793), [!800](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/800), [!1256](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1256)); one author could not get race and acceptance jobs green and closed it ([!1087](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1087)).
- Rejected on AppSec advice ([!1346](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1346)); a duplicate ([!1304](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1304)); a reopen from the community fork ([!1324](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1324)).
- Research or accidental MRs ([!1318](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1318), [!1355](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1355), [!1330](https://gitlab.com/gitlab-org/gitlab-pages/-/merge_requests/1330)); the last one also exposed a credential in its description. Never paste a token into an MR; revoke it at once if you do.
